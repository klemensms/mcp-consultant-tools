# Release Notes: v35.0.0-beta.16

**Date:** 2026-08-13
**Branch:** `release/35.0`
**Status:** Published to beta

> Per-iteration agent-level detail. The user-facing single source of truth is [`v35.0.0.md`](v35.0.0.md).

## Overview

Acts on the first live test of the four tools shipped in beta.15. **All four work.** The test found three defects — one of them a safety issue worth acting on before the package is used to DM anyone — plus a flag-naming inconsistency.

`teams` and `meta` only. No new scopes; the beta.15 consent step is not repeated.

## Changes Implemented

### 1. A guest is no longer resolved from a name (safety)

`resolveDirectoryUser()` refuses a guest identified by anything other than their exact `mail` or `#EXT#` UPN, naming the address to re-run with.

**Why the existing ambiguity guard did not cover it.** That guard refuses to pick between several matches. A first name matching exactly one supplier and *no* colleague is not several matches — it is one, cleanly resolved, and sent to. The live test found a single common first name returning six people, four of them outside the tenant, one of them a personal Gmail address. Any of those four alone would have been messaged silently.

- **A full display name does not count as consent.** It is enough to disambiguate but is not the deliberate act reaching outside the organisation should take. Pinned by a test.
- **An error, not a warning.** The caller is usually an agent; a warning printed after the message has gone is not a guard.
- **Covers @-mentions**, which share the resolver — `@[Sam]` in a channel post notifies a guest and hands them the thread. Pinned on that path separately rather than trusting the shared resolver.
- **Guest detection reads the `#EXT#` UPN marker, not `userType`.** The live test confirmed `userType` returns `null` for every user on `User.ReadBasic.All`; reading it needs `User.Read.All`, which is not consented and is not worth a scope request for a label. *Ceiling: someone genuinely external holding a full member account reads as a colleague.*
- `find-user` output gains an **In org** column, and the ambiguous-match candidate list marks guests inline.

Alternatives considered and rejected: filtering guests out (DMing a genuine external collaborator is legitimate), and warning only (an agent may never surface the warning to a human).

### 2. `search-messages` hits carry their deep link again

`search-service.ts` read `resource.webUrl`. **Graph names the field `webLink` on a search hit** — uniquely; every other message endpoint says `webUrl`. Reading an absent property is silent, so the field was never populated and nothing said why.

Two things were broken independently, and fixing either alone would have shown nothing:

- the mapper read the wrong property — now `resource.webLink ?? resource.webUrl`, keeping the other as a fallback;
- `formatSearchResults()` **never rendered the field at all**, even when populated. Each hit now prints a `View:` line.

### 3. `search-messages` no longer hands back a team id that no read accepts

A channel hit's `channelIdentity.teamId` is relayed straight from Graph, and for a **private-channel** hit it is that channel's own backing group rather than the parent team. Feeding it to `get-channel-messages` fails with `Group ID '…' is not found` — an error that reads like a permission or deletion problem rather than a wrong argument.

`confirmChannelTeams()` now:

1. calls `/me/joinedTeams` once and keeps any hit whose team is among them — **this settles the ordinary case in one call, and no channel walk runs**;
2. for a hit that fails that check, walks joined teams' channels to find the one holding the hit's `channelId`, stopping as soon as every unplaced channel is found (*ceiling: `MAX_TEAM_SCAN` = 20 teams*);
3. **drops the field** on a hit it cannot place, rather than keeping a value that will fail. The renderer says the team could not be identified and points at the link.

A failure reading the directory does not fail the search — the hits are still worth having — but it does clear every channel hit's team id, since none is then confirmed.

### 4. `search-messages` takes `top`, not `size` (breaking)

The lone outlier among six reads, all of which already said `top`. Renamed on the MCP schema and the CLI (`-n, --size` → `-n, --top`). **The Graph wire field stays `size`**, which is what `/search/query` accepts — a test asserts the split.

Failure mode differs by surface: the CLI rejects `--size` by name; the MCP tool silently ignores an unknown `size` and returns the default 20.

### 5. Documentation

The four beta.8 tools had never been documented. `docs/documentation/TEAMS.md` listed 16 tools while `README.md` said 20, and `TEAMS_TECHNICAL.md` had no Tool Reference entries for them — only a research row under "Viable, not yet built". Both docs now cover all 20. Removed as stale: "@-mentions require the target's AAD user id … no directory-lookup tool should be added", "Chat creation is unavailable", and the "not built yet" section. Added: `edit-channel-message` and message deletion as permanent exclusions.

## Testing

`teams` suite **111 → 128**. Full monorepo build (`tsc --build`) and all 14 suites green.

New coverage:

| Area | Cases |
|------|-------|
| Guest guard | Refused from a bare name; refused from a full display name; resolved from exact `mail`; resolved from `#EXT#` UPN; colleague still resolves from a bare first name; guests marked in the ambiguous-candidate list; **nothing posted** on refusal |
| Guest guard on mentions | `@[name]` of a guest refused; `@[exact@address]` of the same guest resolves |
| `webLink` | Deep link read from `webLink`; `webUrl` still honoured as fallback |
| Team confirmation | Kept when the team is joined (**and no channel walk runs** — an absence); replaced when it is a private channel's backing group; walk stops as soon as everything is placed; dropped when unplaceable; hits survive a directory-lookup failure minus their team ids |
| `top` | Clamped, and sent as Graph's `size` |

The existing `channelHit()` fixture said `webUrl` because it had been copied from the Graph reference. It now says `webLink`, matching the live capture.

Runtime, against the clean build: the server registers **20 tools** over real MCP stdio with `search-messages` advertising `top`; the built CLI reports `-n, --top`. The rendered output of both changed renderers was read directly rather than inferred from assertions, which caught a singular/plural slip the tests did not.

## Known Issues

**None of this wave has been verified against live Graph.** No Teams credentials on the build machine — no `TEAMS_CLIENT_ID`/`TEAMS_TENANT_ID`, no token cache.

- **The `webLink` read** is evidence-backed — the field name comes from a live capture in the test report — but the fixed code path has not run.
- **The private-channel diagnosis is inference.** The symptom is measured (a team id Graph rejects, on a hit from a private channel); the explanation for *why* is not. The repair does not depend on it: every channel hit is confirmed against joined teams regardless of the cause.
- **The guest guard is fully provable without Graph** and is covered on both exposure paths. The one live-dependent assumption is that guests in this tenant carry `#EXT#` UPNs, which the report's data is consistent with but did not print.

Check first, in one session: a search returning a hit in a **standard** channel and one in a **private** channel, and that both hits' `teamId` feed `get-channel-messages` successfully.

**Carried forward from beta.15:** `send-direct-message` has still never actually sent. Every safe target has a cost — no self-chat exists, so messaging yourself exercises the *create* path and leaves a thread nothing in this package can delete, and messaging a colleague pings a real person with a test message. Choosing the target is the maintainer's call.

**Also carried forward:** nothing here can delete a message it posted. Four test messages now sit in the test tenant.
