## ⚠️ This release contains breaking changes

v33 renames one Figma sticky-note category returned by `get-figma-semantic`: the blue category previously emitted as `si-investigation` is now `investigation`. The old name is still accepted on input — `stickyColorOverrides` values using `si-investigation` keep working and are normalized to `investigation` — so existing configs won't error. But anything that **reads** the old string from the output (automation or scripts keying off sticky categories) must be updated. Hand the upgrade prompt below to your Claude agent — or just rename the string yourself. Everything else in v33 is drop-in.

## Overview

v33 is a focused release centred on three changes:

1. A new opt-in `mcp-warm-secrets` CLI in `@mcp-consultant-tools/core` that pre-resolves all `op://` 1Password references in an `.mcp.json` with a single prompt per account, so concurrently-launched MCP servers don't each trigger their own prompt.
2. A correctness fix making `sync-work-item-to-file` (Azure DevOps) genuinely read-only against ADO — pulling a work item no longer writes back to the source.
3. A follow-up data-safety fix (beta.2) so `sync-work-item-from-file` (push) no longer re-writes HTML fields you didn't edit — preventing a complex table from being overwritten with its lossy Markdown rendering when you push an edit to an unrelated field.
4. A security republish of the figma package (v33.0.0, published to both `beta` and `latest`): internal example identifiers are removed from the shipped tool descriptions, and the `si-investigation` → `investigation` sticky-category rename ships with a backward-compatible input alias. meta v32.0.1 pins the clean figma.

All are drop-in. No `.mcp.json` changes are required to upgrade.

## Highlights

- **One-prompt secret warming for parallel MCP launches.** `mcp-warm-secrets` resolves every `op://` reference across every server in your `.mcp.json` into the shared encrypted cache up front, eliminating the burst of per-server 1Password prompts when many servers start at once. Opt-in via a documented shell wrapper — default behaviour and biometric users are unaffected.
- **`sync-work-item-to-file` is now read-only against ADO.** Pulling a work item previously PATCHed the item, irreversibly switched its fields to Markdown format, and bumped the revision — silently flattening client-authored HTML (notably tables) on what users experience as a read. Conversion now happens in-memory for the local file only; the ADO item is never touched.

## 🚀 New Features

- **`mcp-warm-secrets` CLI (`@mcp-consultant-tools/core`).** Reads an `.mcp.json`, resolves all `op://` references across every server in a single 1Password prompt per account into the shared encrypted cache, so concurrently-launched MCP servers start without each triggering its own prompt. Opt-in via a documented shell wrapper. An `isOpSignedIn()` guard refuses to run when 1Password is not signed in, so a failed resolve can't poison the cache.

## ✨ Enhancements / Functional Improvements

- **Figma: legacy `si-investigation` accepted as an input alias.** `get-figma-semantic` (and `mcp-figma-cli get-semantic`) normalize `si-investigation` to `investigation` in `stickyColorOverrides` values, so pre-v33 configs keep working. Output always emits `investigation`.
- **Figma: internal example identifiers removed from shipped artifacts.** The tool-description examples in the published package now use synthetic file keys. figma is republished as v33.0.0 to both `beta` and `latest`; meta v32.0.1 pins it so `meta@latest` no longer pulls the old figma tarball.
- **Azure DevOps work-item pull: HTML tables convert to Markdown pipe tables.** `turndown-plugin-gfm` is now applied during HTML→Markdown conversion, so tables in pulled work items render as proper pipe tables in the local file instead of being flattened.
- **Lossy-conversion warnings on pull.** When a pulled field contains a table that can't round-trip cleanly, `sync-work-item-to-file` returns `conversionWarnings` so the agent knows to re-read the intact ADO original via `get-work-item`.

## 🐛 Bug Fixes

- **Azure DevOps: `sync-work-item-to-file` and `sync-tasks-to-file` no longer mutate ADO on pull.** The previous code called `autoConvertFieldsToMarkdown`, which PATCHed the work item, set the field format to Markdown irreversibly, and bumped the revision. Conversion is now pure in-memory (`convertFieldsToMarkdownInMemory`), the re-fetch and revision bump are removed, and `skipAutoConvert=true` behaviour is preserved.
- **Azure DevOps: `sync-work-item-from-file` / `sync-tasks-from-file` no longer rewrite untouched HTML fields on push** (beta.2). Push compared the local Markdown against the raw ADO HTML, which never matches, so every push re-wrote HTML body fields (Description, Acceptance Criteria, Repro Steps, Task Description) even when only an unrelated field was edited — flipping them to Markdown format and overwriting complex tables with their lossy Markdown rendering. Push now compares the local Markdown against `htmlToMarkdown(adoHtml)`, so an unedited HTML field is detected as unchanged and left as the original ADO HTML; genuine edits still push as before.
- **Azure DevOps: `complete-test-run` no longer fails with HTTP 415** (beta.3). The Test Runs – Update endpoint (`PATCH _apis/test/runs/{id}`) expects a plain JSON merge body, but the client defaulted every PATCH to `Content-Type: application/json-patch+json` (correct for work-item JSON-Patch updates). ADO rejected that media type with `HTTP 415 (TF400898)`, so runs stayed stuck "In Progress" even though `create-test-run` and `add-test-results` (both POSTs) succeeded and saved results. `completeTestRun` now overrides the header to `application/json` — the same precedent already used by `updateWorkItemComment`. Affects both the `complete-test-run` MCP tool and the `mcp-ado-cli test complete-run` CLI command.
- **Azure DevOps: `complete-test-run` summary now reports correct pass/fail counts** (beta.4). The completion summary always printed `Passed: 0, Failed: 0` even when results passed — the persisted ADO data and `get-test-run-results` were always correct, only the summary was wrong. `completeTestRun` read the pass/fail aggregates straight off the run-state PATCH response, but ADO recomputes those lazily for these Basic-license automated runs so they came back `0` (only `totalTests` was populated). The counts are now aggregated from the actual per-result outcomes via a follow-up `GET _apis/test/runs/{id}/results` — the same approach `add-test-results` uses. The summary also gains an `Other: N` count (for `NotExecuted` / `NotApplicable` results) so the numbers add up. Return shape unchanged; the `mcp-ado-cli test complete-run` CLI command is fixed in lockstep.
