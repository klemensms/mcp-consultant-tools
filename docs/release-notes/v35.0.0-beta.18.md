# Release Notes: v35.0.0-beta.18

**Date:** 2026-08-20
**Branch:** `release/35.0`
**Status:** Published to beta

> Per-iteration agent-level detail. The user-facing single source of truth is [`v35.0.0.md`](v35.0.0.md).

## Overview

Two independent bodies of work, published together.

**The CLI assurance remediation is complete.** beta.17 took the first priority of a consolidated bug report covering 26 CLI defects and 3 cross-cutting issues, gathered across roughly 700 CLI invocations in two live assurance runs. This iteration ships the rest: 19 tasks across `azure-management`, `azure-defender`, `log-analytics`, `powerplatform` and `core`, plus 7 new read-only commands for resource types the CLIs could not see at all. The report's uniting finding was that roughly 22 of its first 29 defects fail towards a clean-looking result rather than towards an error, so every fix here carries a test asserting the failure case: that a truncated result is not indistinguishable from a complete one, that a filtered result is not indistinguishable from an empty one, and that a partially-authorised collection is not indistinguishable from a fully-authorised one.

**Teams can correct and withdraw what it has already sent.** Six tools take the package from 20 to 26, closing a gap raised in beta.8, beta.15 and beta.16 and deferred each time.

`core` moves onto the 35.0 train at **35.0.0-beta.1**. It was deliberately left on the 34 line at beta.17, but the fan-out contract this iteration adds is a new export that five packages import, and the already-published `core@34.1.0` cannot carry it.

## Changes Implemented

### The fan-out contract (`core`, and `azure-management` as proof)

- **`helpers/fan-out.ts`, exported from the package index:** `FanOutRecorder`, `fanOutSuffix` and the `FanOutInfo` shape. A command that collects from many resources records each failure instead of swallowing it, reports `attempted` / `succeeded` / `failed` counts with the operation names and HTTP statuses, and `outputResult` **exits 1** whenever a payload's fan-out lost an item.

  The measured behaviour it replaces: a run that hit **32 authorisation failures exited 0** and wrote a cache file describing a partial estate as a complete one. The failures were logged to stderr and dropped from the payload, so nothing downstream could tell.

- **`azure-management` converted at all 15 call sites** (43 references now), and `azure-defender` follows for its two-source assessment union. The remaining packages that fan out are unconverted and unscheduled, recorded in the plan file.

- **A CLI cache written outside a git repository now says where it went.** The path is resolved against the working directory, so a run started outside a repository silently scattered `.context/` wherever the shell happened to be.

### `azure-management`

- **`graph role-assignments` resolved no role name at all**: 752 of 752 assignments reported an unresolved role while `roleDefinitionsTruncated` was false, and every one of the 52 distinct GUIDs resolved when fetched directly. The lookup now joins on the trailing GUID rather than the whole resource id, and reports `roleDefinitionsFound` plus a `note`, so a role-definition query that returns nothing declares itself instead of looking like a plain count of unknown roles.
- **`networking event-grid-topics` reported zero while topics existed.** System topics were skipped rather than counted. `summary.total` is now what exists and `listed` is what came back, which costs one extra ARM list call per invocation and is a payload-contract change (see Upgrade Notes in the master).
- **App Service plan and Front Door payloads reported fields nobody had asked ARM for.** Two independent defects behind one symptom on App Service plans: `AppServicePlans_List` returns a subset at subscription scope unless `detailed=true` is passed, **and** `workerCount` was reading `targetWorkerCount`, the writable scaling target, rather than the read-only `numberOfWorkers`. Fixing only the request would have populated a field that was still reporting the wrong number. On Front Door, `endpoints`, `originGroups` and `routes` were gated behind an `includeDetails` flag that `listFrontDoors` hard-coded to `false` with no caller override, so the three calls were never made. `--include-details` now reaches them.
- **Four resource types were invisible.** New read-only commands: `compute list-vms` (with `--include-status` for power state), `monitoring log-alerts` (log-search alert rules, a different surface from `monitoring alerts`, whose absence overstated the alerting gap), `logic-apps list-workflows`, and `logic-apps list-api-connections`. All four mappers pass `properties` through whole and report unrecognised keys rather than naming a documentation-derived allowlist.

### `azure-defender`

- **`defender-list-assessments` missed every identity- and subscription-scoped assessment.** 39 of 39 assessments present in Resource Graph but absent from the CLI were scoped to an identity object or to the subscription itself, which the ARM list does not enumerate. The command now unions ARM with Resource Graph, deduplicating on a case-normalised id, and reports per-source counts.
- **`defender-get-attack-path` dropped the entire risk payload.** Microsoft's published attack-path field table describes only the legacy Defender CSPM names; live rows from Microsoft Security Exposure Management carry a different set, and everything off the documented list was discarded, so a `riskLevel: High` path reported no risk at all on every path of a real estate. Both shapes are now read, with `summary.riskLevelNotReported` counting paths that name no level under either spelling, because an absent field must not render as a value the API returned.
- **The assessment mapper discarded whatever Microsoft had not documented.** Unmapped `properties` keys now arrive in `properties.unmappedProperties`, aggregated into `summary.unmappedPropertyKeys` across all rows **before** the union dedupes and before `maxResults` trims.
- **Two surfaces were unreachable:** `defender-list-alerts` (security alerts) and `defender-list-plans` (Defender plan configuration, reporting a three-state `cspmEnabled` so that "plan absent from the response" cannot be read as "CSPM off").
- **A compliance failure read as a finding rather than as a missing plan.** Every `regulatoryCompliance*` failure now carries a trailing hint naming `defender-list-plans`. ARM's own code and message stay first and the call still throws.

### `log-analytics`

- **`fn stats` triple-counted every function**: 27 functions produced 61 rows at roughly three times the executions, because `FunctionName` arrives as a bare name, a `Functions.`-prefixed name and an empty string. `collapseFunctionStats` keeps the highest-counting variant and names what it dropped in `normalization.collapsed`.
- **`workspace metadata` returned the schema catalogue, not the workspace's contents.** It still returns all ~680 tables and now carries a `scope` block saying so; the new `la-list-workspace-tables` answers what the workspace actually holds, from ingestion metering, with an unconditional caveat that this is a lower bound.
- **A usage sum was labelled MB without checking the unit.** The query now groups by `Usage.QuantityUnit`, so a surprise unit shows as an extra row rather than a wrong total.
- **`query error-summary --table FunctionAppLogs` built an invalid query**, naming an Application Insights column that table does not have. The four query shapes moved into one module so the CLI and the MCP tool cannot diverge, and an unsupported `--table` now throws naming the supported set instead of silently falling through to the `FunctionAppLogs` shape.
- **A `Bad request` discarded the one field that identifies it.** The 400 branch computed ARM's error code into a local and never read it, so the thrown message carried the text and dropped the code. It now reads `Bad request (<code>): <message>`. No retry was added, and a test named `does not retry a 400` pins that.

### `powerplatform` / `powerplatform-core` / `powerplatform-customization`

- **`plugin trace-logs --exception-only` filtered out clean runs and kept nothing else**: `exceptiondetails ne null` matched 147 rows where the intended filter matched 0, because the column holds an empty string rather than null on a clean run. The filter now excludes both.
- **`plugin get` returned the raw Dataverse row where `plugin list` returned a decoded one.** The two now agree. Raw keys and `@odata.etag` are gone rather than duplicated alongside their decoded equivalents (see Upgrade Notes in the master).

### `teams`

- **Six tools, taking the package from 20 to 26:** `update-chat-message`, `delete-chat-message`, `undo-delete-chat-message`, `update-channel-message`, `delete-channel-message`, `undo-delete-channel-message`. The channel three also take a `replyId`, so a single reply inside a thread can be corrected or withdrawn. Every tool has a matching CLI command, and all six share the send path's markdown conversion, HTML sanitisation and `@[Name]` mention resolution, so a corrected message cannot render differently from the one it replaces.
- **An edit replaces the whole body.** Graph offers no partial update, so a mention present in the original and absent from the replacement is dropped.
- **Deletes are soft, and the undo ships alongside rather than later.** An agent-driven delete that cannot be reversed is a sharper edge than the problem being solved.
- **`ChannelMessage.ReadWrite` is deliberately not requested at sign-in.** The channel tools need it, but Entra returns every admin-consented scope in the `scp` claim regardless of what MSAL asks for, so a registration that has been granted it works with no code change and no fresh sign-in. Requesting it explicitly would gain nothing and would fail registrations that lack it **at sign-in**, taking all 26 tools down instead of the 3 that need it.
- **Three 403s in this area do not mean what they say**, and the error wrapper now checks all three ahead of the generic re-authenticate advice, which actively misleads on every one. `MessageIdNotInAllowedRange` is an id-range rejection wearing a permissions error. `AclCheckFailed` is Teams refusing the action after Graph accepted it, normally a tenant messaging policy forbidding users to delete their own sent messages. A missing `ChannelMessage.ReadWrite` needs an administrator, not a re-auth. The inner error lives in the Graph client's `body` property rather than `message`, so all three are matched against both.

## Testing

**1,139 tests pass, 0 fail**, across all 14 suites, after a clean `build:release` from purged `build/` and `*.tsbuildinfo`. 13 of those tests are new for the Teams work and roughly 150 for the assurance chain, every one asserting a failure case rather than a happy path. Declaration output confirmed on all eight published packages, which is the check that caught the `powerplatform@33.0.0` zero-types incident: `core` 32, `azure-management` 54, `azure-defender` 36, `log-analytics` 22, `teams` 41, `powerplatform` 32, `powerplatform-core` 51, `powerplatform-customization` 38.

**Verified live:** Teams message **editing**, end to end on both chats and channels, including a 35-hour-old channel message.

**Not verified live, and this is the larger half of the release.** Every fix in the assurance chain is unit-verified only. There are no Azure, PowerPlatform or Log Analytics credentials on the machine the work was done on, so nothing here has seen a live ARM, Dataverse or Log Analytics response. What was verified without credentials: both MCP servers per package boot over real MCP stdio with pure-JSON stdout and register the new tools with the revised schema text, every CLI renders `--help`, and each fails loudly and exits 1 with empty stdout against fake credentials rather than returning an empty success.

**Teams delete and undo are shipped but have never succeeded against a real tenant**, because the tenant they were built against forbids deletion by policy. The failure mode is proven; the success path is not.

## Known Issues

- **The whole assurance chain needs one live run per package.** 23 specific checks, each reduced to one command and the one field to read, are listed under "Live-run verification list" in `.claude/plans/cli-assurance-remediation.md`. Read the one about `logic-apps list-api-connections` **before sharing any connection listing**: the command trusts ARM's own split between secret and non-secret parameter maps, and the CLI writes the payload to disk.
- **`v35.0.0-beta.17`'s PowerPlatform paging has still never run against a live Dataverse environment.** Five commands ride on it.
- **`assessment list-assessment-metadata` still returns null for `implementationEffort` and `userImpact`** on all 1,302 definitions. Narrowed to one live comparison: both fields are optional at api-version `2025-05-04` and absent from every example, while the `2020-01-01` examples carry them. If the old version populates them and the new one does not, there is no patch that keeps everything, because `2025-05-04` is what the package needs for `Critical` severity.
- **No assessment carries `Critical` severity and none carries a `properties.risk` object.** The mapper-artefact explanation is now decided by reading `summary.unmappedPropertyKeys` on the first live run.
- **The `$top`-based completeness check survives in four `powerplatform-core` methods**, not the two beta.17 recorded: `MetadataService.getGlobalOptionSets`, `WorkflowService.getWorkflows`, `FlowService.searchWorkflows` and `FlowService.getFlowRuns`. `searchWorkflows` and `getFlowRuns` were in no earlier record, and `getFlowRuns` spells the pattern `limit + 1` rather than `maxRecords + 1`, which is how it stayed hidden. `FlowService.getFlows` was fixed in beta.17 and is not affected. Of the four, `getFlowRuns` is the most likely to bite, because a busy flow passes 5,000 runs easily.
- **The documented `ARM="npx …"` then `$ARM …` invocation idiom fails under zsh** in all six CLIs, and the files carrying it are outside this repository. Measured cost included a collection that exited 0 and wrote zero files. The working form is a shell function: `arm() { npx -y --package=@mcp-consultant-tools/azure-management@beta mcp-azure-mgmt "$@"; }`.
- **`--include-details` on `networking front-doors` will make three ARM calls for the first time on a live estate.** Read `fanOut.failures` before using that output for a WAF review: an unattached WAF policy and a refused route list look the same to a reader who skips it.
- **VM power state costs one ARM call per VM, sequentially**, with no cap and no progress output (244 calls on the estate that produced the defect). `list-api-connections` walks every resource group in the subscription, uncapped. Both are recorded with their cheaper alternatives and why those were not taken blind.
- Everything else surviving from the chain is in `docs/KNOWN_ISSUES.md` (six new confirmed defects) and in the plan file's deferred-scope section.
