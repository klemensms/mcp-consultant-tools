# Release Notes: v35.0.0-beta.5

**Date:** 2026-08-11
**Branch:** `release/35.0`
**Status:** Published to beta

> Per-iteration agent-level detail. The user-facing single source of truth is [`v35.0.0.md`](v35.0.0.md).

## Overview

Two correctness fixes, both of which returned a plausible answer rather than an error — which is what
made them expensive to find. One is a **silent data-truncation defect** in `powerplatform-data`'s
`query-records`; the other is an MCP client-facing HTTP status defect on three HTTP servers. No new
tools, no new environment variables, no changed return shapes. Drop-in upgrade.

This iteration also corrects a dependency pin: `powerplatform-data` was pinned to
`powerplatform-core@34.0.0`, so no v35 `powerplatform-core` change had ever reached the published
package. Without that correction the paging fix below would not have shipped.

## Changes Implemented

- **`powerplatform-data` / `powerplatform-core`: `query-records` no longer truncates silently.**
  `DataService.queryRecords` requested `$top = maxRecords + 1` and inferred `hasMore` from
  `value.length > maxRecords`. Dataverse caps every response at 5,000 rows regardless of what `$top`
  asks for, so once `maxRecords` reached 5,000 the sentinel row could never come back: the server
  returned exactly 5,000, `5000 > 5000` evaluated false, and the tool reported `hasMore: false` while
  discarding every row past the cap. A window holding 8,323 rows returned 5,000 of them and told the
  caller nothing was missing.

  `$top` also cannot detect the truncation: it is client-driven paging, so Dataverse returns no
  `@odata.nextLink` alongside it, and `$top` is ignored outright when a page-size preference is
  present. The fix switches to documented server-driven paging — `Prefer: odata.maxpagesize` plus
  following `@odata.nextLink` until `maxRecords` is satisfied or the result set is exhausted.
  `hasMore` is now derived from the continuation token and never from a row count.

  Consequence worth knowing: `maxRecords` above 5,000 is now genuinely served rather than silently
  capped, at one extra API call per 5,000 rows. The tool description and technical doc that
  advertised `max: 5000` are updated accordingly.

- **`powerplatform-data` dependency pin corrected.** `@mcp-consultant-tools/powerplatform-core`
  moves from `34.0.0` to `35.0.0-beta.3`. The published `powerplatform-data@35.0.0-beta.1` shipped
  the v34 core library, so nothing added to `powerplatform-core` during v35 reached it.

- **`powerplatform`, `powerplatform-data`, `sharepoint`: OAuth discovery paths return 404, not 401.**
  These HTTP servers authenticate with a static API key (plus Entra JWT for `powerplatform-data`) and
  expose no OAuth routes, but their global auth middleware gated every path — so
  `/.well-known/oauth-protected-resource`, `/.well-known/oauth-authorization-server` and `/register`
  returned 401. A 401 on those paths tells an MCP client "OAuth is supported, you are unauthorized",
  so the client starts an authorization flow that can never complete and reports "authentication
  failed" — while the API key works fine and `initialize` / `tools/list` keep returning 200. Latent
  until a client probes them. A guard is now registered before the auth middleware (order matters;
  after it, the 401 still wins).

## Testing

- **`DataService.queryRecords`: 5 new unit tests** against a stub reproducing both real Dataverse
  behaviours (hard 5,000-row page cap; `$top` ignored when `odata.maxpagesize` is present). Three of
  the five fail against the previous implementation with exactly the reported symptom — 5,000 rows
  returned, `hasMore: false`. Covers the 5,000 boundary, paging past it, single-page results,
  sub-cap truncation, and the emitted request shape (no `$top`, annotations preserved on every page).
- **Full monorepo suite green** — 13 test-bearing packages, 0 failures.
- **Runtime smoke test** on the built `powerplatform-data` server: the server boots, `query-records`
  is registered, the new cross-module import resolves, and the emitted request carries no `$top`.
- **OAuth discovery fix** was verified on all three servers when committed: the four discovery paths
  return 404, `POST /mcp` without a key still 401s, and `tools/list` with a valid key returns 200.

**Not verified:** no Dataverse credentials were available on the build machine, so `query-records`
has not been executed against a live environment holding more than 5,000 rows in a single filterable
window. The paging logic is covered by unit tests against an emulated server, not by a live pull.
This is the one check to run before promoting to `latest`:

1. `count-records` on a table with filter F, where the result N is greater than 5,000.
2. `query-records` with the same filter and `maxRecords` ≥ N must return either N rows with
   `hasMore: false`, or fewer rows with `hasMore: true`. Never fewer than N rows with
   `hasMore: false`.

## Known Issues

- **The same `$top = maxRecords + 1` sentinel pattern remains in three other services** —
  `MetadataService.getGlobalOptionSets`, `WorkflowService.getWorkflows` and `FlowService.getFlows`.
  Each is the same latent false-completeness defect and will misreport `hasMore` wherever its result
  set can reach the 5,000-row page cap. Not fixed in this iteration; recorded in
  [`docs/KNOWN_ISSUES.md`](../KNOWN_ISSUES.md). `FlowService.getFlowInventory` is unaffected — it
  already pages via `@odata.nextLink`.
- **`powerplatform-customization` remains pinned to `powerplatform-core@34.0.0`.** It is otherwise
  unchanged this wave, so it is not re-bumped; it does not expose `query-records` and is unaffected
  by the paging defect.
