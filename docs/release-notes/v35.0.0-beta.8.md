# Release Notes: v35.0.0-beta.8

**Date:** 2026-08-13
**Branch:** `release/35.0`
**Status:** Published to beta

> Per-iteration agent-level detail. The user-facing single source of truth is [`v35.0.0.md`](v35.0.0.md).

## Overview

A single-defect iteration. Live testing of beta.7 against a real tenant passed on everything except the two reaction tools, which **failed on every call** — one wrong value in the request body, in two places, asserted as correct by four unit tests. `teams` and `meta` only; no new tools, no scope changes, no configuration changes.

## Changes Implemented

### Bug fix — reactions failed on every call (regression against beta.7's new tools)

`react-to-channel-message` and `react-to-chat-message` posted the friendly reaction name as `reactionType`. Graph rejects it with HTTP 400 `BadRequest`:

```
Unicode 'like' in the payload is not supported
```

Identical on `v1.0` and `beta`, on `setReaction` and `unsetReaction`, on parent channel messages, thread replies and chat messages — every reaction type, every target. `setReaction`/`unsetReaction` want the **Unicode emoji character** in `reactionType`, not the name the Graph reference documents.

`REACTION_EMOJI` in `services/message-service.ts` now maps name → emoji immediately before the `.post()`, at both call sites:

| Friendly name | Wire value | `displayName` Graph stores |
|---------------|-----------|----------------------------|
| `like` | 👍 | Like |
| `angry` | 😠 | Angry |
| `sad` | 😢 | Crying |
| `laugh` | 😆 | Laugh |
| `heart` | ❤️ (U+2764 U+FE0F) | Heart |
| `surprised` | 😮 | Surprised |

Confirmed against a live tenant, not inferred. `❤️` is two code points and the variation selector is part of the confirmed value.

**The public surface is unchanged.** The tool schema, the `ReactionType` union and the CLI `--type` flag all keep the six friendly names — no caller types an emoji, and no existing invocation needs editing. Only the wire value changed.

**Everything else in both tools was already correct**, confirmed by probing the raw endpoints directly: path construction, thread-reply routing (an emoji posted to `.../messages/{parent}/replies/{reply}/setReaction` lands on the reply and leaves the parent's `reactions[]` empty), the add/remove switch, scope handling and error wrapping. Nothing else was touched.

Graph also accepts 😡, 😂 and 😲 as *distinct* reactions, so the enum could widen later. Not done here.

## Testing

**Automated.** 31 tests green (`npm run test --workspace=packages/teams`), up from 30.

The four existing reaction-body assertions in `message-service.test.ts` expected `{ reactionType: 'heart' }`, `'like'`, `'laugh'` and `'surprised'` — the code's own wrong assumption — and now expect the emoji. **Fixing the source without fixing these would have re-locked the defect behind a green suite.**

One test is new: the posted `reactionType` must not match `/^[a-z]+$/`, checked across all six types. It asserts an *absence* — that a friendly name never reaches the wire — which is the shape of guard that catches this class of defect, matching the `$top`-absence test added to `teams-service.test.ts` in beta.7.

**Inversion-checked.** The four corrected assertions plus the new guard were run against the unmapped source first: 5 failed, 26 passed. With the mapping in place, 31 pass.

**Runtime.** Clean build; the rebuilt server registers **16 tools** over real MCP stdio, and `react-to-channel-message` still advertises the six friendly names in its schema enum with `like` as the default.

~~**Not verified — needs the work machine.**~~ **Now verified — see below.** The production client ID is not permitted on this machine, so no reaction had been applied to a real message from this build at the time of publishing. The emoji values themselves *were* live-confirmed — they came from direct probes against a real tenant during beta.7 testing — but the fixed code path had not been run.

**Live-test result (2026-08-13, on the published `35.0.0-beta.4` artifact).** **All six reaction types passed a full add → read-back → remove → read-back cycle**, three through the MCP tools and three through the CLI, spread across all three surfaces (channel parent, thread reply, chat message). Every result was confirmed by reading `reactions[]` back from Graph rather than trusting the `204`, and the stored `displayName` matched the mapping table on every row — including `sad` → **Crying**. `❤️` round-tripped with its variation selector intact. **Reply isolation confirmed:** with a reaction on the reply, the parent's `reactions[]` stayed at `count: 0` for the whole cycle. Every target read back empty at the end, so nothing was left decorating a message.

~~**`auth login` is still entirely unexercised**~~ — **now verified.** A full `auth logout` → `auth login` → completed device code was run with a person at the keyboard. The encrypted token cache was **rewritten**, confirming a genuinely new sign-in rather than a fall-back to the old cache, and **the new token carries the full eight-scope set**: `list-teams` (`Team.ReadBasic.All`), a private-channel read (`ChannelMessage.Read.All`) and `list-chats` (`Chat.ReadWrite`) all succeeded on it, where a narrow-scope token would have returned 403 — the exact failure beta.6 was written to prevent. A reaction cycle run after the re-login also passed, so the write path survives re-authentication.

**Still not verified:** the exit code of `auth login` on a *completed* sign-in was not captured, and the **abandoned**-code path was deliberately not tested — proving it needs someone to sit out the device code's full lifetime, which suits a test that fakes the clock better than a live run. `mark-chat-read` and `send-adaptive-card` also remain unexercised: the first would clear real unread state in a live chat.

**Standing caveat on all live results.** Everything above is Graph-confirmed, not confirmed in the Teams client — no agent on the test machine can see the Teams UI. If Graph's stored state and the rendered client ever disagreed, this testing would not catch it.

## Lesson

Both defects found on this release line are the same failure: **a test asserting the code's own wrong assumption.** beta.7 fixed `$top` on `/me/joinedTeams`, where the suite asserted the query the code built — which was the query Graph rejected. beta.7 then shipped reactions with four tests asserting the body the code posted — which was the body Graph rejected. Inversion-checking caught neither, because inversion proves a test notices a change, not that the asserted value is the one the server wants.

A stub can only prove the code agrees with itself. Recorded in `packages/teams/CLAUDE.md`: where a change touches the **shape or value** of a Graph request, get one live confirmation before release, or state plainly in the release notes that the payload is unverified.

## Known Issues

- **Mentions render as one `@` per word — now diagnosed, not yet fixed.** The raw `body.content` was captured live and settles it: **Graph emits one `<at>` element per word.** `htmlToText` is behaving correctly given its input.

  ```html
  <p>Thanks for these <at id="0">Jane</at>&nbsp;<at id="1">Doe</at>&nbsp;— great example!</p>
  ```

  The accompanying `mentions[]` carries **two entries** (`mentionText: "Jane"`, `mentionText: "Doe"`) resolving to an **identical** `mentioned.user.id`. Confirmed on both a user mention and a channel-tag mention, the latter splitting one `displayName` across two entries that share a `conversation.id`, and reproduced across separate messages — so it is systematic, not a one-off.

  The fix is to coalesce adjacent `<at>` elements **whose resolved entity id is identical**, joining their text with a single space and emitting one `@`. The observed separator is `&nbsp;`. Key it on the entity id rather than on adjacency alone: two *different* single-word mentions sitting side by side was not observed, and a naive "merge all adjacent `<at>`" rule would wrongly fuse them.
- **`list-chats` displays a different field from the one it sorts by.** The Graph request correctly orders by `lastMessagePreview/createdDateTime desc`, but the rendered "Last activity" column shows `lastUpdatedDateTime` — a field tracking changes to the chat itself (topic, membership), not messages in it. The ordering is right; the column is not, and the two disagree badly enough to mislead: a chat whose last message arrived hours ago can display a timestamp six weeks old, reading as a colleague who has not been in touch since. Fix is to display the field the list is already sorted by.
- **`<emoji>` elements are dropped from rendered message text.** Teams encodes emoji as `<emoji id="smile" alt="🙂" title="Smile"></emoji>`; `htmlToText` has no branch for the element, so the character vanishes on every read. The character sits in the `alt` attribute, so substituting `alt` fixes it. Low severity, but it occasionally changes the tone of what a colleague wrote.
- **The CLI writes its response cache into the current working directory.** A write command run without `--no-cache` creates `.context/.mcp-teams-cache/<command>.json` wherever it was invoked — which on a test machine meant a new `.context/` inside a cloud-synced folder. Contents were innocuous, but a tool that leaves files where it was invoked is surprising, and this is a repo-wide CLI convention rather than a `teams` defect. Worth deciding whether a *write* command needs a cache file at all.
- **MCP and CLI express "remove" differently.** The MCP tools take `action: "remove"`; the CLI takes a `--remove` flag and rejects `--action remove` outright. Both are reasonable in isolation; only worth changing if the two surfaces should read the same.
- **No tool can delete a message the agent sent.** Test messages posted during verification cannot be cleaned up by the package that created them. Raised as a feature idea (`delete-own-message`); not scoped.
- **`list-teams` is still broken on the `latest` tag (`33.0.0`)** for every device-code user — carried from beta.7. Fixed on the beta channel only; a production patch remains a separate decision.
- **Compiled tests ship inside the published tarball.** `files: ["build", ...]` includes the compiled `build/services/__tests__/` output. Harmless, mildly untidy — and it is how this defect was diagnosed from the published artifact alone. Left as is.
- 19 sibling CLIs still report hardcoded stale versions — carried from beta.7, still deferred to its own sweep.
