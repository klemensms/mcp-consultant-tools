# Release Notes: v35.0.0-beta.17

**Date:** 2026-08-16
**Branch:** `release/35.0`
**Status:** Published to beta

> Per-iteration agent-level detail. The user-facing single source of truth is [`v35.0.0.md`](v35.0.0.md).

## Overview

Acts on a consolidated bug report covering 26 CLI defects and 3 cross-cutting issues, gathered across roughly 700 CLI invocations in two live assurance runs. This iteration takes the report's Priority 1 only: one truncation contract applied to the `powerplatform` list commands, closing five of the measured defects and the cross-cutting issue behind them.

The report's headline finding is that roughly 22 of its first 29 defects fail towards a clean-looking result rather than towards an error. A truncated result that is byte-for-byte indistinguishable from a complete one is the worst of those, because the reader has no signal that anything is missing. That is the class this iteration closes for these commands.

## Changes Implemented

### The contract

- **`@mcp-consultant-tools/core` gains `helpers/truncation.ts`**, exported from the package index: the `TruncationInfo` shape, `buildTruncation`, `truncationSuffix`, and the `UNCAPPED` and `PAGINATION_SAFETY_CEILING` constants. Two rules are enforced by construction. `hasMore` is never inferred from the returned row count, and `totalAvailable` is `null` whenever the fetch stopped short, so a total is reported only when one was actually counted.

  ```typescript
  {
    returnedCount: number,          // rows in this payload, after every filter
    requestedMax: number | null,    // the cap asked for; null when uncapped
    hasMore: boolean,               // rows matching the same filters remained at the source
    totalAvailable: number | null,  // exact source total; null whenever hasMore is true
    truncationReason: 'requestedMax' | 'safetyCeiling' | null
  }
  ```

- **`powerplatform-core` gains `services/paginate.ts`**, one `paginateDataverse` that every changed list service calls. It pages via `Prefer: odata.maxpagesize` plus `@odata.nextLink` rather than `$top`. Dataverse ignores `$top` when a page-size preference is present and returns no continuation token for a `$top`-capped query, so a `$top` result physically cannot distinguish capped from exhausted. Client-side filters run inside the paging loop via a `keep` callback, so a cap counts rows returned rather than rows fetched. An uncapped fetch stops at a 50,000-row safety ceiling and reports that as `truncationReason: 'safetyCeiling'`. A `maxRecords` that is not a non-negative integer throws rather than reaching the wire as `odata.maxpagesize=NaN`.

### The five defects

- **`flow list` reported `hasMore: false` with more flows remaining** (`FlowService.getFlows`). It requested `ceil(maxRecords * 1.5) + 1` rows, applied the SYSTEM and Copilot-for-Sales exclusions to that single page, then computed `hasMore` from what survived. Filtering the page below the cap therefore read as the source being exhausted: 22 returned, `hasMore: false`, 136 matching. The exclusions now run inside the paging loop and `hasMore` comes from the continuation token.
- **`plugin steps` truncated at 500 with no truncation field** (`PluginService.getAllPluginSteps`). Payload was `{ totalCount: 500, steps: [...] }` and nothing else against a true total of 2,637.
- **`security roles` truncated at 100 with no truncation field** (`SecurityRoleService.getSecurityRoles`). Returned 96 of 542, and the `summary` block described only that page, so it read as a complete census. The system-role exclusion now runs inside the paging loop and is counted there.
- **`security connection-refs` truncated at 100 with no truncation field** (`ConnectionReferenceService.getConnectionReferences`). Returned exactly 100 of 169, so `summary.byConnector` under-counted every connector. The `hasConnection` filter now runs inside the paging loop.
- **`plugin list` dropped hidden assemblies and declared no exclusion** (`PluginService.getPluginAssemblies`). Now returns `ootbExcluded`, matching what `integration endpoints` and `integration env-vars` already did in the same package.

### Defaults

- `maxRecords` defaults to `UNCAPPED` (`0`) on all five service methods; the CLI `-m, --max` default moves from `25` / `100` / `500` to `0`, with help text reading `(0 = all, the default)`.
- CLI summary lines carry `truncationSuffix`, so a capped run prints `[TRUNCATED at N of an unknown total. Re-run uncapped (-m 0, or omit maxRecords) for the complete set]` rather than a bare count.
- MCP tool text responses carry the same suffix, and the `maxRecords` schema descriptions state the uncapped default and what `truncation.hasMore` means.

### Surface changes

- `FlowListResult` gains `truncation`; `totalCount`, `hasMore` and `requestedMax` keep their names, positions and meanings.
- `PluginStepInventoryResult` gains `truncation`. New exported `PluginAssembliesResult` replaces the inline `{ totalCount, assemblies }` return type and adds `truncation` and `ootbExcluded`.
- `SecurityRolesResult` and `ConnectionReferencesResult` gain `truncation`.
- Facade signatures updated in `powerplatform` and `powerplatform-customization`.

### Build hygiene (incidental, but it blocked the build)

- Four packages pinned an internal dependency to an older version than the workspace carried, so npm installed a stale copy from the registry under their own `node_modules` instead of symlinking the workspace. They compiled against published code and could not see anything added locally, which surfaced as an imported constant resolving to `undefined` at test time. `npm ls` reports these as `invalid`; `npm install` reports nothing and the build passes.
- Eleven packages move their `core` pin from `34.0.0` to `34.1.0` so they keep resolving the workspace copy. The fourteen still pinned to `core@33.0.0` carry the same latent hazard and are deliberately untouched.

## Testing

**37 new tests, every one asserting the failure case.** `powerplatform-core` 30 → 73, `core` 109 → 118. Full clean build via `npm run build:release`, all 14 test-bearing suites green.

New files: `core/src/helpers/__tests__/truncation.test.ts`, and in `powerplatform-core/src/services/__tests__/`: `paginate.test.ts`, `FlowService.getFlows.test.ts`, `SecurityRoleService.getSecurityRoles.test.ts`, `ConnectionReferenceService.test.ts`, `PluginService.getPluginAssemblies.test.ts`. `PluginService.getAllPluginSteps.test.ts` updated, since two of its assertions pinned the `$top` mechanism this iteration replaces.

The assertions that matter:

- A truncated result and a complete one **at the same row count** are not equal, on every changed command.
- A short page with a continuation token still outstanding is not reported as complete.
- The `flow list` shape specifically: 136 source rows, every third dropped client-side, a cap of 25, asserting `hasMore` is `true`. This is the exact shape that produced the wrong answer and no prior test covered it.
- A cap counts rows **returned**, not rows fetched, so client-side exclusions cannot silently shrink a capped page.
- A filter matching nothing against an exhausted source reports `totalAvailable: 0` rather than `null`, so "none" stays distinguishable from "none so far".
- The safety ceiling reports truncation rather than a complete set.
- The page size reaches the wire via `Prefer`, and never as `$top`.

**Runtime checks.** The server starts over real MCP stdio with pure-JSON stdout (no protocol corruption) and all five affected tools registered with the revised schema text. The built CLI reports `-m, --max` defaulting to `0` on all five commands. Declaration output confirmed on all six published packages: 31 / 51 / 32 / 38 / 17 / 3 `.d.ts` files.

**Not tested: every Dataverse call in this wave.** No PowerPlatform credentials on the build machine.

## Known Issues

- **The paging mechanism has not run against live Dataverse.** The switch from `$top` to `Prefer: odata.maxpagesize` is taken from `DataService.queryRecords`, which has shipped since beta.5 and documents the reasoning, but the changed code path itself has not executed. Check first, against an environment large enough to page: that `mcp-pp-cli plugin steps` returns a count matching the source table rather than 500, and that `mcp-pp-cli plugin steps -m 100` prints the `TRUNCATED` suffix and carries `truncation.hasMore: true`.
- **Uncapped by default means bigger MCP payloads.** On the CLI the full JSON goes to a cache file and only a summary line reaches the terminal, so the change costs nothing there. On the MCP path the full payload reaches the agent's context, and `get-all-plugin-steps` against the environment behind the bug report is 2,637 steps rather than 500. The PowerPlatform package does not use the `context-safe-response` wrapper, so nothing truncates it downstream. Worth watching during testing; passing `maxRecords` explicitly is now safe, because a cap announces itself.
- **Dataverse occasionally offers a continuation token whose next page is empty**, so `hasMore` can read `true` where nothing further existed. Over-warning is the deliberate direction; under-warning is the defect class this iteration closes.
- **The integration audit report still caps plugin assemblies at 100 and discards the truncation block.** `IntegrationAuditService.generateAuditReport` was left alone because fixing it changes that report's own output contract.
- **Two `powerplatform-core` services still carry the `$top = maxRecords + 1` completeness check**: `MetadataService.getGlobalOptionSets` and `WorkflowService.getWorkflows`. `FlowService.getFlows` was the third and is fixed here.

## Not in this iteration

The bug report's remaining priorities, in its own order:

- **D5** - `plugin trace-logs --exception-only` is a no-op, returning the same 147 records as the unfiltered call with `parsed.hasException` false on all of them. Root cause confirmed while in the file: the filter builds `exceptiondetails ne null`, which matches empty strings. A one-line change plus a test.
- **X2** - no CLI surfaces an aggregate failure count, so a partially-authorised collection exits 0 and writes a cache file as though it were complete.
- **D8, D9, D21** - the three defects that each return a confident, plausible, wrong number.
- **X1** - the documented `ARM="npx ..."` invocation idiom fails under zsh, which is every documented command on macOS.
