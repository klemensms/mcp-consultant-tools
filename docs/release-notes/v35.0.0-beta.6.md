## Overview

Extends `packages/teams` so an agent can read and act on Teams rather than only announcing into it. Three defects addressed in dependency order — the scope widening had to land first, because everything downstream depends on the token carrying the right scopes.

Scope boundary observed throughout: the app registration has tenant-wide admin consent on exactly eight delegated scopes and holds no client secret or certificate. Nothing here needs a ninth scope, and two capabilities were dropped rather than implemented because they would have.

## Changes Implemented

### 1. Scope request widened (`services/teams-service.ts`)

- The device-code flow requested five scopes; `ChannelMessage.Read.All` and `Chat.ReadWrite` were consented but never asked for, and `offline_access` was consented and unused. All eight are now requested via a single `DEVICE_CODE_SCOPES` constant.
- Confirmed from `@azure/msal-common` source rather than assumed: `OIDC_DEFAULT_SCOPES` contains `offline_access`, and `ScopeSet.createSearchScopes()` strips OIDC scopes before cache lookups — so listing it explicitly cannot cause an `acquireTokenSilent` cache miss. This was worth checking; the failure it rules out is a permanent silent-refresh miss, invisible until an hour into a live session.

### 2. MSAL token cache + silent refresh (`auth/token-cache.ts`, new)

- New `TokenCache` implements an MSAL `ICachePlugin`: `beforeCacheAccess` decrypts and deserializes, `afterCacheAccess` serializes and encrypts when `cacheHasChanged`. AES-256-GCM (`IV[16] + tag[16] + ciphertext`) under `scryptSync(hostname + username, 'mcp-teams-auth', 32)`, written at mode 0600 in a 0700 directory, at `~/.mcp-consultant-tools/teams-token-cache-{clientId}.enc`.
- `getAccessToken()` order is now: in-memory token → `getAllAccounts()` + `acquireTokenSilent()` → pending interactive auth → throw. `InteractionRequiredAuthError` returns null and falls through to device code; any other error propagates rather than being flattened into a misleading "not authenticated".
- `getAuthStatus()` and `startAuthentication()` both attempt a silent refresh, so an expired access token backed by a live refresh token reports/stays `authenticated` instead of prompting a fresh sign-in. Both became async; `requireAuth()` followed. Four call sites updated (2 tools, 2 CLI commands).
- `logout()` is now async and removes every account from MSAL's in-memory cache in addition to deleting the encrypted file — previously a `logout` then `auth-status` in the same process could resurrect the session via silent refresh.
- Follows the `powerplatform-core/src/auth/token-cache.ts` pattern. Deliberately **not** shared: `powerplatform-core` is a PowerPlatform-specific internal library (wrong dependency direction), and `@mcp-consultant-tools/core` has no `@azure/msal-node` dependency — adding one there would pull MSAL into every package in the monorepo.

**Legacy token handling.** The pre-beta.6 plaintext `~/.mcp-consultant-tools/teams-auth.json` (bare access token, five scopes, no refresh token) is deleted on construction rather than migrated. A silently-reused narrow token 403s every read tool with no visible cause, which is the exact state this iteration must not leave behind. `logout()` removes it too.

### 3. Seven new tools, with CLI parity

New `MessageService` (`services/message-service.ts`) takes `TeamsService` in its constructor and calls `teams.getGraphClient()`, so auth and the token cache are owned in one place. `TeamsService` exposes `getGraphClient()`, `getTeamId()`, `getChannelId()`, `getMe()` and `getTenantId()` for it. The split keeps both files near the repo's <500-line target instead of pushing `teams-service.ts` (753 lines before this work) toward the 1,000-line hard limit.

| Tool | Graph endpoint | Delegated permission |
|------|----------------|----------------------|
| `get-channel-messages` | `GET /teams/{t}/channels/{c}/messages` | `ChannelMessage.Read.All` |
| `get-message-replies` | `GET .../messages/{m}/replies` | `ChannelMessage.Read.All` |
| `reply-to-message` | `POST .../messages/{m}/replies` | `ChannelMessage.Send` |
| `list-chats` | `GET /me/chats` | `Chat.ReadBasic` (have `Chat.ReadWrite`) |
| `get-chat-messages` | `GET /chats/{c}/messages` | `Chat.Read` (have `Chat.ReadWrite`) |
| `send-chat-message` | `POST /chats/{c}/messages` | `ChatMessage.Send` (have `Chat.ReadWrite`) |
| `mark-chat-read` | `POST /chats/{c}/markChatReadForUser` | `Chat.ReadWrite` |

Output-volume controls: reads default to 20 messages, clamp to Graph's max of 50, expose `top` + `since`/`until`, and truncate each rendered body at 1,500 characters. `get-channel-messages` does not `$expand=replies` (which would pull up to 200 replies per message), keeping a wide skim cheap.

Rendering (`tools/format-messages.ts`): author display name, local timestamp, plain-text body, message ID, plus flags for importance / message type / deleted / reply count. The ID is always shown because it is the required input to `reply-to-message` and `get-message-replies`.

`mark-chat-read` needs the caller's own AAD id in a `teamworkUserIdentity` body, so `TeamsService.getMe()` (`GET /me`, cached per process) was added — this is why `User.Read` is a required scope rather than incidental.

**Date-range asymmetry, forced by Graph rather than chosen:** chat messages honour `$filter` only when `$orderby` names the same property, so ranges use `lastModifiedDateTime` (the one property accepting both `gt` and `lt`). Channel messages support neither `$filter` nor `$orderby`, so the range is applied client-side over the fetched page — documented in the tool description, since a narrow-looking range means `top` needs widening.

### 4. Content conversion consolidated (`message-content.ts`, new)

- `markdownToHtml()` was a private function duplicated in `tools/send-message.ts` and `cli/commands/message-commands.ts`. Extracted; both now import it, and every outbound message across all send/reply paths routes through the same sanitizer. `sanitizeHtml()` added for caller-supplied HTML.
- `htmlToText()` added for the inbound direction: flattens Teams' nested-div bodies, renders `<at>` mentions as `@Name`, replaces images/attachments/system events with placeholders (their content is a Graph `hostedContents` URL, useless to a reader), and normalizes `&nbsp;` and whitespace.

### 5. Housekeeping

- `index.ts` had its own duplicate `createServiceContext()`; consolidated onto `context-factory.ts`, whose error text now lists all eight scopes.
- `README.md` teams row: 7 → 14 tools. Package `CLAUDE.md`, `docs/documentation/TEAMS.md` and `docs/technical/TEAMS_TECHNICAL.md` updated for the new scopes, cache location, service split, tool reference, and the deliberately-unsupported list.
- The device-code config examples in the user doc previously showed a `TEAMS_CLIENT_SECRET` value, which would lead someone to add a standing credential to a registration whose whole security case is not having one. Corrected to empty with an explanatory note.
- `vitest` wired into the package (`vitest.config.ts`, `test` script) matching the `azure-devops` setup.

## Testing

### Verified locally

- **Clean build** green across the monorepo; no new `any` widening. Only pre-existing unused-symbol warnings remain (`AuthStatus` in `teams-service.ts`, unused before this work).
- **14 tools register** over real MCP stdio with the expected parameter sets. The MCP client connects successfully, which also confirms nothing writes to stdout to corrupt the protocol.
- **CLI parity** verified programmatically — all 7 new tools have matching `mcp-teams-cli` commands.
- **`message-service.test.ts` — 18 tests.** Stubs the fluent Graph chain (`api().top().orderby().filter().expand().get()/post()`) and asserts the exact path and query parameters that would go on the wire, against **real response payloads copied from the Graph v1.0 reference** for each endpoint. Covers: default/clamped/invalid `top`; the client-side vs server-side date-filter split; `$filter`+`$orderby` pairing; `from: null` system messages; deleted messages; mention rendering; markdown→sanitized-HTML on both send paths; `format: "text"` passthrough; the `markChatReadForUser` identity body; and the 403 stale-scope hint.
- **Inversion-checked.** Eight faults were induced in the service — four endpoint-path typos (`markChatReadForUser`, chat messages collection, `/replies`, `/me/chats`), the dropped `$orderby` pairing, a raised `top` clamp, and skipped markdown sanitisation — and each failed the suite before the source was restored. The first probe attempt was itself flawed (`String.replace` hit a doc comment rather than the URL) and was retargeted; without this step the suite would have looked like it covered path correctness when it did not.
- **Content conversion — 18 cases.** Mentions, plain-text passthrough, nested divs, hosted images, system events, attachment cards, `&nbsp;`, lists, `<br>`, empty bodies, truncation, and XSS: `<script>`, `onerror` and `<img>` all stripped.
- **Auth plumbing** exercised with placeholder credentials: `auth-status` → `logout` → `auth-status` all succeed and correctly report `not_authenticated`, confirming the new cache path and the async logout do not throw on a cold cache.
- **Permission mappings** for all nine Graph operations verified against the current v1.0 permission tables, not assumed.

### NOT verified — required before promoting to `latest`

No Teams credentials were available on the build machine (the production client ID cannot be used there), so **nothing in this iteration has been exercised against live Teams.** Permission and response-shape errors are the expected failure classes here and only surface on a live call.

Run this sequence on a machine with the real `TEAMS_CLIENT_ID` / `TEAMS_TENANT_ID`, after granting admin consent for all eight scopes:

```bash

#    If either succeeds, the corresponding tool is worth adding.
#    a) Channel messages delta — expected 404/400, no delegated endpoint documented:
#    b) Search over chat messages — expected 403, needs Chat.Read not Chat.ReadWrite:
#    Use Graph Explorer or curl with a token from the cache; there is no CLI command
#    for these, deliberately.
```

Report back on step 4 either way — the answers decide whether `search-messages` and a delta tool are buildable within the eight-scope boundary, and `search-messages` would be worth more than several of the tools shipped here.

## Known Issues

- **Nothing in this iteration is live-verified** (see above). Treat beta.6 as unproven against real Teams until step 1–3 above pass.
- `teams` remains pinned to `core@33.0.0` while `meta` pins `34.0.0`. Pre-existing, unrelated to this change, and nothing here requires a newer `core` — noted only because npm will resolve a nested `core` for the teams subtree.
- `teams-service.ts` is 790 lines against the repo's <500-line target (it was 753 before this work, already over). The new code went into a separate `MessageService` rather than extending it further; splitting the auth half out remains available if it grows again.
- `AuthStatus` is imported but unused in `teams-service.ts` — pre-existing dead code, left in place rather than widening this diff.
