**Date:** 2026-08-13
**Branch:** `release/35.0`
**Status:** Local testing — not yet published

> Per-iteration agent-level detail. The user-facing single source of truth is [`v35.0.0.md`](v35.0.0.md).

> **This iteration is still open.** Further audit findings are expected before publish and will be folded in here. The master file is updated, and the Teams announcement sent, only at publish time.

## Overview

**Closes the gap beta.12 left in the CLI write-cache sweep.** Beta.12 marked 155 write commands so they write no cache file and create no `.context/` directory in the caller's working directory. It classified them with a verb-prefix regex, and the regex missed a batch. A static audit of the published artifacts found 21 write commands still caching.

They are marked now, and a guard test enforces the rule mechanically so the class cannot recur.

No new tools, no configuration changes, no changes to how any command is called.

## Changes Implemented

### Bug fix — 21 write commands were still writing a cache file

The commands, by how each was proven to be a write.

**14 whose own `.description()` names an `ENABLE_*_WRITE` flag:**

| Package | Command |
|---|---|
| `1password` | `item batch-create` |
| `azure-devops` | `sync push`, `sync push-tasks`, `wiki str-replace`, `pr vote` |
| `azure-storage` | `blob copy`, `file copy`, `queue receive`, `table insert`, `table upsert`, `table batch` |
| `fabric` | `capacity unassign`, `domain unassign-workspaces` |
| `sharepoint` | `copy` |

**3 whose description names an `ENABLE_*_DELETE` flag:**

| Package | Command |
|---|---|
| `1password` | `item archive`, `item batch-delete` |
| `powerplatform-data` | `disassociate` |

**4 that mutate without naming a flag in their text**, gated in the service context instead (`ctx.checkInsertEnabled()` and friends), so no rule could prove them and they were marked by hand:

| Package | Command | Why it is a write |
|---|---|---|
| `azure-devops-admin` | `pipeline queue` | Queues a pipeline run — starts a build |
| `azure-sql` | `crud insert` | Executes an INSERT |
| `azure-sql` | `view drop` | Drops a view |
| `azure-sql` | `sproc drop` | Drops a stored procedure |

**Why the first sweep missed them.** It matched command *names* against a verb-prefix regex, which is guessing intent from a label. The rule used here reads the repo's own documentation instead:

> A command whose own `.description()` tells the user to set an `ENABLE_*_WRITE=true` / `ENABLE_*_DELETE=true` flag is, by that sentence, a write.

That needs no judgement, and it gets right the one case verb-matching must get wrong: **`azure-storage queue receive` reads like a read**, but receiving a message hides it and changes its visibility — which is exactly why it sits behind the write flag to begin with.

### Deliberately left caching

- **`rest-api batch`** matches a naive scan and keeps its cache. It executes a list of arbitrary REST requests and the cached payload is the actual response bodies — the thing most worth grepping. Its sibling `request` is unmarked for the same reason, even though `request` can POST. The test is *"is the payload worth grepping"*, not *"does it mutate"*; for these two the response is the deliverable.
- **`github-enterprise` (12 commands) and `powerplatform-customization`** name write flags in their descriptions but have bespoke CLI output helpers that `console.log` and never cache anything. There is nothing to suppress.

### Test — guard against the whole class

`packages/meta/src/__tests__/cli-write-cache.test.ts` scans every CLI command in the monorepo and fails on any command whose own description documents it as a write while it still caches, naming the offender as `file:line (command)`. It lives in `meta` for the same reason as `entrypoint-versions.test.ts` — meta aggregates the whole suite.

Three details matter in how it is written:

1. **Keyed on the command's own `.description()` string, not the whole command block.** Testing the block produces false positives — `azure-devops diff` and `azure-management logs` were both flagged during the audit because some *other* text in their block mentioned a write flag. Both are genuine reads and must keep caching.
2. **Sliced from each `.command(` to the next.** A fixed-size window spills into the following command's block and reports *its* `persist: false` as this command's — which is how the original audit produced false "already correct" results.
3. **The excluded packages are derived from the helper source, not hardcoded.** The scan skips any package whose `src/cli/output.ts` has no `persist` support, so it starts enforcing automatically if `github-enterprise` or `powerplatform-customization` ever adopts the caching helper.

## Testing

**Automated.** 818 tests green across 14 test-bearing packages (`meta` 12 → 15), clean full build with zero TypeScript errors.

The guard asserts it **found** things before it asserts they are correct — more than 500 CLI commands scanned and more than 50 documented writes among them. A scanning guard that silently matches nothing reports success while checking nothing, which is the exact failure mode these guards exist to prevent.

**Inversion-checked.** Removing `persist: false` from `azure-storage queue receive` turns the guard red and names `packages/azure-storage/src/cli/commands/queue-commands.ts:131 (receive)` in the failure output. Restored, all 15 `meta` tests pass.

**Not verified:** no command in this iteration was run against a live tenant. The change is a single literal added to an options object on each call site, the behaviour it selects was proven live in beta.10 (in `teams`, a write left the directory empty while a read created the cache file), and the guard plus a clean build cover the rest. A runtime spot-check on a machine with real Azure DevOps credentials — run `sync push` or `wiki str-replace` in an empty directory and confirm no `.context/` appears — is still the one useful post-publish check.

**A counting note for anyone reconciling with beta.12.** Beta.12's notes say 146 write commands; a call-site scan counts 155, now 176. The difference is method, not missing work — a command name registered under two groups (`azure-storage copy` exists under both `blob` and `file`) counts twice in a call-site scan.

## Known Issues

Unchanged from beta.13: `sharepoint`'s CLI still ignores `--no-cache` (its `outputResult` honours `persist` but never reads the global flags, so a read command always writes its cache file with no way to opt out); the Teams package still cannot post an @-mention; `auth login`'s exit code on a completed sign-in and the abandoned-device-code path remain unexercised; no tool can delete a message the agent sent; `list-teams` remains broken on the `latest` tag (`33.0.0`) for device-code users.
