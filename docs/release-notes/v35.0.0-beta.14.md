# Release Notes: v35.0.0-beta.14

**Date:** 2026-08-13
**Branch:** `release/35.0`
**Status:** Local testing — not yet published

> Per-iteration agent-level detail. The user-facing single source of truth is [`v35.0.0.md`](v35.0.0.md).

> **This iteration is still open.** Further audit findings are expected before publish and will be folded in here. The master file is updated, and the Teams announcement sent, only at publish time.

## Overview

Two independent pieces of work, both acting on findings from audits of published artifacts.

**1. Closes the gap beta.12 left in the CLI write-cache sweep.** Beta.12 marked 155 write commands so they write no cache file and create no `.context/` directory in the caller's working directory. It classified them with a verb-prefix regex, and the regex missed a batch. A static audit found 21 write commands still caching. They are marked now, and a guard test enforces the rule mechanically so the class cannot recur.

**2. Fixes two `code-review` error-reporting defects found on a live client tenant.** The membership hint that beta.3 was supposed to add never appeared, because the clone was free to fall back to an interactive credential prompt and the resulting error carried none of the text the hint keys on. And a 404 under the Azure DevOps provider was answering with GitHub SAML SSO guidance.

No new tools, no configuration changes, no changes to how any command is called.

## Changes Implemented

### Bug fix — 21 write commands were still writing a cache file

The commands, by how each was proven to be a write.

**14 whose own `.description()` names an `ENABLE_*_WRITE` flag:**

| Package | Command |
|---|---|
| `1password` | `item batch-create` |
| `azure-devops` | `sync push`, `sync push-tasks`, `wiki str-replace`, `pr vote` |
| `azure-storage` | `blob copy`, `file copy`, `queue receive`, `table insert`, `table upsert`, `table batch` |
| `fabric` | `capacity unassign`, `domain unassign-workspaces` |
| `sharepoint` | `copy` |

**3 whose description names an `ENABLE_*_DELETE` flag:**

| Package | Command |
|---|---|
| `1password` | `item archive`, `item batch-delete` |
| `powerplatform-data` | `disassociate` |

**4 that mutate without naming a flag in their text**, gated in the service context instead (`ctx.checkInsertEnabled()` and friends), so no rule could prove them and they were marked by hand:

| Package | Command | Why it is a write |
|---|---|---|
| `azure-devops-admin` | `pipeline queue` | Queues a pipeline run — starts a build |
| `azure-sql` | `crud insert` | Executes an INSERT |
| `azure-sql` | `view drop` | Drops a view |
| `azure-sql` | `sproc drop` | Drops a stored procedure |

**Why the first sweep missed them.** It matched command *names* against a verb-prefix regex, which is guessing intent from a label. The rule used here reads the repo's own documentation instead:

> A command whose own `.description()` tells the user to set an `ENABLE_*_WRITE=true` / `ENABLE_*_DELETE=true` flag is, by that sentence, a write.

That needs no judgement, and it gets right the one case verb-matching must get wrong: **`azure-storage queue receive` reads like a read**, but receiving a message hides it and changes its visibility — which is exactly why it sits behind the write flag to begin with.

### Deliberately left caching

- **`rest-api batch`** matches a naive scan and keeps its cache. It executes a list of arbitrary REST requests and the cached payload is the actual response bodies — the thing most worth grepping. Its sibling `request` is unmarked for the same reason, even though `request` can POST. The test is *"is the payload worth grepping"*, not *"does it mutate"*; for these two the response is the deliverable.
- **`github-enterprise` (12 commands) and `powerplatform-customization`** name write flags in their descriptions but have bespoke CLI output helpers that `console.log` and never cache anything. There is nothing to suppress.

### Test — guard against the whole class

`packages/meta/src/__tests__/cli-write-cache.test.ts` scans every CLI command in the monorepo and fails on any command whose own description documents it as a write while it still caches, naming the offender as `file:line (command)`. It lives in `meta` for the same reason as `entrypoint-versions.test.ts` — meta aggregates the whole suite.

Three details matter in how it is written:

1. **Keyed on the command's own `.description()` string, not the whole command block.** Testing the block produces false positives — `azure-devops diff` and `azure-management logs` were both flagged during the audit because some *other* text in their block mentioned a write flag. Both are genuine reads and must keep caching.
2. **Sliced from each `.command(` to the next.** A fixed-size window spills into the following command's block and reports *its* `persist: false` as this command's — which is how the original audit produced false "already correct" results.
3. **The excluded packages are derived from the helper source, not hardcoded.** The scan skips any package whose `src/cli/output.ts` has no `persist` support, so it starts enforcing automatically if `github-enterprise` or `powerplatform-customization` ever adopts the caching helper.

### Bug fix — the `code-review` clone hint never appeared, and the error said less than before

Reported from a live client tenant: under `CODE_REVIEW_AZDO_AUTH_METHOD=entra-id`, a clone-path command produced a bare `Git clone failed: Command failed: git … / Cloning into '…'` with no membership paragraph, no mention of `cr-list-repos`, and no object id. Reproduced three times. A second symptom in the same output: beta.2 had ended with git's own `fatal: Authentication failed for '<url>'` and beta.3 did not, so beta.3 surfaced strictly *less* information than its predecessor.

**The two symptoms are one bug, and the hint logic was never at fault.** Diffing beta.2 against beta.3 shows the Entra clone path did not change at all between them — only the PAT clone URL did. What varies is git's own behaviour: left to itself, git answers a rejected credential by falling back to an interactive credential prompt. On a machine with a controlling terminal it then blocks until the 120-second timeout kills it, and a killed git has printed only `Cloning into '<dir>'...`. The authentication text never reaches the caller, so `describeCloneAuthFailure()` — which matches on that text, correctly — finds nothing to match and returns null. Which message you get depends on whether a credential happened to be cached on the machine, which is why it changed between two builds that share the same code.

The fix makes the clone unattended, so it fails the same way every time:

- `GIT_TERMINAL_PROMPT=0`, with `GIT_ASKPASS` and `SSH_ASKPASS` emptied so the prompt cannot be re-routed to a GUI helper. Git now fails immediately with `fatal: could not read Username for '<url>': terminal prompts disabled` — which the existing matcher already recognises, so the membership hint attaches.
- `-c credential.helper=`, neutralising any helper configured on the machine (`osxkeychain` is the macOS default). Every path here supplies its own credential explicitly, so a helper can only answer with a stale cached credential — making the outcome depend on machine state — or with a different person's credential, which would have the run silently review a repository as somebody else.
- A clone killed by the timeout now says so explicitly, instead of presenting whatever git had printed by then as if it were the whole story.

### Bug fix — an Azure DevOps 404 gave GitHub advice

Verbatim from the live run: *"Not found while listing repositories for `<project>` (404). Check the name; for a GitHub org the token may also need SAML SSO authorization (Settings > Developer settings > Personal access tokens > Configure SSO)."* SAML SSO and that settings page are GitHub concepts; under the Azure DevOps provider they name a page the reader does not have.

`notFoundHint()` and `forbiddenHint()` now branch on the provider in use. The Azure DevOps 404 instead points at the actual measured cause — a stale project name, in that case one carried over from a local clone's git remote naming a project the organisation no longer holds — and tells the reader to run `cr-list-repos` with no `--project` to see what is really there.

**The 403 one line above had the same defect and is fixed in the same change**, though it was not in the report: it offered the same SAML guidance to Azure DevOps users. It now distinguishes the two auth methods, which need different fixes — a service principal needs Code (read) granted under Project settings, a PAT needs the right scope and is scoped per organization.

## Testing

**Automated.** 833 tests green across 14 test-bearing packages (`meta` 12 → 15, `code-review` 104 → 119), clean full build with zero TypeScript errors.

The guard asserts it **found** things before it asserts they are correct — more than 500 CLI commands scanned and more than 50 documented writes among them. A scanning guard that silently matches nothing reports success while checking nothing, which is the exact failure mode these guards exist to prevent.

**Inversion-checked.** Removing `persist: false` from `azure-storage queue receive` turns the guard red and names `packages/azure-storage/src/cli/commands/queue-commands.ts:131 (receive)` in the failure output. Restored, all 15 `meta` tests pass.

**Not verified:** no command in this iteration was run against a live tenant. The change is a single literal added to an options object on each call site, the behaviour it selects was proven live in beta.10 (in `teams`, a write left the directory empty while a read created the cache file), and the guard plus a clean build cover the rest. A runtime spot-check on a machine with real Azure DevOps credentials — run `sync push` or `wiki str-replace` in an empty directory and confirm no `.context/` appears — is still the one useful post-publish check.

**A counting note for anyone reconciling with beta.12.** Beta.12's notes say 146 write commands; a call-site scan counts 155, now 176. The difference is method, not missing work — a command name registered under two groups (`azure-storage copy` exists under both `blob` and `file`) counts twice in a call-site scan.

**The non-interactive clone fix cannot be proven from a test process, and the first attempt to do so was a fake pass.** A test that drives a real `git clone` against a local 401 challenge passes *identically with the fix removed* — verified by inversion, not assumed — because a test runner's worker has no controlling terminal, so git declines to prompt there regardless. The assertions that actually invert are the ones on the exported `NON_INTERACTIVE_GIT_ENV` and `buildCloneArgs`; the live-git test was kept but scoped to the half it does prove, that git's own 401 wording still satisfies the hint matcher, so the two cannot drift apart. **The runtime proof needs a machine with a terminal and a real organisation** — see below.

**A credential-in-cache guard now covers the paths the live check could not.** The live run proved the PAT absent from one cache file, the `list-repos` REST response; the `check-dotnet` and 2 MB `review` caches were deleted before they could be checked. `packages/code-review/src/__tests__/cache-secrets.test.ts` covers both, plus every error-message builder that handles a credential. It asserts its preconditions first — that the search pattern is real and the payload non-empty — because both hand-attempts at this check returned confident answers in opposite directions, one from an empty grep pattern matching every file, one from a false zero where the CLI never ran. Inversion-checked by making `redactSecret` a no-op.

Worth recording: the happy path structurally cannot leak a credential. Every `catch` in the services is a bare `catch {}` that discards the error, so no error text reaches a report, and a CLI failure exits through `handleCliError` to stderr without writing a cache at all. The guard is defence in depth rather than the only barrier.

## Needs a live rerun before this is trusted

The clone fix changes how a subprocess behaves on a machine with a controlling terminal, which is precisely what CI does not have. On a machine with a real Azure DevOps organisation, under `CODE_REVIEW_AZDO_AUTH_METHOD=entra-id`:

1. Run any clone-path command (`check-dotnet` or `complexity`). Expect it to **fail within seconds rather than hanging**, and expect the output to end with the membership paragraph naming `cr-list-repos` and the configured organization.
2. Confirm git's own `fatal:` line is back — the beta.3 tails had none.
3. Request a repository under a project that does not exist and confirm the 404 no longer mentions SAML SSO or "Developer settings", and does point at `cr-list-repos`.

Report verbatim output for each. Two of the three findings this iteration acts on were the opposite of what was expected from reading the code, so the reasoning above is not a substitute for the run.

## Known Issues

**Still blocked externally.** The acceptance criterion that a repository the identity cannot read must fail loudly, rather than returning an empty result set or a zero count, remains unproven and cannot be proven yet. Only the not-found case has been tested (a non-existent repository name: exit 1, `TF401019` named, no zero counts). The genuine permission-denied case needs the service principal to be a member of the organisation, requested on an internal ticket and still unactioned — a full-access PAT can read everything and so cannot produce the contrast. This one matters more than a normal loose end: of the 29 defects the assurance run recorded across the six CLIs, roughly 22 failed *towards a clean-looking result* — a zero count, a null field, an empty map. An auth path returning an empty repository list instead of a permission error would be that same failure mode in a new place, and it is the one thing about this feature still unproven.

**Not fixable from this repo.** The documented `CR="npx …"` invocation idiom fails under zsh in all six assurance CLI reference files, because zsh does not word-split an unquoted variable. The working form is a shell function: `cr() { npx -y --package=@mcp-consultant-tools/code-review@beta mcp-code-review-cli --mcp-config ./.mcp.json --mcp-server code-review "$@"; }`. Those files live in the consuming Vantage skills, not in this repository — confirmed absent here — so the sweep has to happen there. Recorded since beta.11.

**Dist tags at promotion.** `code-review`, `azure-defender`, `entra-id` and `message-center` each have a beta on their `latest` tag, because npm assigns `latest` on a package's first-ever publish regardless of `--tag beta`. Harmless for anyone pinned to `@beta`, but a bare `npm install` resolves to a prerelease. Correct at v35 promotion, not mid-beta.

Unchanged from beta.13: `sharepoint`'s CLI still ignores `--no-cache` (its `outputResult` honours `persist` but never reads the global flags, so a read command always writes its cache file with no way to opt out); the Teams package still cannot post an @-mention; `auth login`'s exit code on a completed sign-in and the abandoned-device-code path remain unexercised; no tool can delete a message the agent sent; `list-teams` remains broken on the `latest` tag (`33.0.0`) for device-code users.
