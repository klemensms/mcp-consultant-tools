# Release Notes: v35.0.0-beta.9

**Date:** 2026-08-13
**Branch:** `release/35.0`
**Status:** Published to beta

> Per-iteration agent-level detail. The user-facing single source of truth is [`v35.0.0.md`](v35.0.0.md).

## Overview

Implements the feature request raised from the first full assurance run against a production tenant: `mcp-code-review-cli` was the only CLI in the family that could not use the shared Entra app registration, so it required a personal access token. A PAT is issued against a person, expires on a fixed schedule, and puts a second credential type with a different owner into a config whose standard is one `.mcp.json` of Entra client credentials.

This is not a new capability — both halves already existed in the same codebase. `CODE_REVIEW_PROVIDER=github-app` was already an app identity rather than a human token, and the sibling `mcp-loganalytics-cli` already had an explicit `*_AUTH_METHOD=entra-id` switch. This makes the package consistent with itself.

`code-review` and `meta` only. No breaking change: `CODE_REVIEW_AZDO_AUTH_METHOD` is optional and defaults to `pat`.

## Changes Implemented

- **`AzdoEntraAuth` (new, `src/utils/azdo-entra-auth.ts`).** Client-credentials grant against `https://login.microsoftonline.com/{tenant}/oauth2/v2.0/token`, scope `499b84ac-1321-427f-aa17-267ca6975798/.default` (the Azure DevOps first-party application ID). Token cached in-process and refreshed five minutes before expiry. Mirrors the existing `GheAppAuth` and is deliberately **not** hoisted to `core`, following the per-package precedent (`entra-id`, `azure-defender`, `message-center` each keep their own).
- **`describeTokenError()`** builds a token-failure message from the response body **only**. An axios error carries the outbound form body — which contains the client secret — on `error.config.data`, so anything that stringifies the whole error leaks the credential.
- **Config switch (`context-factory.ts`).** `CODE_REVIEW_AZDO_AUTH_METHOD` accepts `pat` | `entra-id`; absent means `pat`. An invalid value is rejected by name. Per-method validation names every missing variable — `entra-id` demands the client ID / secret / tenant ID and does *not* demand a PAT; `pat` is unchanged.
- **REST auth (`code-review-client.ts`).** Under `entra-id` the Azure DevOps axios instance gets a request interceptor setting `Authorization: Bearer <token>`, matching how the `github-app` provider already works. The PAT branch keeps its basic-auth header untouched.
- **Clone auth — the half the originating request did not cover.** Eight of the ten tools clone the repository (`cr-tree`, `cr-check-dotnet`, `cr-check-nuget`, `cr-complexity`, `cr-review` and the paths beneath them). REST-only auth would have left `cr-list-repos` working and every analysis tool failing, which the request's own acceptance criteria rule out. Under `entra-id` the clone URL carries **no credential at all** (`buildAzdoBearerCloneUrl`); the token is passed as `git -c http.extraHeader=Authorization: Bearer <token>`, the form Microsoft documents for Azure DevOps.
- **Bearer-token redaction (`clone-manager.ts`).** That header is part of git's argv, and Node's `execFile` error message is `Command failed: <full argv>` — so a failed clone would otherwise echo the token. `CloneOptions.bearerToken` is redacted from clone errors alongside the existing URL-userinfo redaction. `redactCloneSecret` is refactored onto a shared `redactSecret` helper.
- **`TF401444` mapping (`describeUnprovisionedPrincipal()`).** Azure DevOps answers a *valid* service-principal token with `401 TF401444` when the principal is not a member of the organisation. That is an identity-provisioning problem, not a bad credential, and a bare 401 reads as "wrong secret". The error now names the prerequisite, the organisation, and the principal's object ID parsed out of the response message, and states that the token was issued and accepted.
- **302-redirect fix (pre-existing defect).** Azure DevOps answers a rejected credential with a **302 to a sign-in page**, not a 401. Axios followed it into an HTML body with no `value` array, and `listAzdoRepositories` died on `undefined.map` — an auth failure disguised as a parse crash. The Azure DevOps client now sets `maxRedirects: 0`, and `raiseGitError` maps `302`/`203` to an authentication error naming which credential type was rejected. This affects the existing PAT path as much as the new one.
- **Docs.** `packages/code-review/CLAUDE.md` (new "Azure DevOps service-principal auth" section + two architecture notes), `docs/documentation/CODE_REVIEW.md`, `docs/technical/CODE_REVIEW_TECHNICAL.md` (config table, a full `entra-id` subsection, error-handling and security updates, and honest `known-limitations`).

## Testing

**98 tests green** (up from 80), run against the clean release build. New coverage:

- Auth-method defaulting, invalid-value rejection, and per-method missing-variable reporting — including the negative assertions that `entra-id` does not demand a PAT and `pat` does not demand the Entra trio.
- Constructor validation for `entra-id` with and without a token source.
- `describeUnprovisionedPrincipal` with an object ID, without one, and negative cases for other 401 bodies and non-object bodies.
- The credential-free clone URL (asserting it contains no `@`).
- `describeTokenError` — asserts the planted client secret from the request body reaches no message.
- A failing clone with a planted bearer token, asserting it survives into no error output.

**The redaction test was checked for vacuity.** A throwaway `node -e` probe confirmed Node's `execFile` really does echo `git -c http.extraHeader=Authorization: Bearer <token>` back in its error message, so the test fails without the redaction rather than passing regardless.

**Runtime:** clean build (`npm run build:release`) green across all 22 packages, 41 `.d.ts` files emitted for `code-review`. The rebuilt server registers 10 tools over real MCP stdio. Three MCP-level checks: `entra-id` with no credentials reports all three missing variables by name; `entra-id` with placeholder credentials reaches Entra and fails there (proving the path is wired, not silently falling back to PAT); the `pat` path is unchanged. CLI parity confirmed — `mcp-code-review-cli list-repos` under `entra-id` logs `auth: entra-id` and takes the same path.

**Two live probes, both unauthenticated:**

- `login.microsoftonline.com` — a placeholder tenant returns `AADSTS90002` through `describeTokenError()`. The client-credentials request shape is confirmed.
- `dev.azure.com` REST with a rejected credential — confirmed HTTP 302 to a sign-in page. This is what found the pre-existing `undefined.map` defect.

## Known Issues

- **`entra-id` has never authenticated successfully.** No service principal is yet a member of an Azure DevOps organisation, so an *accepted* token, the `TF401444` response body shape, and every clone under `entra-id` remain unverified end to end. The `TF401444` handling is mapped from the message quoted in the originating feature request, not from a captured response — if the real body differs, the mapping falls through to a generic 401 rather than misreporting.
- **Adding the service principal to the organisation is a tenant-side step**, not a code change, and is required regardless of which authentication method ships. Requested on Connect365 ticket #618258.
- **`@mcp-consultant-tools/code-review` carries a beta on its `latest` dist-tag** (`35.0.0-beta.1`). npm assigns `latest` on a package's first-ever publish regardless of `--tag`, and this package first shipped in beta.3. Harmless for beta consumers, but `npm install` without a tag currently resolves to a beta. Worth correcting when v35 is promoted.
