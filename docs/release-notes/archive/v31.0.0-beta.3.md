## Why this beta exists

The 2026-04-30 end-to-end demo against `acmedev.crm.dynamics.com` (captured in `tests/pii-demo/demo.md` / `demo.html`) surfaced three completeness gaps in the v1 pipeline. Each was a known scope boundary, none was a regression, but each measurably reduced the pipeline's coverage in the demo. This beta closes them.

## Changes Implemented

### Finding 1 — OData FormattedValue annotations now reach the pipeline (`powerplatform-core`)

**Symptom in beta.2:** `query-records` and `get-record` did not request OData annotations from Dataverse, so `_primarycontactid_value@OData.Community.Display.V1.FormattedValue: "Maria Schmidt"` (and equivalents on every lookup field) were absent from responses. Layer 4 NER on lookup display names was therefore a no-op in production — the v1 deliverables checklist had this listed as "not yet tested with `$expand`," but the demo run confirmed it was simply missing data, not just untested.

**Fix:** added `Prefer: odata.include-annotations="*"` header to:
- `DataService.queryRecords` — the leverage-point read used by `query-records`.
- `DataService.getRecord` — the per-record read used by `get-record`.
- `DataService.createRecord` and `updateRecord` — combined with `return=representation` so the create/update response now includes lookup display annotations alongside the record.

The header is **not** added to `PowerPlatformClient.makeRequest` itself — that would also pollute metadata-query responses (`EntityDefinitions`, `RelationshipDefinitions`, etc.) with annotations that don't apply. Targeted at the data-record paths only.

**Verified:** test 1 in `.context/test-write-paths.mjs` against the seeded `Contoso Deutschland GmbH` account fixture. 44 `FormattedValue` annotations now present in the response (vs zero in beta.2). The `_primarycontactid_value@OData.Community.Display.V1.FormattedValue` annotation reads `[REDACTED:name:be1ad2]` — Layer 4 NER caught Maria Schmidt's name on the lookup display.

### Finding 3 — write-path responses now redacted

**Symptom in beta.2:** the pipeline only ran on read paths. `create-record`, `update-record`, `execute-action`, and the equivalent ADO and SQL write tools echoed full response bodies (Dataverse `Prefer: return=representation` returns the entire created/updated record; ADO `createWorkItem` returns the work-item with identity fields; SQL `executeSproc` and `executeUnrestricted` return result rows). The Phase 2.1 plan called for both directions; only read was wired.

**Fix:** wrapped return values through the existing `pipeline.redactResponse(entity, data)` helper in:

| Package | Service | Methods |
|---|---|---|
| `powerplatform-core` | `DataService` | `getRecord`, `createRecord`, `updateRecord`, `executeAction` |
| `azure-devops` | `WorkItemService` | `createWorkItem`, `updateWorkItem`, `addWorkItemComment`, `updateWorkItemComment` |
| `azure-sql` | `WriteService` | `executeSproc` (rows), `executeUnrestricted` (per-batch resultSets) |

**Not changed:**
- `azure-b2c` `UserService.createUser` was already wrapping through `this.redact(user)` in beta.2; `updateUser` returns through `getUser()` which already redacts. No change required.
- `rest-api` `RestApiService.request()` redacts every response body regardless of HTTP method (its single redaction point already covers POST/PATCH/PUT/DELETE responses). No change required.
- DML methods that return only rowcount/message (`executeInsert`, `executeUpdate`, `executeDelete` in azure-sql) — no row data returned, no redaction needed.

`WriteService` (azure-sql) gains an optional `piiPipeline` constructor argument; wired in `context-factory.ts` and `index.ts` to mirror `QueryService`. `executeAction` (powerplatform-core) uses the synthetic entity name `'action-result'` since custom actions have no fixed entity type — Layer 2 doesn't fire (no per-entity field rules), but Layers 3 and 4 still scan all string values.

**Verified:** tests 2 and 3 in `.context/test-write-paths.mjs`. `get-record` on Maria returns 10 distinct redaction tokens; zero literal "Maria"/"Schmidt" in the response. `update-record` on Maria with a no-op (`firstname: "Maria"`) returns the same 10 tokens; zero literal name. The `[REDACTED:name:be1ad2]` token appears identically in test 1 (lookup annotation), test 2 (full record), and test 3 (update echo) — cross-call correlation across read and write paths confirmed.

### Finding 2 — custom-pattern documentation expanded (`docs/documentation/pii-protection.md`)

**Symptom in beta.2:** the demo run flagged that locale-specific date formats (e.g. `12 March 1985`, `12.03.85`) pass through Layer 3 because the built-in regex matches ISO `YYYY-MM-DD` only. The `customPatterns` extension point existed but was not surfaced in the user-facing doc — operators trying to extend coverage had to read the technical doc or the source.

**Fix:** added a new "Adding custom patterns (Layer 3 extension)" subsection under "Coverage notes" with:
- The exact JSON shape (`name`, `tokenType`, `pattern`).
- A worked example covering UK domestic phones, locale-format dates, and a national-ID format.
- A note that patterns compile as `new RegExp(pattern, 'g')` (case-sensitive, no inline-flag support; use character classes for case insensitivity).
- A warning about over-broad patterns and a recommendation to start with Layer 2 field rules where the field name is known.

Also added an explicit bullet under "Coverage notes" calling out the ISO-only date-regex limit, alongside the existing international-only phone-regex limit.

**Not done:** built-in regex extension for non-ISO dates. Adding more permissive date patterns risks false positives on version strings, IDs, and timestamps — the cost/benefit is wrong for the default set. Documented `customPatterns` is the cheapest defensible position.

## Bonus discovery

`DataService.getRecord` was not redacting in beta.2 either — the demo only exercised `query-records`, so this was not surfaced earlier. The Finding 1 fix (which added the Prefer header) also added the missing pipeline call. Now both `getRecord` and `queryRecords` redact.

## Verified

All verifications run locally against `acmedev.crm.dynamics.com` with real fixtures (Maria Schmidt, Contoso Deutschland GmbH).

- **Workspace `npm run build`:** clean across affected packages (`powerplatform-core`, `powerplatform-data`, `azure-devops`, `azure-sql`, `azure-b2c`).
- **Finding 1(a) — annotations + lookup-name redaction:** `query-records` on `accounts` filtered to Contoso → 44 `FormattedValue` annotations in response; `_primarycontactid_value@OData.Community.Display.V1.FormattedValue` shows `[REDACTED:name:be1ad2]`.
- **Finding 3 — getRecord redaction:** `get-record` on Maria's contactid → 10 distinct redaction tokens; zero literal name.
- **Finding 3 — updateRecord redaction:** `update-record` on Maria with no-op → 10 distinct redaction tokens in the response; zero literal name.
- **Cross-call correlation across read/write:** the `[REDACTED:name:be1ad2]` token for "Maria Schmidt" is identical across the three test calls within one process (Q1 contract still met).

End-to-end verification against the other write paths (`createWorkItem`, `updateWorkItem`, `addWorkItemComment`, `updateWorkItemComment`, `executeSproc`, `executeUnrestricted`, `executeAction`) is the purpose of the beta-testing phase. Implementation mirrors the read-path pattern that has already been validated in beta.2.

- `packages/azure-devops/src/services/work-item-service.ts` — pipeline wrap on `addWorkItemComment`/`updateWorkItemComment`/`updateWorkItem`/`createWorkItem`.
- `packages/azure-sql/src/services/write-service.ts` — `piiPipeline` constructor argument; pipeline wrap on `executeSproc.rows` and `executeUnrestricted.batchResult.resultSet`.
- `packages/azure-sql/src/context-factory.ts` and `index.ts` — pipeline injected into `WriteService` constructor (mirrors `QueryService`).
- `docs/documentation/pii-protection.md` — `customPatterns` subsection + ISO-only date-regex limit bullet.

## Out of scope (deferred again)

These remain on the v1.5 / v32 backlog as before:

- Phase 6 (audit and compliance logging) — separately scoped session.
- Layer 5 (local LLM safety net) — v2 alongside model-host deployment topology.
- `pii-explain-last-call` MCP tool and `--redaction-diff` CLI flag — v1.5.
- Auto-detection of PII-candidate fields from Dataverse metadata — v1.5+.
- Built-in non-ISO date regex — `customPatterns` is the answer; default set stays narrow.
- Nested-object Layer 2 walking for ADO identity objects — v1.5.
- B2C `GroupService` — group fields are not person PII.
