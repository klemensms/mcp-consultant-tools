# Release Notes: v34.0.0-beta.2

**Date:** 2026-06-15
**Branch:** `release/34.0`
**Status:** Published to beta

> Per-iteration agent-level detail. The user-facing single source of truth is [`v34.0.0.md`](v34.0.0.md).

## Overview

A security-hardening wave from a self-audit of every tool that takes a caller-supplied filesystem path or URL. Two classes of issue closed: unconfined write paths / traversable untrusted filenames, and the `rest-api` `host` override that could exfiltrate the configured credentials to an arbitrary host. No new tools; no change to success-path response shapes. Behaviour changes are confined to two narrow patterns documented in the master Upgrade Notes.

## Changes Implemented

- **`core`** — new `helpers/safe-path.ts`: `resolveSafePath` (confine writes to `MCP_FILE_ROOT`/cwd), `assertNoTraversal` (reject `..` on reads, allow absolute), `safeBasename` (collapse an untrusted filename to its basename). Exported from the package index. 19 vitest tests.
- **`rest-api`** —
  - `host` override locked to the `REST_BASE_URL` origin; additional origins via new `REST_ALLOWED_HOSTS` (comma-separated) env var. Rejection happens before any network call.
  - `redirect: 'error'` on the request fetch so a 3xx can't bounce an authed request cross-origin.
  - MCP server entry (`index.ts`) now imports `createServiceContext` from the shared `context-factory` instead of a copy-pasted `buildConfigFromEnv` — fixes a latent drift bug (the duplicate ignored `REST_ALLOWED_HOSTS`) and removes ~120 duplicated lines. Matches the azure-devops reference pattern.
  - `host` tool description updated to state the restriction; `getConfigSummary` reports `allowedHosts`.
- **`azure-devops`** —
  - `download-work-item-attachment`: `safeBasename` on the untrusted attachment filename + `resolveSafePath` on `outputDir` — fixes injection-reachable path traversal.
  - `save-wiki-page-to-file`, `download-wiki-attachment`: confine caller-supplied output paths (server defaults untouched).
  - `upload-wiki-page-from-file`, `upload-work-item-attachment`: reject `..` traversal on the source path.
- **`powerplatform-customization`** —
  - `download-form-to-file`: confine the write destination.
  - `deploy-form-file`, `diff-form-file`, `deploy-web-resource-file`, `create/update-plugin-assembly`: reject `..` traversal on the source path while still allowing the absolute paths these workflows use (e.g. a DLL at an absolute build path).
- **Docs** — documented `REST_ALLOWED_HOSTS` (rest-api guide) and `MCP_FILE_ROOT` (core guide).
- **Versions** — `core` and `rest-api` enter the v34 line at `34.0.0-beta.2`; `azure-devops`, `powerplatform-customization`, `meta` bump `beta.1 → beta.2`. The three packages that consume the new `core` helper (`rest-api`, `azure-devops`, `powerplatform-customization`) repin their `core` dependency to `34.0.0-beta.2`; `meta` repins `core`/`rest-api`/`azure-devops`/`powerplatform-customization`. Unchanged beta.1 packages (`powerplatform`, `powerplatform-core`, `powerplatform-data`, `log-analytics`) are left at beta.1.

## Testing

- `core`: 109 tests pass (90 existing + 19 new safe-path).
- `azure-devops`: 7 tests pass.
- `rest-api` host-lock verified end-to-end through the live MCP server (`.claude/templates/mcp-test-runner.mjs`): disallowed host, `localhost`, and non-URL rejected before any network call; allowlisted host (via `REST_ALLOWED_HOSTS`), same-origin host, and no-host pass the guard and proceed to the network stage.
- `rest-api`/`powerplatform-customization` have no vitest suite — verified by clean build + runtime checks of the helper integration.
- Clean `build:release` green; `.d.ts` files present in all 5 republished tarballs.

## Known Issues

- None found this iteration. The path confinement is opt-out via `MCP_FILE_ROOT`; the host lock is opt-out via `REST_ALLOWED_HOSTS` — see master Upgrade Notes for the two affected usage patterns.
