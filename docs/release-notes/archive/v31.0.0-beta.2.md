## Overview

Two follow-on items on top of `v31.0.0-beta.1`'s PII pipeline:

1. **`PII_SESSION_SALT` env var** — opt-in cross-MCP-server token correlation. Set the same 64-hex value across all MCP servers in a `.mcp.json` and they all derive identical tokens, enabling the agent to reconcile "same person across systems" (e.g. linking a B2C user to a CRM contact by email).
2. **B2C MCP server PII wiring** — the fifth surface to gain redaction. Default field rules cover `givenName`, `surname`, `displayName`, `mail`, `otherMails`, `mobilePhone`. Borderline fields (`streetAddress`, `city`, `country`, `postalCode`, `jobTitle`) are not in defaults but can be opted-in via `PII_CONFIG_PATH`.

No change to the v1 surface contract: same flag-contract gating (`MCP_ENVIRONMENT_TYPE` + `PII_PROTECTION` both required, production refuses `PII_PROTECTION=false`), same refuse-to-start matrix, same observe-mode and URL-heuristic safety-net behaviour.

## Breaking Changes

- **`UserService` constructor (azure-b2c)** — second optional argument `piiPipeline?: PiiProtectionPipeline`. Existing callers passing only `(client)` continue working.
- **`b2c-user` entity added to `defaultFieldRules()` in core's PII config** — six fields (`givenName`, `surname`, `displayName`, `mail`, `otherMails`, `mobilePhone`) redacted by default for any callers using the default config. To override, supply `PII_CONFIG_PATH` with a custom `fieldRules.b2c-user` entry.

No public API or response-shape breaks beyond these constructor extensions.

## New Features

### `PII_SESSION_SALT` (cross-MCP-server token correlation)

By default, each MCP server process generates an independent random 32-byte salt at startup, so the same email tokenizes differently across `pp-data` / `azure-devops` / `azure-sql` / `rest-api` / `azure-b2c`. The agent cannot reconcile "same person across systems" — which blocks cross-MCP analysis tasks.

Set `PII_SESSION_SALT` to a 64-character hex string (32 bytes) in **every** MCP server's `env:` block in `.mcp.json` to share a salt. All servers then derive identical tokens for the same input value.

```bash
# Generate a fresh salt
openssl rand -hex 32
```

```json
// .mcp.json — paste the SAME value into each server's env block
{
  "mcpServers": {
    "powerplatform-data": { "env": { "PII_SESSION_SALT": "a3f4...", ... } },
    "azure-devops":       { "env": { "PII_SESSION_SALT": "a3f4...", ... } },
    "azure-sql":          { "env": { "PII_SESSION_SALT": "a3f4...", ... } },
    "azure-b2c":          { "env": { "PII_SESSION_SALT": "a3f4...", ... } }
  }
}
```

**Validation rules:**
- A non-empty value must contain only hex characters (`0-9`, `a-f`, `A-F`) and decode to exactly 32 bytes (i.e. exactly 64 hex characters). Anything else → refuse-to-start.
- Unset, empty string (`""`), or whitespace-only → falls back to per-process random salt (no error). Leaving `PII_SESSION_SALT=""` in `.mcp.json` is a deliberate "I see the option exists but I'm not opting in yet" pattern.

**Tradeoff:** persistent shared salt = stronger correlation across servers, weaker forgetability across time. Rotation recommendation:
- **Minimum once per engagement.**
- Per-day for sensitive work.
- Do not persist outside `.mcp.json` (which itself should be gitignored).

**Implementation:** `loadSessionSalt()` helper in `packages/core/src/pii/config.ts`. Called inline from `loadPiiConfig()`. Returns `Buffer` of length 32; the buffer is captured in closure inside `LoadedPiiContext.getSalt()` and never serialised in any `PipelineReport`.

### Azure B2C MCP server — PII pipeline wired

`UserService` (in `packages/azure-b2c/src/services/user-service.ts`) now accepts an optional `piiPipeline` constructor argument and applies redaction at every read return path:

- `listUsers` — both branches (cache hit and Graph fetch). Cache stores **unredacted** data so per-session salts apply correctly across cache hits.
- `getUser` — both branches (`includeAllFields=true` returns raw response; `includeAllFields=false` returns mapped `B2CUser`).
- `searchUsers` — both branches.
- `createUser` — the mapped `B2CUser` returned after a successful create is redacted.
- `updateUser` — inherits redaction via its trailing `await this.getUser(userId)` call.

`deleteUser` returns `void`, no redaction needed. Group methods are not currently wired (group `displayName`/`description` aren't person PII; can be added later if a particular client carries person names in group fields).

**Default field rules** (in `defaultFieldRules()`):
- `redactInResponse`: `givenName`, `surname`, `displayName`, `mail`, `otherMails`, `mobilePhone`.
- `excludeFromSelect`: empty (the MCP path doesn't expose arbitrary `$select`; L1 is inactive for B2C).

**Borderline fields NOT in defaults** — opt-in via `PII_CONFIG_PATH` if your client treats these as PII:
- `streetAddress`, `city`, `postalCode`, `country`
- `jobTitle`

Note: `userPrincipalName` typically holds the same email as `mail`, and Layer 3's email regex catches it — so even without an explicit field rule for `userPrincipalName`, it ends up redacted. The salted-HMAC produces the same token for the same email, so the agent can still reconcile "userPrincipalName and mail are the same person."

**Pipeline construction:** `index.ts` and `context-factory.ts` both eagerly construct the pipeline at server startup with `environmentIdentifier: process.env.AZURE_B2C_TENANT_ID`. The URL-heuristic warning fires at startup when `PII_PROTECTION=false` and the configured tenant identifier doesn't match any non-prod hint.

## Testing

All checks run locally; not published to npm.

**`PII_SESSION_SALT` loader (7 scenarios, all PASS):**
1. Unset → random 32-byte salt, differs between calls.
2. Valid 64-char hex → decodes to 32 bytes.
3. Shared salt → identical across loads (cross-server correlation).
4. Too-short hex → refuse-to-start.
5. Too-long hex → refuse-to-start.
6. Non-hex characters → refuse-to-start.
7. Mixed-case hex → still works.

**B2C refuse-to-start matrix (5 scenarios, all PASS):**
1. No flags set → refuse to start.
2. `production` + `PII_PROTECTION=true` → continue.
3. `production` + `PII_PROTECTION=false` → refuse to start.
4. `uat` + `PII_PROTECTION=false` → continue.
5. `dev` + `PII_PROTECTION=false` → continue.

**B2C functional redaction (12/13 expected, 13/13 actual):** synthetic Graph API user object with `givenName`, `surname`, `displayName`, `mail`, `otherMails`, `mobilePhone` plus non-PII fields (`id`, `jobTitle`, `department`, `city`, `country`, `accountEnabled`). All six PII fields redacted; `userPrincipalName` redacted via L3 email regex (the test originally expected it to pass through, but L3 catching emails regardless of field name is the correct, defensive behaviour).

**Full workspace build:** clean.

## Migration

If you were running v31.0.0-beta.1 and want to enable cross-MCP correlation, add `PII_SESSION_SALT=<openssl-rand-hex-32-output>` to every MCP server's `env:` block in `.mcp.json`. Without it, behaviour is unchanged from beta.1.

If you're starting B2C work fresh on this branch, add `MCP_ENVIRONMENT_TYPE`, `PII_PROTECTION`, `PII_OBSERVE_MODE` to the existing `azure-b2c` MCP config (see [`AZURE_B2C.md`](../documentation/AZURE_B2C.md) for both 1Password and local-credentials variants).
