# Release Notes: v31.0.0-beta.4

**Date:** 2026-04-30
**Branch:** `release/31.0`
**Status:** Published to beta

> Per-iteration agent-level detail. The user-facing single source of truth is [`v31.0.0.md`](v31.0.0.md).

## Overview

Closes the four findings (F4–F7) the beta.3 demo regen surfaced. No breaking changes — additive defaults + additional response footers + a docs section. Drop-in upgrade from beta.3 in any environment.

## Changes Implemented

### F4 — `yomifullname` not redacted on contact write paths (`@mcp-consultant-tools/core`)

Added the Yomi family (`yomifirstname`, `yomimiddlename`, `yomilastname`, `yomifullname`) plus `middlename` to the default Layer 2 `redactInResponse` rules for the `contact` entity in `packages/core/src/pii/config.ts`. Discovered in beta.3 demo Q5 (`update-record` on Maria Schmidt) where the computed phonetic-romanisation full name returned raw "Maria Schmidt" while every other PII field on the same record redacted correctly. Layer 2's `inferTokenType()` already classified yomi-prefixed fields as `name`; only the field list was the gap.

### F7 — Audit other Yomi-pattern fields (`@mcp-consultant-tools/core`)

Same Yomi family added to default rules for `lead` (entirely new entry — `lead` had **no** default rules previously, so every PII field on a lead response was passing through Layer 2 untouched) and `systemuser` (extended with the Yomi family, `middlename`, `mobilephone`). `account` picked up `telephone1` / `telephone2` / `telephone3` alongside the existing email defaults. Configurations that override `fieldRules.contact.redactInResponse` via `PII_CONFIG_PATH` should carry the Yomi-family entries — they are NOT additive on top of an explicit override.

### F5 — `[PII protection: ...]` audit footer on write-path responses (`@mcp-consultant-tools/powerplatform-data`, `@mcp-consultant-tools/azure-devops`)

Beta.3 wrapped `create-record` / `update-record` / `execute-action` / write-path work-item tools through the redaction pipeline so their bodies redact correctly. The audit-trail footer (`[PII protection: N redacted by L1/L2/L3/L4]`) that read-path `query-records` carries was missing on writes — an operator validating "did the pipeline actually fire" saw responses indistinguishable from a no-protection baseline at a glance even when redaction did run.

**`powerplatform-core` `DataService`** — `getRecord`, `createRecord`, `updateRecord`, `executeAction` now embed `piiReport` as a sibling key on the result object (mirrors the `WorkItemService` pattern). Return type changes from `Promise<unknown>` to `Promise<Record<string, unknown>>`. Backwards-compatible for consumers that read individual fields (e.g. SharePoint `validateDocumentLocation`); `piiReport` just appears as an extra key.

**`powerplatform-data` tools** — `read-tools.ts` (`get-record`) and `write-tools.ts` (`create-record`, `update-record`, `execute-action`) destructure `piiReport` off the result and append `formatSummaryFooter(piiReport)` to the response text.

**`azure-devops` work-item-tools.ts** — new `splitPiiReport` helper that extracts `piiReport` from any embed-pattern result. Applied to `get-work-item`, `query-work-items`, `add-work-item-comment`, `update-work-item-comment`, `update-work-item`, `create-work-item`. The corresponding service methods already wrapped `piiReport` since beta.3 — only the tool layer was discarding it.

**Verified end-to-end** via mcp-local-tester against `acmedev.crm.dynamics.com`: `update-record` response now ends with `[PII protection: 6 names + 3 emails + 3 dobs + 2 phones redacted by L2/L3/L4]`; `yomifullname` in the same response renders as `[REDACTED:name:42e629]`; `jobtitle` (the field actually being updated) passes through untouched; no raw `piiReport` key in the JSON body.

### F6 — Locale date format documentation (no code change)

Decision recorded: built-in locale date defaults (`DD-Month-YYYY`, `DD.MM.YYYY` DE/AT, `DD/MM/YYYY` UK, `MM/DD/YYYY` US) **rejected** for the same reason F2 was closed `customPatterns`-only — global string-scanning regex for these formats produces too many false positives at scale (build numbers, version strings, timestamps, GUID fragments). Instead, opt in per-engagement via `PII_CONFIG_PATH` → `regex.customPatterns`, or — preferably — redact via Layer 2 `redactInResponse` where the field name is known.

`docs/documentation/pii-protection.md` gains a new **"Locale date formats — copy-paste recipes"** subsection with a vetted 5-pattern JSON config (English long/short month, German numeric, UK slash, US slash) plus per-pattern caveats: the `(?:19|20)\d{2}` year guard, why `dob-uk-slash` and `dob-us-slash` shouldn't both fire on the same data, and the "Layer 2 first" recommendation. The "Coverage notes" date-regex bullet now points at this section and includes a Yomi-family note describing the new beta.4 defaults.
