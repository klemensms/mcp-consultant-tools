## Overview

v32 is the first production release since v30. It adds two opt-in privacy/compliance subsystems and a new integration, all **off by default** so that any server running on v30 starts unchanged with **no `.mcp.json` edits**:

- An opt-in **PII protection pipeline** — four-layer redaction that prevents personal data from reaching the LLM during MCP tool calls, wired into five MCP servers (introduced across the v31 line).
- An opt-in **PII Audit Logging** subsystem — a tamper-evident, hash-chained audit log over every Dataverse data tool call, with a companion `mcp-audit-cli` (introduced in the v32 line).
- The new **Microsoft Fabric** integration (`@mcp-consultant-tools/fabric`).
- Several bug fixes, including a lookup-bind fix, a `create-record` return-value fix, and a version-reporting fix.

**Opt-in is explicit.** Both the PII pipeline and audit logging stay completely inert unless you set their env vars. There is **no environment-type gating** and no refuse-to-start for a plain upgrade.

> **Note for anyone who tracked the v31 betas:** v31 made `MCP_ENVIRONMENT_TYPE` + `PII_PROTECTION` *mandatory* (the server refused to start without them). v32 relaxed this to pure opt-in — `MCP_ENVIRONMENT_TYPE` is no longer required or gated (it is now advisory only, feeding the "looks unprotected" startup warning). To turn protection on you set `PII_PROTECTION=true`; to leave it off you do nothing.

## Highlights

- **PII protection pipeline (opt-in).** Four layers — `$select` injection, config-based field redaction, regex pattern matching, and NER-based name detection — wired into `powerplatform-data`, `azure-devops`, `azure-sql`, `rest-api`, and `azure-b2c`. Off by default; enable with `PII_PROTECTION=true`.
- **Cross-MCP token correlation (`PII_SESSION_SALT`).** Set the same salt across servers and the same value tokenizes identically everywhere, letting an agent reconcile "same person across systems."
- **Observe-mode.** Run the full pipeline and report what *would* be redacted while returning original data — for validating recall before committing.
- **PII Audit Logging (Phase A, opt-in).** Tamper-evident, GDPR-defensible hash-chained audit log over every `@mcp-consultant-tools/powerplatform-data` tool call, with a companion `mcp-audit-cli` for verification, quarantine, and search. Enable with `MCP_AUDIT_LEVEL=lean|full`.
- **Microsoft Fabric integration.** New `@mcp-consultant-tools/fabric` package — 27 tools across 6 domains plus 2 prompts.
- **No breaking changes.** Upgrading from v30.x requires no `.mcp.json` action; every new subsystem is off until you opt in.

## 🚀 New Features

### PII protection pipeline (`@mcp-consultant-tools/core`, opt-in)

A four-layer redaction pipeline at `packages/core/src/pii/`, shared across each MCP server and its CLI via `context-factory.ts`:

- **Layer 1 — `$select` injection.** Drops configured PII fields from caller-supplied `$select` lists before the query reaches Dataverse, so the data never leaves the source system.
- **Layer 2 — Config-based field redaction.** Replaces values of configured per-entity fields with synthetic tokens `[REDACTED:{type}:{6-char-hex}]`. Token derivation is `truncate(HMAC-SHA256(session_salt, value), 6)` — the same value within one server lifetime yields the same token (cross-call correlation); a restart rolls the salt (privacy hygiene). Walks nested objects, arrays, and OData `@OData.Community.Display.V1.FormattedValue` annotations.
- **Layer 3 — Regex pattern matching.** Built-in patterns for email, international phone, and ISO-format dates of birth; custom patterns configurable. Scans every string value regardless of field name.
- **Layer 4 — NER (compromise.js).** Detects PERSON entities in configured scan-fields plus all OData annotation values. Pure JS, no native deps; validated against German Unicode, English, and mixed-language fixtures.

The pipeline is wired into five MCP servers — `powerplatform-data`, `azure-devops`, `azure-sql`, `rest-api`, `azure-b2c` — on both read and write paths (create/update echoes are redacted, not just queries). Each affected service has a single point of redaction; all other tools route through it.

### Enabling PII protection (opt-in)

Protection is **off by default**. To turn it on, set one env var on the relevant MCP server:

```json
{
  "mcpServers": {
    "PROD-pp-data": {
      "command": "npx",
      "args": ["-y", "--package=@mcp-consultant-tools/powerplatform-data@latest", "mcp-pp-data"],
      "env": {
        "PII_PROTECTION": "true",
        "PII_SESSION_SALT": "<64-char hex from `openssl rand -hex 32`>",
        "POWERPLATFORM_URL": "https://yourorg.crm.dynamics.com",
        "POWERPLATFORM_CLIENT_ID": "...",
        "POWERPLATFORM_CLIENT_SECRET": "...",
        "POWERPLATFORM_TENANT_ID": "..."
      }
    }
  }
}
```

Resolution order for "is the pipeline on" is `PII_CONFIG_PATH file "enabled" ?? PII_PROTECTION ?? false`. Setting nothing keeps it off. There is no production-vs-dev gate — enabling protection is an explicit choice on each server.

### Cross-MCP-server token correlation (`PII_SESSION_SALT`)

By default each server process generates an independent random 32-byte salt, so the same email tokenizes differently across servers. Set `PII_SESSION_SALT` to the **same** 64-char hex string in every server's `env:` block to share a salt — all servers then derive identical tokens for the same input, enabling cross-MCP "same person" analysis. Generate with `openssl rand -hex 32`. Empty string (`""`) or whitespace is treated as unset (falls back to per-process random) — a deliberate "the option exists but I'm not opting in yet" pattern. A non-empty value must be exactly 64 hex chars (32 bytes) or the server refuses to start.

**Tradeoff:** a persistent shared salt gives stronger cross-server correlation but weaker forgetability over time. Rotate at least once per engagement; per-day for sensitive work. Keep it only in `.mcp.json` (which should be gitignored).

### Observe-mode, per-call footer, per-layer toggles

- **Observe-mode (`PII_OBSERVE_MODE=true`)** runs the full pipeline (computing what would be redacted) but returns original data unchanged, with a footer noting `(observe-mode — values not changed)`. Useful for validating recall against real production-shaped responses before committing.
- **Per-call summary footer.** Every redacted response carries a compact line like `[PII protection: 2 emails + 4 names + 2 dobs + 1 phone redacted by L1/L2/L3/L4]` — counts-by-category only, never values.
- **Per-layer toggles** (`l1`–`l4`) are independently switchable via `PII_CONFIG_PATH` JSON, for diagnosing which layer is doing its job.
- **URL-heuristic warning.** When protection is off and the configured environment identifier matches none of `PII_NONPROD_HINTS` (default `dev,uat,training,support,migration,sandbox,test`), a stderr warning fires at startup. This is a safety net, not a gate — the server still starts.

### PII Audit Logging (Phase A, opt-in)

A tamper-evident audit subsystem in `packages/core/src/audit/`: canonical-JSON SHA-256 hash chain, monthly/weekly/daily/size rotation, atomic appends, session-scoped engagement state, and an `auditEmit` wrapper that guarantees audit failures never block tool execution. All pp-data tools record structured, PII-redacted audit entries when enabled. Activated via `MCP_AUDIT_LEVEL=lean|full` (default `off`).

- **`set-audit-engagement` tool (`@mcp-consultant-tools/powerplatform-data`).** Stamps the work-item engagement for a session (pp-data tool count 13 → 14). Only required when audit is enabled at `lean`/`full`.
- **`mcp-audit-cli` (`@mcp-consultant-tools/audit-cli`).** Standalone CLI: `verify` (walk the chain, report OK/BROKEN), `quarantine` (isolate a broken file, reset chain state), `search` (nine filters, `table|json|csv`). On its own independent `0.1.x` track.

### Microsoft Fabric integration (`@mcp-consultant-tools/fabric`)

New package providing MCP access to Microsoft Fabric — MCP server `mcp-fabric` plus CLI `mcp-fabric-cli`. 27 tools across 6 domains (workspaces, capacities, items, OneLake shortcuts, governance domains, tenant-wide admin inventory) and 2 prompts. Entra service-principal auth via `@azure/identity` against the `https://api.fabric.microsoft.com/.default` scope (one token covers both the core `/v1` and admin `/v1/admin` base URLs). Mutations gated behind `FABRIC_ENABLE_WRITE` / `FABRIC_ENABLE_DELETE`. Purely additive — no `.mcp.json` action required for any existing server.

## ✨ Enhancements / Functional Improvements

- **PII protection is opt-in.** `createPiiPipelineFromEnv` / `loadPiiConfig` no longer throw when `PII_PROTECTION` is unset; resolution order is `fileConfig.enabled ?? PII_PROTECTION ?? false`, and there is no environment-type gating. This relaxes the v31-line behaviour (mandatory refuse-to-start) to a clean opt-in. Affects every PII-wired package (`powerplatform-data`, `azure-devops`, `azure-sql`, `azure-b2c`, `rest-api`).
- **PII config — single key per entity.** The redaction config loader expands and lowercases field rules so a single per-entity key drives redaction consistently.
- **Default entity rules** ship for `contact`, `lead`, `account`, `systemuser` (Dataverse) and `b2c-user` (Graph), including the Yomi name family (`yomifirstname`/`yomimiddlename`/`yomilastname`/`yomifullname`) for `contact`, `lead`, and `systemuser`. `PII_CONFIG_PATH` overrides are **not additive** — a custom `fieldRules.contact` carries the full list.

## 🔧 Technical Improvements / Architecture

- **Single point of redaction per package.** Each affected service runs results through the pipeline in one method (`DataService.queryRecords`, `WorkItemService.getWorkItem`/`queryWorkItems`, `QueryService.executeQuery`, `RestApiService.request()`, `UserService.{listUsers,getUser,searchUsers,createUser,updateUser}`); every other tool routes through these.
- **ServiceContext-shared pipeline.** A single `PiiProtectionPipeline` instance is constructed at startup and shared across the MCP server and CLI via `context-factory.ts`.
- **Cache stores unredacted data.** Caches hold raw mapped objects; redaction happens on every return path, preserving correctness across cache hits and salt rotation.
- **Audit module.** `packages/core/src/audit/` — canonical-JSON hashing, rotation, atomic appends, session-scoped engagement state, and the non-blocking `auditEmit` wrapper.
- **Salt confinement.** The session salt lives in a closure (`LoadedPiiContext.getSalt()`) and is never serialised into any report or footer.

## 🧩 Configuration, Metadata & Validation

All PII and audit env vars are **optional**; defaults preserve v30 behaviour (everything off).

**PII protection**

| Env var | Default | What it does |
|---|---|---|
| `PII_PROTECTION` | `false` | Master switch. Set `true` to enable redaction. |
| `PII_SESSION_SALT` | per-process random | 64-char hex (32 bytes). Share the same value across servers for cross-MCP token correlation. Empty/whitespace = unset. Invalid hex/length = refuse-to-start. |
| `PII_OBSERVE_MODE` | `false` | Run the pipeline but return original data; footer reports what *would* be redacted. |
| `PII_CONFIG_PATH` | unset | JSON config with per-layer toggles, per-entity field rules, custom regex, NER scan-fields. Overrides defaults. Unloadable file = refuse-to-start. |
| `PII_NONPROD_HINTS` | `dev,uat,training,support,migration,sandbox,test` | Substrings the URL-heuristic "looks unprotected" warning treats as non-prod. |
| `MCP_ENVIRONMENT_TYPE` | unset | **Advisory only in v32** (no longer a gate). Referenced in the "looks unprotected" warning text. |

**PII Audit Logging**

| Env var | Default | What it does |
|---|---|---|
| `MCP_AUDIT_LEVEL` | `off` | `off` \| `lean` \| `full`. |
| `MCP_AUDIT_CLIENT` | unset | **Required** only when audit is `lean`/`full`. |
| `MCP_AUDIT_OPERATOR` | unset | Optional operator identity stamp. |
| `MCP_AUDIT_PATH` | `./audit-out` | Audit output directory. |

When audit is enabled (`lean`/`full`), a refuse-to-start matrix applies: the server exits with a single stderr line if `MCP_AUDIT_CLIENT` is unset, the audit directory is unwritable, or chain state is corrupted (pointing at `mcp-audit-cli quarantine`). With `MCP_AUDIT_LEVEL` unset/`off`, none of this engages.

## 🐛 Bug Fixes

- **Lookup `@odata.bind` resolution** (`powerplatform-core`, `powerplatform-data`). `DataService` was converting lookup attribute logical names to their `SchemaName` for `@odata.bind` keys; Dataverse navigation properties are actually the lookup attribute's `ReferencingEntityNavigationPropertyName`. Result: every `create-record` / `update-record` with a lookup bind silently failed. The fix queries `ManyToOneRelationships` for the actual nav property (filtering by `ReferencedEntity` for polymorphic lookups, cached per-process), and `get-lookup-target` now returns the correct nav property name. **Behavioural change:** callers that depended on the old (silently broken) `SchemaName` guidance from `get-lookup-target` will see the corrected value — no config action required.
- **`create-record` now returns the new record GUID** (`powerplatform-data`). With `Prefer: return=representation`, Dataverse returns the entity-specific primary key (`contactid`, `accountid`, …) and suppresses the `OData-EntityId` header; the parser now reads `<entity>id` directly instead of returning `N/A`.
- **CLI `--version` and MCP server version now report the real package version** (`core`). `createCliProgram` and `createMcpServer` derive the version from the running package's `package.json` instead of a hardcoded string, so they stay in lockstep with releases. Previously CLIs reported stale versions (e.g. `27.0.0`) and servers reported `1.0.0`. No tool behaviour changes.
- **Pre-commit hook false positives** (`scripts/hooks/pre-commit`). `.env.{example,template,sample,dist}` are now allowed while `.env`/`.env.local`/`.env.prod` stay hard-blocked; `package-lock.json` sha512 integrity hashes are excluded from the long-string scan.

## Migration

**Upgrading from v30.x requires no `.mcp.json` changes.** Every new subsystem is off until you opt in.

Optional, if you want the new capabilities:

1. **Enable PII protection** on any of `mcp-pp-data`, `mcp-ado`, `mcp-sql`, `mcp-rest-api`, `mcp-azure-b2c`: add `PII_PROTECTION=true` to its `env:` block. (Optional: `PII_OBSERVE_MODE=true` first to dry-run; the footer reports what *would* be redacted.)
2. **Correlate tokens across servers:** generate one salt with `openssl rand -hex 32` and set the same `PII_SESSION_SALT` on every server.
3. **Enable audit logging** on `mcp-pp-data`: set `MCP_AUDIT_LEVEL=lean|full` and `MCP_AUDIT_CLIENT`. Verify the chain with `mcp-audit-cli verify`.
4. **Add the Fabric server** if you need it (`@mcp-consultant-tools/fabric`, `mcp-fabric`).

Servers you don't opt in on behave exactly as on v30.
