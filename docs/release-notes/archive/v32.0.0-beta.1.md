# Release Notes: v32.0.0-beta.1

**Date:** 2026-05-03
**Branch:** `release/31.0`
**Status:** Published to beta

> Per-iteration agent-level detail. The user-facing single source of truth is [`v32.0.0.md`](v32.0.0.md).

## Overview

Phase A of the PII Audit Logging programme. Lands a tamper-evident, GDPR-defensible audit log over every Dataverse MCP tool call (`@mcp-consultant-tools/powerplatform-data`): a new `packages/core/src/audit/` subsystem (~1000 lines, 53 vitest cases), a new `set-audit-engagement` MCP tool, all 13 existing pp-data tools wrapped in `auditEmit`, PII redaction applied to input parameters before recording, a new `@mcp-consultant-tools/audit-cli` binary (`mcp-audit-cli verify | quarantine | search`), and 12 documentation surfaces refreshed.

> **⚠️ Breaking change.** `MCP_AUDIT_LEVEL` is now a REQUIRED env var on every Phase A surface (currently just `@mcp-consultant-tools/powerplatform-data`). Servers `process.exit(1)` at startup if it is unset or fails the refuse-to-start matrix. Existing `.mcp.json` configurations from beta.4 will fail to boot until updated. See **Migration** below for copy-paste config blocks.

Out of scope this iteration: the multi-target sync layer, HMAC-signed central uploader, server-side retention enforcement, and network-offline buffering — all reserved for Phase B in a separate session. Phase A's on-disk schema is forward-compatible (additive fields, no migrations needed when Phase B lands).

## Migration

Pick the path that matches the environment, edit each affected `.mcp.json`, restart the MCP server.

### Path 1 — No audit needed (dev / training / personal sandbox)

```json
"env": {
  "MCP_AUDIT_LEVEL": "off",
  "POWERPLATFORM_URL": "...",
  "POWERPLATFORM_CLIENT_ID": "...",
  "POWERPLATFORM_CLIENT_SECRET": "...",
  "POWERPLATFORM_TENANT_ID": "..."
}
```

`level=off` boots cleanly with no audit chain, no engagement requirement, and zero on-disk writes. This is the drop-in equivalent of beta.4 behaviour.

### Path 2 — UAT / pseudonymised data (`lean`)

```json
"env": {
  "MCP_AUDIT_LEVEL": "lean",
  "MCP_AUDIT_CLIENT": "<client-name>",
  "MCP_AUDIT_OPERATOR": "<directory-id>",
  "MCP_AUDIT_PATH": "./audit-out",
  "MCP_ENVIRONMENT_TYPE": "uat",
  "PII_PROTECTION": "true",
  "POWERPLATFORM_URL": "...",
  "POWERPLATFORM_CLIENT_ID": "...",
  "POWERPLATFORM_CLIENT_SECRET": "...",
  "POWERPLATFORM_TENANT_ID": "..."
}
```

`MCP_AUDIT_OPERATOR` is optional (operator fingerprint is captured automatically); set it when the directory identity should be recorded alongside. `MCP_AUDIT_PATH` defaults to `./audit-out` if omitted. Records contain redaction reports + tool input/output structure but NOT raw payload data.

### Path 3 — Production / full payloads (`full`)

Same as Path 2 but `MCP_AUDIT_LEVEL=full`. Records additionally include `payload.input` and `payload.output` (each pre-redacted by the PII pipeline). Use only against production environments where the operator is authorised to see real PII.

### Refuse-to-start matrix (server exits 1 if any of these hold)

- `MCP_ENVIRONMENT_TYPE=production` AND `MCP_AUDIT_LEVEL` unset.
- `MCP_ENVIRONMENT_TYPE=production` AND `MCP_AUDIT_LEVEL=off`.
- `MCP_AUDIT_LEVEL=lean|full` AND `MCP_AUDIT_CLIENT` unset.
- `MCP_AUDIT_LEVEL=lean|full` AND audit base directory unwritable.
- `MCP_AUDIT_LEVEL=lean|full` AND chain state corrupted on disk (message references `mcp-audit-cli quarantine`).

Each failure prints a single user-facing error line to stderr naming the missing/invalid setting before the exit.

## Changes Implemented

### Audit subsystem foundation (`@mcp-consultant-tools/core`)

New module tree at `packages/core/src/audit/` orthogonal to the existing `utils/audit-logger.ts` operational logger (which remains untouched). Components:

- `types.ts` — 16 type/interface declarations covering `AuditConfig`, `AuditOperator`, `AuditAuth`, `AuditEngagement`, `AuditEnvironment`, `AuditToolCall`, `AuditResult`, `AuditRedaction`, `AuditPayload`, `AuditRecord`, `ChainState`, `AuditEmitOptions`. `AuditLevel = 'off' | 'lean' | 'full'`. `AuditEnvironmentType = 'production' | 'uat' | 'dev'`. `AuditAuth.principalType` widened to include `'user-interactive'` (Power Platform interactive browser auth, previously mislabelled as `'user-impersonation'`).
- `errors.ts` — Four error classes: `AuditRefuseToStartError` (config validation / startup, server exits), `AuditEngagementUnsetError` (refuse-to-execute mid-session), `AuditWriteError` (write failure mid-session, surfaced via `safeEmit`), `AuditChainError` (chain integrity violation, requires `mcp-audit-cli quarantine`).
- `operator.ts` — Captures the operator fingerprint (host + user) + optional `MCP_AUDIT_OPERATOR` identity.
- `config.ts` — `loadAuditConfig()` enforces the refuse-to-start matrix with byte-exact user-facing error messages. Threads `environment.type` through.
- `chain.ts` — Canonical-JSON `canonicalize()` + `computeRecordHash()` (SHA-256). `ZERO_HASH` lives here as the chain's natural owner; deduplicated from `types.ts` at Task 12 to avoid the TS2308 collision when both modules re-export through the package barrel.
- `rotation.ts` — `nextRotationFilename()` for `monthly` (default), `weekly` (ISO week-year derivation), `daily`, and `{ sizeBytes }` rotation strategies.
- `storage.ts` — `path.dirname`-aware mkdir, atomic `fs.rename` with unique tmp suffix, append helper, sentinel writer.
- `session.ts` — `AuditSessionStore` with engagement freezing semantics (re-setting the same engagement is a no-op; switching engagements emits a `contextChange` record).
- `pipeline.ts` — `AuditPipeline` Promise-chained internal write queue. Symmetric `level=off` short-circuit; ordering comments document the sequence guarantees; defensive throw on engagement-unset path.
- `emit.ts` — `auditEmit()` wrapper + `safeEmit()`. **Phase A guarantee: audit failures NEVER block tool execution.** Every emit path is wrapped in try/catch — failures log to stderr but never propagate to the tool result.
- `index.ts` — Public barrel. `SetEngagementResult` exported alongside the rest.

53 vitest cases cover the subsystem (1 sanity + 3 operator + 9 config + 7 chain + 5 rotation + 7 storage + 8 session + 7 pipeline + 6 emit). Vitest 2.1.x introduced as a new dev-dep on `packages/core` (Phase 0 of the plan); `tsc` emit excludes `src/**/__tests__/**` so test files do not ship in the published build.

### `set-audit-engagement` MCP tool (`@mcp-consultant-tools/powerplatform-data`)

New tool. Tool count: 13 → **14**. Schema: `workItemIds: string[]` (required, min 1, max 50, each ≤ 50 chars) + `reason?: string` (optional, max 500 chars). Calling it stamps the engagement on the `AuditSessionStore` and emits a context-change record (or a no-op note if the engagement is identical to the current one). Every other audit-emitting tool will fail with a clear `AuditEngagementUnsetError` until `set-audit-engagement` has been called once per process.

The tool itself emits regardless of whether engagement was set previously — i.e. the very first audit record on a new chain is the engagement-setting record.

### All 13 pp-data tools wrapped in `auditEmit`

**Read tools** (`tools/read-tools.ts`): `query-records`, `get-record`, `count-records`, `get-entity-metadata`, `get-lookup-target`, `get-flow-runs`, `get-flow-run-details`. Each handler captures input/output redaction reports from the PII pipeline and emits `outputRedaction` to `auditEmit`. `recordCount` semantics documented inline (`query-records` reports `value.length`; `count-records` reports the API-returned `@odata.count`; non-list reads omit the field).

**Write tools** (`tools/write-tools.ts`): `create-record`, `update-record`, `delete-record`, `execute-action`, `associate-records`, `disassociate-records`. Synthetic-shape comments document the record-count semantics for void-returning tools.

The MCP SDK doesn't thread Zod inference through `server.tool(...)` so each handler keeps its inline TypeScript type annotations (e.g. `{ entityName: string; query: string; ... }`) even though they duplicate the Zod schema — TS7031 errors otherwise.

### PII redaction on tool input parameters (Task 18)

Every audit-emitting handler pre-redacts `params` through the PII pipeline before `auditEmit` records `tool.params`. New `PowerPlatformService.piiPipeline` getter exposes the pipeline instance. The 13 pp-data tools all use this pre-redaction step so a stored audit record's `tool.params` field never contains raw PII even at `MCP_AUDIT_LEVEL=full`.

### `@mcp-consultant-tools/audit-cli` (new package, binary: `mcp-audit-cli`)

New monorepo package at `packages/audit-cli/`. Initial version `0.1.0` (deliberately decoupled from the 32.x train so the CLI can iterate independently). Depends on `@mcp-consultant-tools/core` + `commander@^14.0.3`. Three subcommands:

- `mcp-audit-cli verify <chain-dir>` — Walks the chain across rotated files, reports OK / BROKEN with the offending seq + file, exits 2 on chain break. `--quiet` suppresses per-record output for batch use.
- `mcp-audit-cli quarantine <chain-dir> --reason <text>` — Renames the broken file to `<name>.quarantined-<timestamp>`, writes a sentinel record on the new chain (inheriting `environment.type` from the last parseable record — falls back to `'dev'`, never `'unknown'`), resets `.chain-state`. Server can then restart cleanly on the new chain.
- `mcp-audit-cli search <chain-dir>` — Nine filter options (operator, client, engagement, work-item, tool, entity, since, until, principal-type) with `--format table|json|csv`. Defensive parse + null safety so a partially-corrupt file produces a usable result instead of a crash.

`mcp-audit-cli --version` → `0.1.0`. CLI is published alongside the rest of the workspace under the `@mcp-consultant-tools` scope.

## Known Issues

- **`tests/audit-smoke/` and `tests/audit-demo/` (Task 30 — pending) are scaffold-only this beta.** Both depend on MCPTest credentials being substituted into the committed `.mcp.json` placeholders. Once the operator runs them end-to-end, the resulting `audit-out/` JSONL files validate the refuse-to-execute, refuse-to-start, hash-chain verify-OK, deliberate corruption + quarantine, and search-CLI scenarios from the spec's acceptance checklist.
- **Demo runner (`tests/pii-demo/run.mjs`) still broken on rotated `MCPTest` credential** since beta.1 — the in-session 6-MCP approach via `.mcp.json` remains the workaround; `run.mjs` is dormant. Carry-over from beta.4 — not a 32.x regression.
- **The pre-existing operational logger** at `packages/core/src/utils/audit-logger.ts` (and the pp-core `utils/auditLogger.ts` used by `PluginDeploymentService` / `WorkflowManagementService`) is **orthogonal** to this Phase A subsystem. Phase A audit lives at `packages/core/src/audit/`. The two systems do NOT share state. Per the spec's Open Question #3, renaming the older logger to `customizationAuditLogger` is deferred to a future sweep.
- **Phase A is `powerplatform-data`-only.** Other Dataverse-adjacent surfaces (`powerplatform-customization`, `powerplatform-core` direct usage, `azure-devops` work-item PII paths) do not yet emit audit records. Tracked in the programme plan at `docs/programmes/pii-and-audit/00-master-plan.md` for Phase B + later phases.
- **`MCP_AUDIT_OPS_TARGETS`** env var is read in this beta but its non-`local` values are ignored. Phase B activates the multi-target sync layer.
