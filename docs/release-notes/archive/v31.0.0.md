## Overview

v31 introduces a **PII protection pipeline** that prevents personal data from reaching the US-hosted LLM during MCP tool calls against client production environments. A four-layer redaction pipeline lives in `@mcp-consultant-tools/core` and is wired into five MCP servers:

- `powerplatform-data`
- `azure-devops`
- `azure-sql`
- `rest-api`
- `azure-b2c`

The pipeline drives the organisational AI usage policy's "Conditional" verdict to achievable for L1–L4 columns. Phase 6 (the audit logger that takes the verdict to fully unconditional) is a separately scoped session deferred from v31.

## Highlights

- A four-layer PII redaction pipeline (`$select` injection, config-based field redaction, regex pattern matching, NER-based name detection) wired into five MCP servers.
- A refuse-to-start contract (`MCP_ENVIRONMENT_TYPE` + `PII_PROTECTION` both required, production refuses `false`) that makes it impossible to accidentally point a production environment at the LLM with redaction off.
- Optional cross-MCP-server token correlation via `PII_SESSION_SALT` — set the same salt across servers and tokens line up, enabling agents to reconcile "same person across systems."
- Observe-mode for validating recall against real production-shaped responses without committing to redaction yet.
- Per-call human-readable summary footer on every redacted response (`[PII protection: 2 emails + 4 names + 2 dobs redacted by L2/L3/L4]`).
- Lookup-bind fix in `powerplatform-data` — `create-record` and `update-record` calls with `@odata.bind` now succeed for both polymorphic and non-polymorphic lookups (a long-standing silent failure).
- **Write-path redaction (beta.3).** `create-record`, `update-record`, `execute-action` (powerplatform-data), `createWorkItem`/`updateWorkItem`/`addWorkItemComment`/`updateWorkItemComment` (azure-devops), `sql-execute-sproc`/`sql-execute-unrestricted` (azure-sql) now redact response bodies. Beta.1/.2 only ran the pipeline on read paths; create/update echoes were leaking PII back through `Prefer: return=representation` and equivalent.
- **OData lookup display annotations now reach the pipeline (beta.3).** PowerPlatform reads request `Prefer: odata.include-annotations="*"`, so `_primarycontactid_value@OData.Community.Display.V1.FormattedValue: "Maria Schmidt"` (and equivalents on every lookup field) appear in responses and are redacted by Layer 4 NER. Beta.1/.2 omitted the header so these annotations were absent from responses entirely — Layer 4 on lookup names was a no-op in production.
- **Yomi-family fields redacted by default + write-path audit footer (beta.4).** Default Layer 2 rules for `contact`, `lead`, and `systemuser` now include the Yomi family (`yomifirstname`, `yomimiddlename`, `yomilastname`, `yomifullname`); `lead` gains a default rule set (previously empty). `update-record` / `create-record` / `execute-action` (powerplatform-data) and `create-work-item` / `update-work-item` / `*-comment` (azure-devops) responses now emit the same `[PII protection: ...]` audit footer that read-path query tools carry — the bodies were already redacted in beta.3, only the audit-trail line was missing.
- **Microsoft Fabric integration (beta.5).** New `@mcp-consultant-tools/fabric` package — MCP server `mcp-fabric` plus CLI `mcp-fabric-cli`. 27 tools across 6 domains (workspaces, capacities, items, OneLake shortcuts, governance domains, tenant-wide admin inventory) and 2 prompts. Entra service-principal auth via `@azure/identity` against the `https://api.fabric.microsoft.com/.default` scope; one token covers both the core (`/v1`) and admin (`/v1/admin`) base URLs. Mutations gated behind `FABRIC_ENABLE_WRITE` / `FABRIC_ENABLE_DELETE`. **Not a breaking change** — fabric is a brand-new package, no `.mcp.json` action is required for any existing server. The meta package re-publishes (`31.0.0-beta.4 → 31.0.0-beta.5`) only to pick up the new fabric registration in its bundled startup.

## ⚠️ Upgrade Notes / Breaking Changes

### Action required if you use any of these five MCP servers

If your `.mcp.json` references **any** of `mcp-pp-data`, `mcp-ado`, `mcp-sql`, `mcp-rest-api`, or `mcp-azure-b2c`, **the server will refuse to start on v31** until you add two new env vars to its `env:` block:

| Env var | Required values | What it does |
|---|---|---|
| `MCP_ENVIRONMENT_TYPE` | `production` \| `uat` \| `dev` | The gate. Production rejects `PII_PROTECTION=false`. UAT and dev allow either. |
| `PII_PROTECTION` | `true` \| `false` | The switch. Must be set explicitly — there is no env-type-based defaulting. |

**Refuse-to-start matrix:**

| Environment | `PII_PROTECTION` unset | `=false` | `=true` |
|---|---|---|---|
| `production` | refuse to start | refuse to start | enabled |
| `uat` | refuse to start | disabled | enabled |
| `dev` | refuse to start | disabled | enabled |

When the server refuses to start, it exits with code 1 and prints a stderr message naming the missing/invalid flag.

### Optional env vars (no action required, opt-in)

| Env var | Default | What it does |
|---|---|---|
| `PII_OBSERVE_MODE` | `false` | Run the pipeline but return original data unchanged. Footer reports what *would* have been redacted. Useful for validating recall before committing. |
| `PII_SESSION_SALT` | per-process random | 64-char hex string (32 bytes). Set the **same** value across all MCP servers in your `.mcp.json` to enable cross-MCP token correlation. Generate with `openssl rand -hex 32`. **Empty string (`""`) is treated as unset** — falls back to per-process random salt. Useful if you want the variable visible in your config to remember the option exists without opting in yet. |
| `PII_CONFIG_PATH` | unset | Path to a JSON config file with per-layer toggles, per-entity field rules, custom regex, and NER scan-fields. Overrides default rules. |
| `PII_NONPROD_HINTS` | `dev,uat,training,support,migration,sandbox,test` | Comma-separated substrings the URL-heuristic warning treats as "looks like non-prod." |

### Other behavioural changes

- **`get-lookup-target` (powerplatform-data)** previously instructed callers to use `SchemaName` for `@odata.bind`. It now correctly returns the actual `ReferencingEntityNavigationPropertyName`. This is a **fix**, but it is breaking for any caller that depended on the (silently broken) old guidance. See [Bug Fixes](#-bug-fixes).
- **Constructor signatures** of the affected services (`PowerPlatformService`, `DataService`, `WorkItemService`, `QueryService`, `RestApiService`, `UserService` in azure-b2c) gain an optional trailing `piiPipeline?: PiiProtectionPipeline` argument. Existing callers with prior arities continue to work.
- **Response shapes** of the affected services gain an optional `piiReport?: PipelineReport` field. Callers ignoring the field are unaffected.

## 🚀 New Features

### PII Protection Pipeline (`@mcp-consultant-tools/core`)

A four-layer pipeline at `packages/core/src/pii/`:

- **Layer 1 — `$select` injection.** Drops configured PII fields from caller-supplied `$select` lists before the query is sent to Dataverse. Data never leaves the source system.
- **Layer 2 — Config-based field redaction.** Replaces values of configured per-entity fields with synthetic tokens `[REDACTED:{type}:{6-char-hex}]`. Token derivation: `truncate(HMAC-SHA256(session_salt, value), 6)`. Same value within one server lifetime → same token (cross-call correlation). Server restart → fresh salt → fresh tokens (privacy hygiene). Walks nested objects, arrays, and OData `@OData.Community.Display.V1.FormattedValue` annotations.
- **Layer 3 — Regex pattern matching.** Built-in patterns for email, international phone, and ISO-format dates of birth. Custom patterns configurable. Scans every string value regardless of field name — catches PII embedded in free text.
- **Layer 4 — NER (compromise.js).** Detects PERSON entities in configured scan-fields (`description`, `notetext`, `comments`, `body`, `displayName`, `System.Description`, `System.Title`, `System.History`, `Microsoft.VSTS.TCM.ReproSteps`, `Microsoft.VSTS.TCM.SystemInfo`, `Microsoft.VSTS.Common.AcceptanceCriteria`, `text`) plus all OData annotation values. Pure JS, no native deps. Validated against German Unicode ("Klaus Müller"), English baseline, and mixed-language fixtures.

### Cross-MCP-server token correlation (`PII_SESSION_SALT`)

By default, each MCP server process generates an independent random 32-byte salt at startup, so the same email tokenizes differently across servers. The agent cannot reconcile "same person across systems" — which blocks cross-MCP analysis tasks.

Set `PII_SESSION_SALT` to a 64-character hex string in **every** MCP server's `env:` block in `.mcp.json` to share a salt. All servers then derive identical tokens for the same input value.

```bash
openssl rand -hex 32   # generates a 64-char hex salt
```

**Validation rules:**
- A non-empty value must contain hex characters only (`0-9`, `a-f`, `A-F`) and decode to exactly 32 bytes (i.e. exactly 64 hex characters). Anything else → refuse-to-start.
- Unset, empty string (`""`), or whitespace-only → fall back to per-process random salt (no error). This is the deliberate "I see the option exists but I'm not opting in yet" pattern — leave the key present in `.mcp.json` with an empty value as a visible reminder.

**Tradeoff:** persistent shared salt = stronger correlation across servers, weaker forgetability across time. Rotate at minimum once per engagement; per-day for sensitive work. Do not persist outside `.mcp.json` (which itself should be gitignored).

### Refuse-to-start contract

Documented in [⚠️ Upgrade Notes](#-upgrade-notes--breaking-changes). The server refuses to start with a loud stderr message and exit code 1 when:
- `PII_PROTECTION` is unset (any environment type), or
- `MCP_ENVIRONMENT_TYPE=production` and `PII_PROTECTION=false`, or
- `PII_CONFIG_PATH` is set but the file fails to load, or
- `PII_SESSION_SALT` is set but invalid (non-hex / wrong length).

UAT and dev allow `PII_PROTECTION=false` — many UAT environments hold anonymized data and turning the pipeline off there is a legitimate operational choice. No break-glass for production.

### URL-heuristic warning

When the pipeline ends up disabled (`PII_PROTECTION=false` in `uat`/`dev`), the loader checks the configured environment identifier against `PII_NONPROD_HINTS`. If none match, a stderr warning fires at startup. Server still starts — this is a heuristic safety net, not a gate. Catches the failure mode where a consultant copy-pastes a dev `.mcp.json` and swaps in a production URL while leaving the env-type label as `dev`.

Identifier source per package: `powerplatform-data` uses `POWERPLATFORM_URL`; `azure-devops` uses `AZUREDEVOPS_ORGANIZATION` (the host `dev.azure.com` is intentionally excluded so it doesn't always match `dev`); `azure-sql` uses `AZURE_SQL_SERVER` (or first server in `AZURE_SQL_SERVERS`); `rest-api` uses `REST_BASE_URL`; `azure-b2c` uses `AZURE_B2C_TENANT_ID`.

### Per-call summary footer

Every redacted MCP response is followed by a compact human-readable footer like `[PII protection: 2 emails + 4 names + 2 dobs + 1 phone redacted by L1/L2/L3/L4]`. The agent sees what was denied, the consultant sees the same line in their Claude Code transcript, and counts-by-category leak only structural information (never values). The orchestrator emits a structured per-layer report (`PipelineReport`) consumed by the footer; the same report will power the deferred `pii-explain-last-call` tool and CLI `--redaction-diff` view in v1.5.

### Observe-mode

`PII_OBSERVE_MODE=true` runs the full pipeline (computing what would be redacted) but returns the original data unchanged. Footer notes `(observe-mode — values not changed)`. Useful for validating recall against real production-shaped responses before committing to redaction behaviour.

### Per-layer toggles

Each of `l1`, `l2`, `l3`, `l4` is independently switchable via `PII_CONFIG_PATH` JSON. Useful for diagnosing which layer is or isn't doing its job during iteration:

```json
{
  "enabled": true,
  "layers": { "l1": true, "l2": true, "l3": false, "l4": true }
}
```

### Default entity rules

Pre-shipped defaults in `defaultFieldRules()` (beta.4 — the Yomi family was added in beta.4 to close a leak surfaced by the demo regen on `update-record` of a contact whose computed `yomifullname` was being returned raw):

| Entity | Redacted in response | Excluded from `$select` |
|---|---|---|
| `contact` (Dataverse) | `firstname`, `lastname`, `middlename`, `fullname`, `yomifirstname`, `yomimiddlename`, `yomilastname`, `yomifullname`, `emailaddress1`, `emailaddress2`, `emailaddress3`, `mobilephone`, `telephone1`, `telephone2`, `telephone3`, `birthdate` | (none) |
| `lead` (Dataverse, **new in beta.4**) | `firstname`, `lastname`, `middlename`, `fullname`, `yomifirstname`, `yomimiddlename`, `yomilastname`, `yomifullname`, `emailaddress1`, `emailaddress2`, `emailaddress3`, `mobilephone`, `telephone1`, `telephone2`, `telephone3` | (none) |
| `account` (Dataverse) | `emailaddress1`, `emailaddress2`, `emailaddress3`, `telephone1`, `telephone2`, `telephone3` | (none) |
| `systemuser` (Dataverse) | `fullname`, `firstname`, `lastname`, `middlename`, `yomifirstname`, `yomimiddlename`, `yomilastname`, `yomifullname`, `internalemailaddress`, `mobilephone` | (none) |
| `b2c-user` (Graph) | `givenName`, `surname`, `displayName`, `mail`, `otherMails`, `mobilePhone` | (none — L1 inactive for B2C) |

Borderline B2C fields (`streetAddress`, `city`, `postalCode`, `country`, `jobTitle`) are NOT in defaults — opt-in via `PII_CONFIG_PATH` if your client treats these as PII.

**`PII_CONFIG_PATH` overrides are not additive.** If you ship a custom config that overrides `fieldRules.contact.redactInResponse`, your override carries the full list — the Yomi family is not merged on top. Either (a) carry the full list, or (b) leave `fieldRules.contact` unset in your config and override only the entities that need different rules.

## 🔧 Technical Improvements / Architecture

- **Single point of redaction per package.** Each affected service has one method that runs results through the pipeline (`DataService.queryRecords`, `WorkItemService.getWorkItem`/`queryWorkItems`, `QueryService.executeQuery`, `RestApiService.request()`, `UserService.{listUsers,getUser,searchUsers,createUser,updateUser}`). All other tools call through these — no per-tool redaction code.
- **ServiceContext-shared pipeline.** A single `PiiProtectionPipeline` instance is constructed at server startup and shared across the MCP server and the CLI via `context-factory.ts`. Identical wiring on both surfaces.
- **Eager construction with refuse-to-start.** Pipeline is built before any tool registration — the server cannot reach a state where it accepts tool calls without honouring the contract.
- **Cache stores unredacted data.** B2C `usersCache` (and equivalents) hold raw mapped objects; redaction happens on every return path. Preserves correct behaviour across cache hits and across `PII_SESSION_SALT` rotation.

## 🐛 Bug Fixes

### Lookup `@odata.bind` resolution (powerplatform-core, powerplatform-data)

`packages/powerplatform-core/src/services/DataService.ts` was converting lookup attribute logical names to the attribute's `SchemaName` (e.g. `primarycontactid` → `PrimaryContactId`) for `@odata.bind` keys. Dataverse navigation properties are actually the lookup attribute's logical name (per `ReferencingEntityNavigationPropertyName` in `ManyToOneRelationships` metadata), not the SchemaName. Result: every `create-record` / `update-record` call with a lookup bind silently failed with *"An undeclared property 'X' which only has property annotations in the payload but no property value was found."*

Fix: query `ManyToOneRelationships` for the actual nav property name; for polymorphic lookups, filter by `ReferencedEntity` to disambiguate. Cached per-process to avoid repeated metadata calls. The `get-lookup-target` tool now returns the correct nav property name and the corrected wording (`@odata.bind` requires the navigation-property name, NOT the SchemaName).

### Pre-commit hook false positives (`scripts/hooks/pre-commit`)

- `.env.example` was blocked by regex `\.env($|\.)`. The hook now allows `.env.{example,template,sample,dist}` while still hard-blocking `.env`, `.env.local`, `.env.prod`, etc.
- `package-lock.json` long-string scan flagged sha512 integrity hashes (88-char base64 with `~`/`+`/`/`). Now excluded wholesale via `:(exclude)package-lock.json` `:(exclude)**/package-lock.json` pathspecs.

## What's NOT in v31 (deferred)

- **Phase 6 (audit and compliance logging).** Separate scoping session pending. Decision banner: option (a) — metadata + counts only, no PII at rest. Until Phase 6 ships, the organisational AI usage policy should not authorise enterprise-tier external LLMs against production data via the redaction pipeline alone — the pipeline is the technical mitigation; the audit log is what makes it defensible.
- **Layer 5 (local LLM safety net).** Deferred to v2 alongside the deployment-topology decisions for the model host (PoC localhost / SI-managed model host / client-tenant Azure VM).
- **`pii-explain-last-call` MCP tool and `--redaction-diff` CLI flag.** Deferred to v1.5. The structured per-layer report that powers them is built today; the operator surface comes later.
- **Per-client config templates** beyond the defaults plus `PII_CONFIG_PATH` overrides — v1.5+.
- **Auto-detection of PII-candidate fields** from Dataverse metadata (e.g. fields of type Email/Phone) — v1.5+.
- **Textual-date detection** (e.g. "12 March 1985" in free text). The ISO-format DOB regex catches structured dates; textual dates are a Layer 4 enhancement candidate (`compromise.js` has `dates()` extraction; opt-in for v1.5).
- **Nested-object Layer 2 walking** for ADO identity objects (`System.AssignedTo`, etc.). Currently L3 catches the email-formatted `uniqueName` and L4 catches the `displayName`; explicit Layer 2 rules with nested-path support are a v1.5 enhancement.
- **PowerPlatform packages other than `powerplatform-data`** (read-only `powerplatform`, `powerplatform-customization`) — they don't use `DataService`, their tools return metadata not records, and metadata responses don't carry PII.
- **B2C `GroupService`.** B2C group `displayName`/`description` aren't person PII. If a future client carries person names in group fields, wiring is the same pattern as `UserService`.

## Migration

If you're upgrading from v30.x:

1. **Identify which of the five affected servers you run** (`mcp-pp-data`, `mcp-ado`, `mcp-sql`, `mcp-rest-api`, `mcp-azure-b2c`).
2. For each one, add `MCP_ENVIRONMENT_TYPE` and `PII_PROTECTION` to its `env:` block in `.mcp.json`. See the [worked example](#worked-example-mcpjson-for-a-production-engagement) above.
3. (Optional) For cross-MCP correlation, generate one salt with `openssl rand -hex 32` and paste the same value into `PII_SESSION_SALT` for every server in your `.mcp.json`.
4. (Optional) For dry-run validation against real production data, set `PII_OBSERVE_MODE=true` first and inspect the per-call summary footers before flipping to `false`.
5. Servers not in the affected five list (`mcp-pp`, `mcp-pp-custom`, `mcp-figma`, `mcp-spo`, etc.) require no `.mcp.json` changes — their version bumps for workspace lockstep only.
