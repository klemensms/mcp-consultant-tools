# Release Notes: v31.0.0-beta.1

**Date:** 2026-04-27
**Branch:** `release/31.0`
**Status:** Beta Testing

## Overview

PII protection v1 — a four-layer redaction pipeline that prevents personal data from reaching the US-hosted LLM during MCP tool calls against client production environments. Layers 1-4 are in (`$select` injection, config-based field redaction, regex pattern matching, NER-based name detection); Layer 5 (local LLM safety net) is deferred to v2.

The pipeline lives in `@mcp-consultant-tools/core` and is wired into `powerplatform-data` (via `DataService.queryRecords`), `azure-devops` (via `WorkItemService`), `azure-sql` (via `QueryService.executeQuery`), and `rest-api` (via `RestApiService.request()`). One leverage point per package, single ServiceContext-shared pipeline instance.

Drives the organisational AI usage policy's "Conditional" verdict to achievable for L1-4 columns. Phase 6 (audit logger) is a separate scoped session before that verdict becomes fully unconditional.

## Breaking Changes

- **`PowerPlatformService` constructor (powerplatform-data)** — third optional argument `piiPipeline?: PiiProtectionPipeline`. Existing callers passing only `(config)` or `(config, authProvider)` continue working.
- **`DataService` constructor (powerplatform-core)** — second optional argument `piiPipeline?: PiiProtectionPipeline`.
- **`WorkItemService` constructor (azure-devops)** — second optional argument `piiPipeline?: PiiProtectionPipeline`.
- **`QueryService` constructor (azure-sql)** — second optional argument `piiPipeline?: PiiProtectionPipeline`.
- **`RestApiService` constructor (rest-api)** — second optional argument `piiPipeline?: PiiProtectionPipeline`.
- **`DataService.queryRecords` return shape** — added optional `piiReport?: PipelineReport`. Callers ignoring the field are unaffected.
- **`SqlApiCollectionResponse<T>`** — added optional `piiReport?: PipelineReport`.
- **`RequestResult` (rest-api)** — added optional `piiReport?: PipelineReport`.
- **`get-lookup-target` tool guidance** — previously told callers to use `SchemaName` for `@odata.bind` (e.g. `PrimaryContactId`); now correctly returns the actual `ReferencingEntityNavigationPropertyName` (e.g. `primarycontactid`). The old guidance silently broke `create-record` and `update-record` calls with lookup binds.

## New Features

### PII Protection Pipeline (`@mcp-consultant-tools/core`)

A 4-layer pipeline at `packages/core/src/pii/`:

- **Layer 1 — `$select` injection.** Drops configured PII fields from caller-supplied `$select` lists before the query is sent to Dataverse. Data never leaves the source system. Q5.1 decision: drops silently.
- **Layer 2 — Config-based field redaction.** Replaces values of configured per-entity fields with synthetic tokens `[REDACTED:{type}:{6-char-hex}]`. Token derivation: `truncate(HMAC-SHA256(session_salt, value), 6)`. Same value within one server lifetime → same token (cross-call correlation, Q1). Server restart → fresh salt → fresh tokens (privacy hygiene). Walks nested objects, arrays, OData `@OData.Community.Display.V1.FormattedValue` annotations.
- **Layer 3 — Regex pattern matching.** Built-in patterns for email, phone (international), and ISO-format dates of birth. Configurable custom patterns. Scans every string value regardless of field name — catches PII embedded in free text.
- **Layer 4 — NER (compromise.js).** Detects PERSON entities in configured scan-fields (`description`, `notetext`, `comments`, `body`, `displayName`, `System.Description`, `System.Title`, `System.History`, `Microsoft.VSTS.TCM.ReproSteps`, `Microsoft.VSTS.TCM.SystemInfo`, `Microsoft.VSTS.Common.AcceptanceCriteria`, `text`) plus all OData annotation values. Pure JS (compromise.js, ~700KB), no native deps. Validated against German Unicode ("Klaus Müller"), English baseline ("John Smith"), and mixed-language fixtures.

### Refuse-to-start contract (Q3 decision, refined)

Both `MCP_ENVIRONMENT_TYPE` and `PII_PROTECTION` are required to be set explicitly — there is no env-type-based defaulting. `MCP_ENVIRONMENT_TYPE` is the *gate* (production rejects `false`); `PII_PROTECTION` is the *switch*. The server refuses to start with a loud stderr message and exit code 1 when:

- `PII_PROTECTION` is unset (any environment type), or
- `MCP_ENVIRONMENT_TYPE=production` and `PII_PROTECTION=false` (production never permits raw data), or
- `PII_CONFIG_PATH` is set but the file fails to load.

UAT and dev allow `PII_PROTECTION=false` — many UAT environments hold anonymized data and turning the pipeline off there is a legitimate operational choice. No break-glass for production — fork the binary if you genuinely need that, and Phase 6's audit log catches it post-hoc.

| Environment | `PII_PROTECTION` unset | `=false` | `=true` |
|---|---|---|---|
| `production` | refuse to start | refuse to start | enabled |
| `uat` | refuse to start | disabled | enabled |
| `dev` | refuse to start | disabled | enabled |

### URL-heuristic warning (`PII_NONPROD_HINTS`)

When the pipeline ends up disabled (`PII_PROTECTION=false` in `uat`/`dev`), the loader checks the configured environment identifier against a list of non-prod hint substrings — `dev`, `uat`, `training`, `support`, `migration`, `sandbox`, `test` by default. If none match, a stderr warning fires at startup: `[PII WARNING] PII protection is OFF and the configured environment identifier '...' does not match any non-prod hint ...`. Server still starts — this is a heuristic safety net, not a gate. Catches the failure mode where a consultant copy-pastes a dev `.mcp.json` and swaps in a production URL while leaving the env-type label as `dev`. Override the hint list via `PII_NONPROD_HINTS` (comma-separated, case-insensitive substrings).

Identifier source per package: `powerplatform-data` uses `POWERPLATFORM_URL`; `azure-devops` uses `AZUREDEVOPS_ORGANIZATION` (the host `dev.azure.com` is intentionally excluded so it doesn't always match `dev`); `azure-sql` uses `AZURE_SQL_SERVER` (or first server in `AZURE_SQL_SERVERS`); `rest-api` uses `REST_BASE_URL`.

### Per-call summary footer (Q4 decision)

Every redacted MCP response is followed by a compact human-readable footer like `[PII protection: 2 emails + 4 names + 2 dobs + 1 phone redacted by L1/L2/L3/L4]`. The agent sees what was denied, the consultant sees the same line in their Claude Code transcript, and counts-by-category leak only structural information (never values). The orchestrator emits a structured per-layer report (`PipelineReport`) consumed by the footer; the same report will power the deferred `pii-explain-last-call` tool and CLI `--redaction-diff` view in v1.5.

### Observe-mode

`PII_OBSERVE_MODE=true` runs the full pipeline (computing what would be redacted) but returns the original data unchanged. Footer notes `(observe-mode — values not changed)`. Useful for validating recall against real production-shaped responses before committing to redaction behaviour.

### Per-layer toggles

Each of `l1`, `l2`, `l3`, `l4` is independently switchable via `PII_CONFIG_PATH` JSON:

```json
{
  "enabled": true,
  "layers": { "l1": true, "l2": true, "l3": false, "l4": true }
}
```

Useful for diagnosing which layer is or isn't doing its job during iteration.

### Cross-package integration

- **PowerPlatform (`powerplatform-data`):** `DataService.queryRecords` runs results through the pipeline. Layer 1 filters caller-supplied `$select`. Pipeline shared via ServiceContext across MCP server + CLI. The `powerplatform` (read-only) and `powerplatform-customization` packages do not use `DataService` — their tools return metadata, not records, so no PII path needs wiring.
- **Azure DevOps (`azure-devops`):** `WorkItemService.getWorkItem` and `queryWorkItems` run results through the pipeline. ADO identity objects (`System.AssignedTo`, etc.) flow through Layer 3 (catches `uniqueName` email format) and Layer 4 (catches `displayName` person names if the `displayName` key is in scan-fields, which it now is by default).
- **Azure SQL (`azure-sql`):** `QueryService.executeQuery` runs query result rows through the pipeline. Layers 3 and 4 do the work since SQL has no per-entity field rules — Layer 2 is effectively a no-op for SQL.
- **REST API (`rest-api`):** `RestApiService.request()` runs every HTTP response body through the pipeline. JSON-parsed bodies are walked as object trees; plain-text/XML/HTML bodies are wrapped under `body` (which is in default `scanFields`) and scanned. L1 + L2 do not apply (no schema, no entity types) — L3 + L4 do all the work, identical surface to Azure SQL. Use case: REST clients that proxy backend systems (e.g. DAB → SQL) need the same redaction posture as the underlying datastore.

## Bug Fixes

### `convertLookupNamesToSchemaNames` was using the wrong identifier

`packages/powerplatform-core/src/services/DataService.ts:668` (now `convertLookupNamesToNavProperties`) was converting lookup attribute logical names to the attribute's `SchemaName` (e.g. `primarycontactid` → `PrimaryContactId`) for `@odata.bind` keys. Dataverse navigation properties are actually the lookup attribute's logical name (per `ReferencingEntityNavigationPropertyName` in `ManyToOneRelationships` metadata), not the SchemaName. Result: every `create-record` / `update-record` call with a lookup bind silently failed with "An undeclared property 'X' which only has property annotations in the payload but no property value was found."

Fix: query `ManyToOneRelationships` for the actual nav property name; for polymorphic lookups, filter by `ReferencedEntity` to disambiguate. Cached per-process to avoid repeated metadata calls. The `get-lookup-target` tool now returns the correct nav property name and the corrected wording (`@odata.bind` requires the navigation-property name, NOT the SchemaName). (powerplatform-core, powerplatform-data)

## Beta Testing Configuration

To enable PII protection in production environments, set the env vars below. The server refuses to start when `MCP_ENVIRONMENT_TYPE=production` and `PII_PROTECTION` is unset/false — this is the contract.

```json
{
  "mcpServers": {
    "PII-PROD-pp-data": {
      "command": "npx",
      "args": ["-y", "--package=@mcp-consultant-tools/powerplatform-data@beta", "mcp-pp-data"],
      "env": {
        "MCP_ENVIRONMENT_TYPE": "production",
        "PII_PROTECTION": "true",
        "PII_OBSERVE_MODE": "false",
        "POWERPLATFORM_URL": "https://yourorg.crm.dynamics.com",
        "POWERPLATFORM_CLIENT_ID": "your-client-id",
        "POWERPLATFORM_CLIENT_SECRET": "your-client-secret",
        "POWERPLATFORM_TENANT_ID": "your-tenant-id"
      }
    },
    "DEV-pp-data": {
      "command": "npx",
      "args": ["-y", "--package=@mcp-consultant-tools/powerplatform-data@beta", "mcp-pp-data"],
      "env": {
        "MCP_ENVIRONMENT_TYPE": "dev",
        "PII_PROTECTION": "false",
        "POWERPLATFORM_URL": "https://yourdev.crm.dynamics.com",
        "POWERPLATFORM_CLIENT_ID": "...",
        "POWERPLATFORM_CLIENT_SECRET": "...",
        "POWERPLATFORM_TENANT_ID": "..."
      }
    }
  }
}
```

Optional config file (`PII_CONFIG_PATH`) for per-client overrides:

```json
{
  "enabled": true,
  "observeMode": false,
  "layers": { "l1": true, "l2": true, "l3": true, "l4": true },
  "fieldRules": {
    "contact": {
      "excludeFromSelect": ["birthdate"],
      "redactInResponse": ["firstname", "lastname", "fullname", "emailaddress1", "mobilephone"]
    }
  },
  "regex": { "email": true, "phone": true, "dateOfBirth": true, "customPatterns": [] },
  "ner": { "scanFields": ["description", "notetext"], "scanOdataAnnotations": true }
}
```

## Out of v1 Scope (Documented Gaps)

- **Layer 5 (local LLM safety net)** — deferred to v2 alongside the deployment-topology decisions for the model host (PoC localhost / SI-managed model host / client-tenant Azure VM). v2 also picks up Q7 (silent-degradation behaviour).
- **Phase 6 (audit and compliance logging)** — deferred to a separate scoped session. Until Phase 6 ships, the organisational AI usage policy should not authorise enterprise-tier external LLMs against production data via the redaction pipeline alone — the pipeline is the technical mitigation; the audit log is what makes it defensible.
- **`pii-explain-last-call` MCP tool and `--redaction-diff` CLI flag** — deferred to v1.5. The structured per-layer report that powers them is built today; the surface for consultants and DPOs comes later.
- **Per-client config templates** beyond the defaults plus `PII_CONFIG_PATH` overrides — v1.5+.
- **Auto-detection of PII-candidate fields** from Dataverse metadata (e.g. fields of type Email/Phone) — v1.5+.
- **Textual-date detection** (e.g. "12 March 1985" in free text). The ISO-format DOB regex catches structured dates; textual dates are a Layer 4 enhancement candidate (`compromise.js` has `dates()` extraction; opt-in for v1.5).
- **Nested-object Layer 2 walking** for ADO identity objects (`System.AssignedTo`, etc.). Currently L3 catches the email-formatted `uniqueName` and L4 catches the `displayName`; explicit Layer 2 rules with nested-path support are a v1.5 enhancement.
- **PowerPlatform packages other than `powerplatform-data`** (read-only `powerplatform`, `powerplatform-customization`) — they don't use `DataService`, their tools return metadata not records, and metadata responses don't carry PII.
