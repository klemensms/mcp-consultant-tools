# Release Notes: v32.0.0-beta.2

**Date:** 2026-05-11
**Branch:** `release/31.0`
**Status:** Held for npm publish

> Per-iteration agent-level detail. The user-facing single source of truth is [`v32.0.0.md`](v32.0.0.md) (still pending — see beta.1 notes).

## Overview

Reverses the beta.1 posture: every new PII and audit environment variable is now **optional**. MCP servers that worked on `31.0.0-beta.4` start unchanged on `32.0.0-beta.2`, with no config edits required. Opt-in remains explicit — set the env vars and the subsystems engage exactly as in beta.1.

> **No breaking changes.** This iteration walks back the beta.1 refuse-to-start matrix in response to the friction it caused for existing operators. Configs that pin `31.0.0-beta.4` should be able to bump to `32.0.0-beta.2` without touching `.mcp.json`.

The audit and PII subsystems themselves are unchanged — same redaction layers, same chain semantics, same `mcp-audit-cli` surface. Only the startup gates differ.

## Changes Implemented

### PII pipeline — optional by default (`@mcp-consultant-tools/core`)

`packages/core/src/pii/config.ts` no longer throws when `PII_PROTECTION` is unset. Resolution order: `fileConfig.enabled ?? PII_PROTECTION ?? false`. Operators opt in by setting `PII_PROTECTION=true` or shipping a config with `"enabled": true`. The previous "production env rejects `PII_PROTECTION=false`" gate is removed. `MCP_ENVIRONMENT_TYPE` is no longer read.

The `[PII WARNING] PII protection is OFF and the configured environment identifier ...` stderr warning (`checkEnvironmentLooksUnprotected`) is no longer wired into `createPiiPipelineFromEnv`. The function is retained as a public export for future consumers but currently has no callers.

Affects: every package that calls `createPiiPipelineFromEnv` — `powerplatform-data`, `azure-devops`, `azure-sql`, `azure-b2c`, `rest-api`.

### Audit subsystem — optional by default (`@mcp-consultant-tools/core`)

`packages/core/src/audit/config.ts` defaults `MCP_AUDIT_LEVEL` to `off` when unset (was: throw). The "production env rejects `MCP_AUDIT_LEVEL=off`" gate is removed. `MCP_ENVIRONMENT_TYPE` is no longer read; audit records stamp `environment.type='production'` as a fixed value (deferred to Phase B if differentiation is needed). Invalid `MCP_AUDIT_LEVEL` values still refuse to start. Client-required-when-lean/full and rotation parsing are unchanged.

`buildAuditPipeline()` in `powerplatform-data/src/context-factory.ts` continues to return `null` when level is `off`; tool wrappers already null-check `ctx.audit`.

### Bug 3 fix — `create-record` returns the GUID (`@mcp-consultant-tools/powerplatform-data`)

`packages/powerplatform-data/src/tools/write-tools.ts` — the response parser previously walked `Object.keys` looking for a key ending in `id` and fell back to `'N/A'` when the body didn't carry an `id` field. Dataverse with `Prefer: return=representation` returns the entity-specific primary key (`contactid`, `accountid`, …) and suppresses the `OData-EntityId` response header. The new code reads `visibleResult[\`${entityLogicalName}id\`]` directly. Closes the deferred UX bug tracked in `docs/programmes/pii-and-audit/implemented/audit-phase-a-pp-data.md`.

## Known Issues

- Audit records always stamp `environment.type='production'` regardless of the actual environment. `MCP_ENVIRONMENT_TYPE` is fully ignored. If the prod/UAT/dev differentiation is wanted back, reinstate reading at the per-record level (no gating) in a follow-up.
- The master `v32.0.0.md` doc referenced from beta.1 was not authored. It should land before promotion to `@latest`, summarising the whole 32.x stream (audit Phase A + the beta.2 walk-back).
- `audit-cli@0.1.0` is published for the first time in this iteration. No `@latest` promotion until it has been exercised against a real client engagement.
