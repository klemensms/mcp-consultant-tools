# Release Notes: v35.0.0-beta.23

**Date:** 2026-09-07
**Branch:** `release/35.0`
**Status:** Published to beta

> Per-iteration agent-level detail. The user-facing single source of truth is [`v35.0.0.md`](v35.0.0.md).

## Overview

Closes the `docs/KNOWN_ISSUES.md` queue down to what genuinely cannot be closed without a live tenant or a release-shaped pin bump. Five defects, and they share one shape: **a result that cannot be told apart from a good one.** A flow whose definition would not parse scored zero and reported no hardcoded secrets, which is byte-for-byte what a simple, clean flow returns. A validation pass over part of a solution read exactly like one that covered all of it. A guessed entity set name was printed into a copy-paste URL as though it had been read from Dataverse. And the PII "looks unprotected" warning, the thing meant to catch a server pointed at production with redaction off, had never fired once.

**No breaking change requires a config edit, so this iteration ships no `⚡ Quick upgrade` block.** One breaking change exists and it is scoped to direct importers of the `powerplatform-core` library; every MCP tool and CLI behaves as before. Adding the upgrade block for it would tell every user their `.mcp.json` needs attention when it does not, which is the failure the block's own guidance warns about.

## Changes Implemented

- **`fix(core): wire the PII "looks unprotected" warning into pipeline construction`** (`59ad04f`). `createPiiPipelineFromEnv` declared its parameter `_options` and ignored it, while five call sites passed an `environmentIdentifier`; `checkEnvironmentLooksUnprotected` had zero call sites anywhere in the repo. One defect from either end. The option is now honoured and the check runs at construction. The dead `MCP_ENVIRONMENT_TYPE` advice was removed from the warning string, and eleven docs claiming that variable feeds the warning were corrected to say it is inert. 7 new tests, red before green.

- **`fix(cli): build the PII pipeline on first use, not at module load`** (`c1af53f`). All four Commander CLIs run `const ctx = createServiceContext();` at module top level, one line above `program.parseAsync`, so it executes before the `preAction` hook that calls `loadEnvAndResolve`. Anything supplied only through `--env-file` was invisible to the PII pipeline - including `PII_PROTECTION=true`, so a correctly-configured run could be warned at for being unprotected. All six factories (`azure-devops`, `azure-sql` x2, `rest-api`, `azure-b2c` x2) now build through a memoised thunk. No signature changed; every use site was already inside a lazy getter.

- **`fix(powerplatform-core): report the entity cap validateBestPractices was applying silently`** (`023dd49`). The built truncation block is spread and `totalAvailable` set from the counted value, because a client-side cap knows the population it capped. Reports "2 of 5" where it previously said nothing at all.

- **`fix: name the six fan-out failures that returned an empty result as an answer`** (`16c9c51`). Four `powerplatform-core` utilities (`extractComplexityFactors`, `extractComplexityFlags`, `extractUrlsFromFlowDefinition`, `detectHardcodedSecrets`) now throw rather than returning an empty accumulator; `analyseOneFlow` attempts each section separately and collects `analysisFailures` onto the flow, keeping it in `summary.total`. `code-review` NuGet vulnerability lookups run through a `FanOutRecorder`. `powerplatform-data`'s `get-lookup-target` still guesses an `EntitySetName` but flags the guess above anything copyable. 10 new tests, red before green.

- **`chore: sweep U+2014 and U+2013 out of everything but the one exemption`** (`7f9c2c8`). 174 files, 3,508 characters. The `KNOWN_ISSUES` entry scoped four directories; a repo-wide re-count found 19 more files outside all four but inside the entry's own title, so the entry could not have been removed honestly on its stated scope. The exemption is `packages/core/src/pii/ner-redaction.ts:18`, where both characters are members of a regex character class stripped from a token's edges.

- **`fix: replace five real Dataverse record GUIDs with sanctioned placeholders`** (`2d96882`). The repo's own internal-identifier scan flagged five record GUIDs from a client environment, in eleven places across the PII demo fixtures and one archived release note. They entered in the initial public-release commit, not in this work. History is deliberately not rewritten - the values are already on every branch of a public repo and cannot be recalled. Each record keeps a **distinct** placeholder, because the account fixture's `_primarycontactid_value` has to keep pointing at the contact fixture. Nothing published to npm carried them: all five files sit outside `packages/`.

- **`chore: drain the carry-forward register and reconcile it against disk`** (`21f52b5`). Fourteen carried items reconciled by reading the code, not by trusting that an earlier session closed what it said it closed.

## Testing

**Unit-verified, plus live runs of the built CLIs for the PII behaviour. Nothing in this iteration has met a live Dataverse environment.**

- **1,289 tests pass across 15 workspaces**, unchanged from before the em-dash sweep, with 17 new tests written red-first across the two PII fixes and the fan-out work.
- **The PII warning was confirmed in the built `azure-devops` CLI**, not only in source: it warns on identifier `contoso`, is silent on `contoso-dev`, and is silent with `PII_PROTECTION=true`.
- **The lazy-context fix was verified against the compiled output**, using a script reproducing `cli.ts`'s module order: silence at construction, silence when `PII_PROTECTION` is set after construction, and the warning when protection is genuinely off.
- **The stale-pin divergence was measured, not inferred.** The built `azure-devops` CLI (pinned `35.0.0-beta.1`) emits the new warning and the built `azure-sql` CLI (pinned `33.0.0`) does not, from identical inputs.
- **`powerplatform-data`'s fix has no unit test and could not have one.** The package ships no test harness - see Known Issues - so its handler was driven with a stub server and a stub client, which exercised both branches but leaves no regression guard.
- **The em-dash sweep was proved file by file:** each changed file was confirmed to differ from its committed version by exactly the substitution and nothing else, by re-applying the substitution to the HEAD blob and diffing. `tests/` was done last and by hand; all 321 dash-bearing lines were read before and after, and none is compared with `===`, `includes`, `toBe` or `match`.

**Not verified:** every fix's behaviour against a live Dataverse or Azure environment. There are no such credentials on the machine that produced this iteration.

## Known Issues

Found or re-measured during this iteration. Full detail in [`docs/KNOWN_ISSUES.md`](../KNOWN_ISSUES.md).

- **14 of 29 packages declare no `test` script, and the root `npm test` skips them in silence.** The script is `npm run test --workspaces --if-present`. The green "1,289 passing across 15 workspaces" reported above is accurate about what ran and says nothing about the other fourteen, none of which contains a test file. This was recorded against one package and is true of fourteen. Cheapest first fix is one line: drop `--if-present` so the run names what it skipped.
- **Five fan-out sites stay open, blocked by the stale `core` pin rather than by the code.** `azure-sql`, `azure-storage` and `service-bus` pin `core` at `33.0.0`, which predates both `FanOutRecorder` and `buildTruncation`; importing either fails the build with `TS2305`. Worth keeping the distinction: adding a **new** `core` export to a stale-pinned package fails loudly at build, whereas **changing** an existing one passes the build and diverges only at runtime.
- **`MCP_ENVIRONMENT_TYPE` remains inert.** Wiring it up or deleting it and its documentation is an open decision, not an oversight.
- **The two `azure-defender` entries are untouched and must not be reported as fixed.** Both need a live tenant run, not a code change.
- **Eight files mirrored verbatim to `mcp-computer-use` now diverge**, because that repo is not checked out on this machine and "edit both" could not be honoured. Every difference is inside a `#` comment, so no hook behaviour moved on either side. Recorded in the root `CLAUDE.md`.
