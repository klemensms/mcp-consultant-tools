## Overview

Extends `teams` from "reads and replies" to "finds people and starts conversations": directory lookup, direct messaging by name, cross-surface message search, incremental channel reads, and @-mentions on every outbound path. `teams` and `meta` only.

The work began from a brief that described a pre-`a1ce296` state and asked for changes that had largely already shipped in beta.6/beta.7 — widening five scopes to eleven, implementing MSAL silent refresh, and adding ten tools of which seven already existed. That was reported back and the scope was reduced to the genuine delta before any code was written.

## Changes Implemented

### Scopes (breaking)

- `DEVICE_CODE_SCOPES` widens from eight to ten, adding `User.ReadBasic.All` and `Chat.Create`.
- `ChannelMessage.Edit` is **deliberately not requested** despite being consented. No published Graph method accepts it: editing a channel message's content is `PATCH /teams/{t}/channels/{c}/messages/{m}`, whose delegated permission is `ChannelMessage.ReadWrite` or `Group.ReadWrite.All`, neither consented. Requesting it would widen the token for zero capability, so `edit-channel-message` is not implemented and cannot be on this registration.
- Widening the array invalidates access tokens minted against the old set. Handled rather than breaking: `acquireTokenSilent` redeems the cached refresh token for the wider set where consent exists, falling back to device code only if the refresh token itself is dead.

### New tools (4, all with CLI parity)

- **`find-user`** — `GET /users?$search`. An *advanced* query: Graph rejects it without **both** `ConsistencyLevel: eventual` and `$count=true`, and the resulting error mentions neither. Quotes and backslashes are stripped from the term, which is interpolated into quoted `"field:term"` clauses.
- **`send-direct-message`** — resolve → find existing one-on-one chat → create only if none → post, behind one tool rather than three, so the caller does not carry the duplicate-thread risk. Ambiguous names are reported with candidates rather than guessed at; an exact email/UPN/display-name match beats partial hits. Two guards against duplicates: the lookup runs first so the result can honestly report `chatExisted`, and Graph documents that `POST /chats` returns the existing one-on-one chat rather than creating a second — so a missed lookup costs an inaccurate label, never a duplicate thread.
- **`search-messages`** — `POST /search/query` spanning channels and chats. Two shape traps, both pinned by tests: `chatMessage` is not in the v1.0 `entityType` enum so `Prefer: include-unknown-enum-members` is mandatory; and hits carry the sender as `from.emailAddress`, not the `from.user` shape the message endpoints use, so routing one through `toMessageInfo` renders every hit as an unattributed "Unknown" — which reads as a permission failure rather than a mapping bug.
- **`get-channel-messages-delta`** — `$deltatoken=latest` is not honoured, so a cold start must page to the end of history before Graph issues a `deltaLink`. `maxPages` bounds that walk, and a truncated walk returns **no** `deltaLink`, because one from a partial walk would silently skip everything beyond the cut. Truncation is stated in the output, not hidden.

### @-mentions on all four outbound paths

- Inline `@[Name or email]` markers, resolved and sent as a real Teams mention.
- **Both halves or neither.** Graph needs an `<at id="N">` element in the body AND a `mentions[]` entry with the same id. An `<at>` with no entry renders as a literal tag; an entry with no `<at>` notifies nobody. `buildOutboundMessage()` is the only thing that builds either.
- Required changing `TeamsService.sendChannelMessage` to take raw content plus a `format` rather than pre-converted HTML: `tools/send-message.ts` and `cli/commands/message-commands.ts` were each calling `markdownToHtml` themselves, which is precisely the shape of bug where a feature lands on one surface and not the other. Conversion, sanitisation and mention resolution now happen in one place for every path. `buildMessageBody` was left dead by the change and removed.
- Resolution reuses `resolveDirectoryUser`, moved to module scope in `people-service.ts` rather than duplicated: `PeopleService` depends on `TeamsService`, and `TeamsService` owns one of the four send paths, so a method would have been a cycle. An ambiguous mention therefore behaves exactly like an ambiguous DM recipient — candidates reported, message **not** sent.
- Ordering is deliberate: marker → plain alphanumeric placeholder → markdown conversion/escaping → sanitise → `<at>`. Injecting `<at>` before sanitisation would mean either widening the DOMPurify tag allowlist or watching the sanitizer strip the markup just added. The trade-off is that the `<at>` fragment is the one thing not sanitised, so the display name is HTML-escaped explicitly — a directory display name can contain anything.
- Same person mentioned twice resolves once and reuses one id (two entries render as a duplicate mention). A `format: "text"` message carrying a mention is promoted to HTML with its text escaped, since a mention cannot render from plain text, while still not interpreting markdown. A message with no markers makes **no directory call at all**, so the common path still works on a token without `User.ReadBasic.All`.

### Architecture

- New `PeopleService` and `SearchService` share `TeamsService`'s authenticated Graph client, as `MessageService` already does. Channel delta lives with the other channel reads.
- `clampTop` and `wrapGraphError` exported from `message-service` rather than duplicated.

## Testing

Suite grown **45 → 111** across 9 files.

- `people-service.test.ts` (19) — `ConsistencyLevel`/`$count` presence, search-term sanitisation, ambiguity handling, existing-chat reuse, chat-creation body shape.
- `search-service.test.ts` (11) — `Prefer` header, entity type, the `from.emailAddress` mapping path, `<c0>` marker stripping, total/more-results reporting.
- `mentions.test.ts` (18) — marker parsing, `<at>`/`mentions[]` pairing, de-duplication, text-format promotion, display-name escaping, unresolvable and ambiguous markers.
- `outbound-mentions.test.ts` (12) — **all four outbound paths in one `describe.each` table.** The realistic bug is not "mentions are broken" but "mentions work everywhere except one path", which per-service tests cannot catch. **If a fifth send path is added, add it there.**
- `message-service.test.ts` +6 — delta paging, deltaLink resumption, and the withheld deltaLink on truncation.

**Mutation-verified rather than trusted**, per the standing lesson in this package that a stub only proves the code agrees with itself:

| Induced fault | Result |
|---|---|
| Remove `ConsistencyLevel` header | 1 test fails |
| Skip the existing-chat lookup | 3 tests fail |
| Drop `mentions[]` from `send-chat-message` only | **exactly that path's test fails, no other** |
| Remove display-name escaping | injection test fails |
| Remove mention de-duplication | 2 tests fail |

Also verified: clean `build:release` green, all 21 build dirs present, `teams` ships 41 `.d.ts`, server registers 20 tools over real MCP stdio, CLI registers a matching command for each.

### Not tested

**Every Graph call in this wave.** The Teams server was not configured on the build machine — no `TEAMS_CLIENT_ID`/`TEAMS_TENANT_ID`, no token cache — so nothing here has touched real Teams. Specifically unproven:

1. The ten-scope device-code sign-in.
2. Silent refresh across the scope widening (does the cached refresh token redeem for the wider set without a prompt?).
3. `find-user`, `send-direct-message`, `search-messages`, `get-channel-messages-delta` — all permission behaviour and response shapes.
4. **The @-mention request body.** Highest risk in the wave: it is a new Graph request body, and beta.7's reaction tools shipped broken in exactly this way — failing on every call while four unit tests asserted the wrong payload. This package's own guidance is to get one live confirmation before releasing a changed request body. That did not happen here; the release proceeded on an explicit decision to treat beta as the testing vehicle.

Minimum live checks before promoting anything from this iteration:

```bash
cd packages/teams
node build/cli.js auth logout && node build/cli.js auth login   # ten-scope consent
node build/cli.js list-teams
node build/cli.js find-user "<a colleague>"
node build/cli.js send-direct-message <your-own-email> "test @[<a colleague>] mention"
node build/cli.js search-messages "release"
node build/cli.js get-channel-messages-delta --max-pages 3
```

The mention check is the one that matters: confirm it renders as a real mention that notifies the person, not a literal `<at>` tag.

## Known Issues

- Nothing in this iteration is confirmed working against live Teams. See **Not tested** above.
- `edit-channel-message` is not implemented and cannot be on this permission set — `ChannelMessage.Edit` has no published Graph method. Recorded so it is not re-attempted.
- The `search-messages` permission mapping rests on observed behaviour, not the documented table: Graph's reference lists `Chat.Read` for `entityTypes: ["chatMessage"]`, which is not consented, yet live testing on 2026-08-12 returned 200 on `Chat.ReadWrite` alone. If Graph ever enforces its documented list literally, this is the first tool to break, and the fix is a scope request rather than a code change.
