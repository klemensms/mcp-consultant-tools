# Release Notes: v35.0.0-beta.26

**Date:** 2026-10-04
**Branch:** `release/35.0`
**Status:** Published to beta

> Per-iteration agent-level detail. The user-facing single source of truth is [`v35.0.0.md`](v35.0.0.md).

## Overview

Two PowerPlatform changes.

1. **The browser sign-in is hardened.** Its localhost callback sent no PKCE challenge, although its header said it did, checked no `state`, and listened on every network interface.
2. **The flow run tools live in the read-only server only.** `get-flow-runs` and `get-flow-run-details` were registered in both `powerplatform` and `powerplatform-data`, calling the same service with the same parameters. The data server is now about records only. The read-only server keeps the tools, with the audit logging they had in the data server.

**One breaking change, and it is not a config edit:** a caller using the two flow tools, or the `flow` CLI commands, on `powerplatform-data` must call them on `powerplatform` (`mcp-pp-cli flow runs` / `flow run-details`) instead. No `.mcp.json` change is needed, so this iteration ships no `⚡ Quick upgrade` block.

## Changes Implemented

- **`fix(powerplatform-core): harden the browser sign-in callback`** (`6553183`). The authorisation request carries an S256 code challenge, and the code is redeemed with its verifier. Each sign-in gets a random `state`; a callback whose `state` does not match is answered `400 invalid_state`, its code is never redeemed, and the server keeps waiting for the genuine response. The callback server and the free-port probe bind to `127.0.0.1`. The redirect URI is unchanged (`http://localhost:<port>`), so no app-registration change is needed. 8 tests run against the real callback server; 7 of them fail on the previous code.
- **`refactor(powerplatform): flow run tools live in the read-only server only`** (`f0ba881`).
  - The two tools and the `flow` CLI commands are removed from `powerplatform-data` (14 to 12 tools).
  - `powerplatform` builds the same audit pipeline as the data server. It is off while `MCP_AUDIT_LEVEL` is unset, and with a level set it requires `MCP_AUDIT_CLIENT`.
  - `powerplatform` logs both flow-run tools through it and gains `set-audit-engagement` (52 to 53 tools).
  - `powerplatform` gets a vitest setup with 4 tests.

## Testing

- Full suite: 1,727 tests across 19 packages, on a clean release build. Tool lists read from the running servers: `powerplatform` 53 with both flow tools and `set-audit-engagement`, `powerplatform-data` 12 without the flow tools.
- Confirmed with the real MSAL library that the sign-in URL carries the code challenge and our `state` unchanged.
- **Not verified live:** a real browser sign-in against a tenant, and a flow-run read against a real environment with audit on.

## Known Issues

- The browser opens `http://localhost` while the callback now listens on IPv4 `127.0.0.1` only. Mainstream browsers fall back to it when `localhost` also resolves to IPv6, but the first real sign-in is the proof.
