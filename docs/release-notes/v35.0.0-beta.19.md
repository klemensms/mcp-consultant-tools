# Release Notes: v35.0.0-beta.19

**Date:** 2026-08-21
**Branch:** `release/35.0`
**Status:** Published to beta

> Per-iteration agent-level detail. The user-facing single source of truth is [`v35.0.0.md`](v35.0.0.md).

## Overview

Closes the remainder of the CLI assurance report that beta.18 left open, plus the two carried-over
defects recorded in `docs/KNOWN_ISSUES.md` for the integration audit and the two for Log Analytics.

Every change in this iteration is the same defect class: **a result that cannot be told apart from a
complete one.** A capped list reporting `hasMore: false`, an audit report naming 100 assemblies with
nothing said about the rest, a description field that is `null` because nobody asked for it, and two
surfaces rendering the same investigation from two copies of the same KQL.

**`meta` jumps from beta.17 to beta.19.** beta.18 was never published as a bundle, so anyone on
`mcp-consultant-tools` receives beta.18's changes for the first time in this release, including its
breaking exit-code change. Individually-installed packages are unaffected - they got beta.18 when it
shipped.

No config changes. No new or renamed env vars. No removed or renamed tools.

## Changes Implemented

### The last four `$top`-based completeness checks (`5005061`)

`MetadataService.getGlobalOptionSets`, `WorkflowService.getWorkflows`,
`FlowService.searchWorkflows` and `FlowService.getFlowRuns` each requested `$top = max + 1` and
inferred `hasMore` from the returned row count. That cannot work at Dataverse's 5,000-row response
cap: the server returns exactly 5,000, the sentinel row never arrives, `5000 > 5000` is false, and a
truncated result is reported as complete.

All four now page via `paginateDataverse` (`Prefer: odata.maxpagesize` plus `@odata.nextLink`) and
return a `truncation` block from `buildTruncation`. `getFlowRuns` was the likeliest of the four to
bite in practice - one row per execution, so a busy flow passes 5,000 runs easily - and it was the
one that survived two earlier counts of this defect, because it spelled its cap
`$top=${limit + 1}` inline in the URL where a grep for `maxRecords + 1` misses it.

- Caller-visible on three commands and their MCP twins: `flow search`, `flow runs`,
  `flow workflows`, across `powerplatform`, `powerplatform-customization` and `powerplatform-data`.
  `getGlobalOptionSets` has no MCP tool and no CLI command, so its change is library-only.
- `maxRecords: 0` on `getFlowRuns` now resolves to the documented 250-run ceiling. It previously
  became `$top=1`, returned no runs at all, and reported that more were available.
- The hand-rolled "more available" hints are replaced by `truncationSuffix`, except on `flow runs`,
  where the generic suffix's "re-run uncapped" advice would be wrong - that method is hard-capped at
  250, so it tells the caller to narrow the window instead.
- The `workflows-report` prompt reads 100 workflows and printed that count as **Total Workflows**
  unqualified. It now declares the cap.

### `gen-integration-audit` no longer claims completeness it does not have (`b2991a0`)

`generateAuditReport` capped the plugin-assembly inventory at 100 and discarded the `truncation`
block `getPluginAssemblies` returns.

- `report.summary.completeness` carries `requestedMax`, the plugin-assembly `TruncationInfo`, and an
  `unverified` list; `report.plugins.truncation` carries the same block.
- The markdown states the scope of its counts under the executive summary. The CLI summary no longer
  opens with the word "complete".
- **The `unverified` list is the load-bearing part.** The report caps four collections and only the
  plugin inventory can currently answer for itself, so a completeness block covering one out of four
  would be read as covering the report. It names `serviceEndpoints`, `webhooks`,
  `environmentVariables` and `flows` instead, and the markdown says those figures may be a capped
  page and that the report cannot tell you which.

### `plugin list` returns each assembly's description (`b2991a0`)

`description` was selected only by `plugin get`, so the audit's `externalPlugins` block read it off a
shape that never carried it: `null` for every assembly, which reads as "this assembly has no
description" rather than "the query did not ask for it". `description` moves from
`PluginAssemblyDetail` into `PluginAssemblySummary`, the list query selects it, and
`PluginAssembliesResult.assemblies` is typed `PluginAssemblySummary[]` rather than `unknown[]` - the
`unknown[]` plus a cast at the call site is what let a read of a non-existent field compile.

### `investigate-sync` renders one report from one code path (`d6d2585`)

Four KQL queries, the workspace-name parse and the whole markdown assembly were written out inline
in the CLI and again in the MCP tool. That is how the invalid `FunctionAppLogs` query got in
earlier: a string that exists twice is a string no test can assert against.

The two copies had already drifted. The tool rendered its empty-result note with a tick and the CLI
without, so the same environment produced two different reports; and an unparseable workspace id
`process.exit(1)`-ed in the CLI while returning an `isError` payload in the tool.

`utils/sync-investigation-query.ts` builds the queries and does the parse,
`LogAnalyticsService.investigateSync` runs them, `formatInvestigateSyncMarkdown` renders, and both
surfaces call all three. The parse throws, so both fail identically. `investigate-app` needed none of
this - it already went through the service; only `investigate-sync` was duplicated, and the
`KNOWN_ISSUES` entry claiming both was half stale.

### The Log Analytics query API retries transient failures (`d6d2585`)

`LogAnalyticsService.executeQuery` made exactly one `axios.post` and had no retry policy, while
`azure-management`'s `ArmClient` and `azure-defender`'s `DefenderClient` both retry the transient set
with backoff and honour `Retry-After`. Its 429 branch read that header purely to print it.

`utils/retry.ts` retries `[429, 500, 502, 503]`, honours `Retry-After`, and otherwise backs off
exponentially from 1000ms across three attempts. The original error is rethrown once the retries are
spent, so the existing error mapping is unchanged.

Two deliberate divergences, both documented in `packages/log-analytics/CLAUDE.md`:

- **504 is excluded**, where the sibling clients include it. On a control-plane list a 504 is a
  gateway hiccup; on the query API it means the query itself did not finish inside the service's
  window, so an identical retry costs another 30-second wait and returns the same answer. The
  existing 504 message already tells the caller to narrow the query.
- **The policy lives in `log-analytics`, not in `core`.** That package pins `core` at `33.0.0` and
  carries a vendored copy of that version, so a helper hoisted into `core` would be invisible there
  until the pin moves and the stale copy is deleted.

### X2's remaining fan-out scope is measured, not converted (`0a8f150`)

The fan-out contract landed in beta.18 for `azure-management` and `azure-defender`. What remained
elsewhere had never been counted, and the recorded work-list - a grep for one log string - was
exhausted.

`scripts/sweep-fanout-candidates.mjs` finds candidates by shape instead: a `catch` inside an
iteration that neither rethrows nor records the failure, plus the promise-chain equivalents. It
returns **42 candidates across 12 of 29 packages**, every one read and classified: **17 are the
defect**, 5 record the outcome but not the reason, 6 are a related undeclared-partial-value family
that wants `buildTruncation` rather than `FanOutRecorder`, and 14 are deliberately not defects. 17
packages carry no candidates at all.

**None of the 17 is converted in this iteration.** Three of the four affected packages need their
`core` pin checked and possibly moved first, which is a release-shaped change. The full table, naming
what goes missing at each site, is in `docs/KNOWN_ISSUES.md`, and the sweep is committed so the
number can be re-run and argued with rather than taken on trust.

### Release hygiene found while preparing this iteration

- **`powerplatform-data` pinned `powerplatform-core` two versions behind** (`beta.4` against a
  workspace at `beta.5`). Published unchanged, its `get-flow-runs` would have installed the old
  library and shipped without the truncation fix, silently, because the local build was green
  through the workspace link. Corrected, along with the same pin in `powerplatform` and
  `powerplatform-customization`.
- **The incremental build was hiding a `core` version skew.** A from-scratch build after the pin fix
  failed with two conflicting `PiiProtectionPipeline` types: `powerplatform-data` carried a vendored
  `core@34.1.0` while `powerplatform-core` linked the workspace `core@35.0.0-beta.1`. Its `core` pin
  moves to the 35.0 line and the stale copy is gone. **Every build claim in this iteration is from a
  clean rebuild**, not an incremental one.
- **`meta` carried eight stale pins** spanning three sessions' work, and had never been published at
  beta.18. All 25 pins now match the workspace, and every target already exists on npm.

## Testing

**Verified, without credentials:**

- Clean from-scratch build of the whole workspace, no TypeScript errors.
- **1,205 tests, 0 failures**, up from 1,155 at beta.18. 50 new tests.
- **Seven inversion checks.** Each load-bearing assertion was confirmed to fail when the fix is
  removed: deriving `hasMore` from the row count turns 13 red; passing `maxRecords: 0` straight
  through turns 1 red; dropping `description` from the list `$select` turns 1 red; removing it from
  the formatter turns 2 red; hard-coding the audit completeness block to "complete" turns 2 red;
  ignoring `Retry-After` turns 2 red; unwiring the retry from `executeQuery` turns 3 red.
- All four affected MCP servers boot over real stdio with pure-JSON stdout and register their tools
  (`powerplatform` 52, `powerplatform-customization` 88, `powerplatform-data` 14, `log-analytics`
  14).
- `flow --help`, `integration --help` and `query --help` list every changed command.
- Against fake credentials, `flow search`, `flow runs`, `flow workflows`, `integration audit`,
  `plugin list` and `query investigate-sync` all fail loudly at **exit 1 with empty stdout** and
  write no cache file.
- `query investigate-sync` with an unparseable workspace id now produces the same message through
  the same error path on both surfaces.

**Not verified:** every fix in this iteration is unit-verified only. There are no Azure,
PowerPlatform or Log Analytics credentials on the machine that produced it, so **no change here has
been exercised against a live environment.** The live-run checklist is in
`.claude/plans/cli-assurance-remediation.md`.

The retry policy in particular has never met a real 429 or 503 - its behaviour is asserted against
injected errors with an injected clock.

## Known Issues

Recorded in `docs/KNOWN_ISSUES.md` rather than fixed:

- **17 fan-outs still drop a per-item failure without recording it**, in `powerplatform-core` (6),
  `azure-devops` (5), `code-review` (5) and `audit-cli` (1). Measured this iteration, not converted.
- **Three `IntegrationAuditService` collections still fetch with `$top` and report no truncation**
  (`getServiceEndpoints`, `getEnvironmentVariables`, `getWebhookRegistrations`), and three failure
  paths in the same file are swallowed. The audit report's own `unverified` list names them, so the
  gap is visible to a reader rather than only recorded here.
- **`ValidationService.validateBestPractices` truncates its entity list by slicing it client-side**
  and returns no truncation flag of any kind.
- **535 em-dashes remain in `packages/*/src`**, including strings the CLIs print. Deliberately
  dropped from this iteration: it touches user-facing strings that tests match on, and it was never
  part of the assurance report.
- **`plugin list` gained a `description` key.** Additive, but a consumer that enumerates keys or
  snapshots the payload will see a new one.
- **`flow runs` may now take up to 7 seconds longer to fail** on a transient error, because it
  retries before giving up.
