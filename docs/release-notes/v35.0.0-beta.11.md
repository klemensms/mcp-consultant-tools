# Release Notes: v35.0.0-beta.11

**Date:** 2026-08-13
**Branch:** `release/35.0`
**Status:** Published to beta

> Per-iteration agent-level detail. The user-facing single source of truth is [`v35.0.0.md`](v35.0.0.md).

## Overview

Acts on the first live tenant run of the `code-review` Entra path shipped in beta.9. The headline is that **the feature works**: the client-credentials token is issued, sent and *accepted* by Azure DevOps, which rejects only the identity — a service principal that is not yet a member of the organisation. That is precisely the premise the feature request argued from, now confirmed rather than inferred.

The run found three defects, every one of which produced a confident, well-formed, wrong result rather than a loud failure — the same shape as the majority of the defects this tool set exists to surface.

`code-review` and `meta` only. No breaking change.

## Changes Implemented

- **`TF401444` quoted the tenant ID, not the principal's object ID** (introduced in beta.9). Azure DevOps names the rejected identity as a backslash triple, `tenant\tenant\principal`, and on a real response **all three segments are GUIDs**. `describeUnprovisionedPrincipal` took the first GUID in the message, so the error handed an organisation administrator the tenant ID labelled as the object ID — a Users search for it finds nothing. A new `extractPrincipalObjectId` takes the last backslash segment, falling back to the last GUID in the message when the identity is not backslash-separated.

  **Why the test did not catch it:** the fixture wrote the identity as `tenant\tenant\<guid>` using the literal word `tenant`, so "first GUID in the message" accidentally matched the object ID. The fixture now mirrors the measured three-GUID shape and asserts the tenant ID appears nowhere in the output.

- **Clone failures gave no route to the fix.** A clone authenticates separately from REST and receives no `TF401444` body — git reports only `fatal: Authentication failed`. Anyone whose first command happened to clone (`cr-check-dotnet`, `cr-complexity`, `cr-review` — eight of the ten tools) got a raw git error with nothing pointing at organisation membership. New `describeCloneAuthFailure` attaches the membership explanation under `entra-id` and a scope/expiry hint under `pat`. It returns null for a non-auth clone failure, so "repository not found" or a bad branch is never buried under an authentication guess.

- **The Azure DevOps `pat` clone path had never worked** (pre-existing since the package's first release, found while verifying the fix above). `buildAzdoCloneUrl` produced `https://<pat>@dev.azure.com/...`, putting the PAT in the **username** position and leaving git without the second credential field. Git prompted for it and failed locally with `could not read Password` before ever reaching Azure DevOps — regardless of whether the PAT was valid. It now produces `https://:<pat>@...`, matching the empty-username basic auth the REST path has always built (`Buffer.from(':' + pat)`).

  `buildGheCloneUrl` keeps its original `https://<token>@host` shape: that is the common GitHub idiom and has not been disproven, but no clone has ever been run against a real GitHub Enterprise host either. Flagged as unverified rather than changed blind.

- **Docs.** `packages/code-review/CLAUDE.md` gains the backslash-triple rule, the clone-mapping rationale, the PAT-position rule, and a rewritten verification-status section. `docs/technical/CODE_REVIEW_TECHNICAL.md` updates the `entra-id` subsection and `known-limitations`.

## Testing

**104 tests green** (up from 98), run against the clean release build.

**Both handler fixes were inversion-checked before being trusted.** Restoring the first-GUID parser turns exactly one test red; disabling the clone-failure matcher turns three red. New coverage:

- `TF401444` object-id extraction against a fixture carrying three GUIDs in the measured shape, asserting the tenant ID appears nowhere in the output.
- The no-backslash fallback path.
- Clone-failure mapping under `entra-id` (membership) and `pat` (scope/expiry), including git's `could not read Username/Password` form.
- A negative case asserting a non-auth clone failure is passed through unenriched.
- The corrected Azure DevOps clone URL, asserting explicitly that it is *not* the old username-position form.

**Runtime:** the corrected `pat` clone URL was run against `dev.azure.com` and confirmed to reach the server and return a genuine `fatal: Authentication failed` with the new hint attached — where the previous form died locally at a password prompt without ever making the request. The PAT remains redacted to `https://***@` in that output.

**Verified on the published artifact** (not just locally): `@mcp-consultant-tools/code-review@beta` resolves to `35.0.0-beta.3`, its server registers **10 tools** over real MCP stdio with the per-method validation live, the corrected clone URL reaches `dev.azure.com` and returns a genuine rejection with the new `pat` hint attached, and `mcp-consultant-tools@35.0.0-beta.11` pins `code-review@35.0.0-beta.3` (read with `--prefer-online`, since `npm view` serves a stale cache immediately after a publish).

**Live-test result (2026-08-13), beta.2 against a real tenant and Azure DevOps organisation:**

- The `entra-id` path works up to the identity check. The token is issued, sent and **accepted**; Azure DevOps rejects the identity with `TF401444`.
- The auth method is selected as configured, logged as `auth: entra-id` on every command, with **no fallback** — no PAT was present in the config at all.
- REST failures are loud: exit 1, and `--json` returns neither an empty result set nor a zero count.
- The bearer token is masked in the echoed clone command line (`Bearer ***`), so it cannot land in a log or terminal transcript.

## Known Issues

- **`entra-id` has still never authenticated to an accepted identity.** No service principal is yet a member of an Azure DevOps organisation, so no clone has ever succeeded and `cr-review` has never run end to end. Requested on Connect365 ticket #618258, unactioned as of 2026-08-13. Re-probing is a single read call.
- **The "unreadable repository fails loudly rather than returning an empty result" criterion is untestable** while every repository is unreadable — there is no readable case to contrast against. It is the criterion most worth proving once membership lands, and stays on the list.
- **The GitHub Enterprise clone URL is unverified.** It carries the same username-position shape that was just disproven for Azure DevOps. GitHub's idiom differs and it has not been disproven, but no clone has run against a real GHE host.
- **The documented `CR="npx …"` invocation idiom fails under zsh** for all six assurance CLIs, because zsh does not word-split an unquoted variable. This is a documentation defect in the consuming skills rather than in any package; a shell function (`cr() { npx … "$@"; }`) works in both shells.
- **`@mcp-consultant-tools/code-review` still carries a beta on its `latest` dist-tag** (`35.0.0-beta.1`). npm assigns `latest` on a package's first-ever publish regardless of `--tag`. Worth correcting when v35 is promoted.
