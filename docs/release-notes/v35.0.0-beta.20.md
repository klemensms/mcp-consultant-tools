# Release Notes: v35.0.0-beta.20

**Date:** 2026-08-24
**Branch:** `release/35.0`
**Status:** Published to beta

> Per-iteration agent-level detail. The user-facing single source of truth is [`v35.0.0.md`](v35.0.0.md).

## Overview

One defect, six call sites, three packages. The HTTP wrapper in `powerplatform`, `powerplatform-data` and `sharepoint` sent a JSON-RPC request through `InMemoryTransport` and only then installed the listener meant to receive the response. `InMemoryTransport.send()` is synchronous: it calls the other transport's `onmessage` inline, and where `onmessage` is unset it pushes to a `_messageQueue` that is only drained on `start()`, which never runs again on a connected transport.

The outcome therefore depended entirely on whether the SDK produced the response synchronously. A **known** method is dispatched through a promise chain, so its response arrives at least one microtask after the send, by which time the listener exists. An **unknown** method has no registered handler, so `Protocol._onrequest` sends `MethodNotFound` **inline, during the send**, while the listener slot is still empty. That response was pushed to the dead queue, the listener was installed a moment later, and nothing ever arrived.

Since 2026-08-11 claude.ai has health-checked connectors with a `server/discover` probe, which is exactly an unknown method. Every probe hung for the full 30s timeout and returned HTTP 500 `-32603`. Because the connected badge keys off the probe rather than off the session, connectors flapped between Connected and Not Connected while `initialize`, `notifications/initialized` and `tools/list` were all returning in 6 to 16ms alongside.

The SDK is behaving correctly throughout. Unknown methods failed because they fail fast.

## Changes Implemented

`9e9dbe2` - `fix: correlate MCP HTTP responses by request id instead of a shared handler`

- **One permanently installed `onmessage` handler per transport**, set when the transport is created in `initializeMcpServer()`, before anything can be sent through it. Nothing can now reach `_messageQueue`.
- **A `pendingResponses` map keyed by request id** replaces the per-request handler in the single mutable `onmessage` slot. A `sendAndAwaitResponse()` helper registers the resolver, sends, races against the 30s timeout, and clears both the timer and the map entry in a `finally`.
- **The resolver is registered before the send**, which is the ordering that fixes the reported bug. The helper carries a comment saying why, because the two statements look independent and are not.
- Applied at all six call sites: `POST /mcp` and the REST-to-MCP bridge in each of the three packages. The three copies are near-identical because there is no shared HTTP-server helper in `core`.
- **The REST bridge's request id moves from `Date.now()` to a sequential `rest-N` string.** At millisecond granularity two concurrent bridge calls could share a correlation key, which would reintroduce the same class of bug the map exists to close. The string prefix also guarantees no collision with the numeric ids a JSON-RPC client picks.
- **The notification path is unchanged**: `id === undefined` still sends and returns 202 without waiting. Its send moved inside the `isNotification` branch so the request path can register its resolver first.

### Two further defects closed by the same change

Both were latent in the old shape and are fixed as a consequence of correlating by id rather than by a shared slot.

1. **The slower of two overlapping requests was dropped.** `clientTransport.onmessage` was one mutable field, so request B's handler replaced request A's. A's response was then tested against B's id, discarded, and A timed out at 30s. This is not theoretical: measured against a server with a 400ms tool and an instant tool, two concurrent calls under the old shape return the fast one and time out the slow one. It went unnoticed because identical fast calls (four simultaneous `tools/list`) resolve in registration order and all pass.
2. **A dropped response was retained for the life of the process** in `_messageQueue`, which nothing drains after `start()`. Measured at 1 retained object across 5 timed-out probes rather than 5, because after the first drop the previous request's stale handler was still installed and silently discarded the rest - so the leak is bounded rather than unbounded, but it is real. With a permanent handler installed, nothing is queued at all.

## Testing

**Verified end to end against all three running servers**, from a clean rebuild.

Build hygiene: `build/` and every `tsconfig.tsbuildinfo` deleted before rebuilding, then the emitted `build/http-server.js` asserted to declare the correlation map and the helper, and to contain no `requestId = Date.now()`. The artifact was checked rather than the build being trusted to have re-emitted.

Transport-level, in a standalone harness against a real `McpServer` over `InMemoryTransport`:

| Check | Old shape | New shape |
|---|---|---|
| `server/discover` | TIMEOUT | `-32601` |
| `foo/bar` | TIMEOUT | `-32601` |
| Concurrent slow + fast tool call | slow one TIMEOUT | both correct |
| Concurrent slow + fast + unknown | all three TIMEOUT | all three correct |
| Sequential known calls | correct | correct |
| `_messageQueue` after 5 dropped probes | 1 retained object | 0 |

Over real HTTP, against each of the three built servers:

| Check | Result |
|---|---|
| `server/discover` | `-32601` in 2 to 3ms (was 30,000ms) |
| `foo/bar` | `-32601` in 2 to 3ms |
| `initialize` | 200 in 13 to 20ms |
| `notifications/initialized` | 202 in 3 to 4ms |
| `tools/list` | 14 / 52 / 22 tools |
| `tools/list` after an unknown method | same counts, unchanged |
| 6 concurrent (4 `tools/list`, 2 unknown) | all 6 correctly matched to their own ids, 6 to 7ms total |
| REST bridge, unknown tool name | 200 in ~14ms, no hang |
| 6 simultaneous REST-bridge calls | all answered, 18ms total |
| stdout | clean on all three servers |

**Not verified: anything requiring credentials.** Every check above is at the transport layer. No Dataverse or SharePoint call was made, and no tool's behaviour against a live environment changed in this iteration.

## Known Issues

- **There is still no shared HTTP-server helper in `core`, and no test covers any of this.** The three `http-server.ts` files are near-duplicates, which is why this was a six-site fix and why the OAuth-discovery 404 in beta.5 was a three-site fix. They are also untestable as they stand: each one calls `createEnvLoader()` and `app.listen()` at import time, so **this iteration adds no unit tests** - the suite stays at 1,205 - and the verification above is harness-driven against the built servers instead. A test asserting the correlation pattern without importing the real module would assert nothing about the real module. Extracting the wrapper into `core` is what would make a genuine regression test possible, and is deliberately not folded into a bug fix: a refactor across three published packages is a larger blast radius than the defect.
- **`powerplatform-data` and `sharepoint` expose no `bin` entry for their HTTP server** (only `powerplatform` does, as `mcp-pp-http`). Anyone hosting those two over HTTP has to invoke `build/http-server.js` by path.
- The 30s timeout is now close to unreachable through `POST /mcp`: every JSON-RPC method either has a handler or gets `MethodNotFound`. It remains as a backstop for a genuinely hung tool call.
