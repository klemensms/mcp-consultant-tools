# Release Notes: v35.0.0-beta.7

**Date:** 2026-08-12
**Branch:** `release/35.0`
**Status:** Published to beta

> Per-iteration agent-level detail. The user-facing single source of truth is [`v35.0.0.md`](v35.0.0.md).

## Overview

Acts on the first live-Teams test of beta.6. Six of the seven new beta.6 tools worked against real data, the eight-scope sign-in was accepted, and silent refresh worked end to end — the three things that could not be proven on the build machine. Testing surfaced one production defect, two minor CLI defects, one cosmetic nit, and evidence that two capabilities beta.6 documented as impossible in fact work.

This iteration fixes all four defects, ships the reaction tools that beta.6 left out, and corrects the two wrong "deliberately not implemented" claims. `teams` and `meta` only.

## Changes Implemented

### Bug fix — `list-teams` was broken in device-code mode (pre-existing, also affects `latest`)

`TeamsService.listTeams()` built one query for both auth modes and always applied `$top=100`. In device-code mode the endpoint is `/me/joinedTeams`, which rejects `$top` outright:

```
The query specified in the URI is not valid. Query option 'Top' is not allowed.
```

Every call failed with HTTP 400, MCP tool and CLI alike. Isolated live: the same request with `$select=id,displayName,description&$top=100` returns 400; without `$top` it returns 200. `$select` is fine.

`.top()` is now applied only on the client-credentials branch, whose `/groups?$filter=...` endpoint does accept it. No result bound is applied on `/me/joinedTeams` — how that endpoint behaves for a user in very many teams, and whether it paginates via `@odata.nextLink`, is untested, so no bound was invented.

**This is not a beta.6 regression.** `listTeams()` is byte-identical in `33.0.0`, the current `latest` tag, so `list-teams` is broken for every device-code user in production today. It never surfaced because the client-credentials path uses `/groups`, which accepts `$top`.

**Regression guard.** The existing suite could not have caught this: it stubs the fluent Graph chain and asserts *the query the code builds*, which is exactly the query Graph rejects. A new `teams-service.test.ts` asserts `.top()` is **never called** on `/me/joinedTeams` — an absence, not a match. The lesson is recorded in `packages/teams/CLAUDE.md`: for each endpoint, pin the query options it rejects, not only the ones it needs.

### New tools — reactions (+2, 16 total)

- **`react-to-channel-message`** — `POST /teams/{teamId}/channels/{channelId}/messages/{messageId}/setReaction` (or `/unsetReaction`), delegated `ChannelMessage.Send`. With `replyId`, targets `.../messages/{messageId}/replies/{replyId}/setReaction` instead.
- **`react-to-chat-message`** — `POST /chats/{chatId}/messages/{messageId}/setReaction` (or `/unsetReaction`), delegated `Chat.ReadWrite`.

Both take `reactionType` (`like` | `angry` | `sad` | `laugh` | `heart` | `surprised`, default `like`) and `action` (`add` | `remove`, default `add`). Graph requires `reactionType` on removal too, since a user may hold one reaction of each type on a message. Both permissions are already in the consented eight — **no ninth scope**, so no new consent step. Matching `mcp-teams-cli react-to-channel-message` / `react-to-chat-message` commands ship alongside (`--type`, `--remove`, `-r/--reply-id`).

### Bug fix — CLI reported the wrong version

`mcp-teams-cli -V` printed `27.0.0`, hardcoded in `src/cli.ts` while `package.json` said `35.0.0-beta.2`. It now reads `pkg.version` via `createRequire`, matching `powerplatform`, `azure-sql`, `entra-id`, `azure-defender`, `code-review` and `message-center`.

**Same defect in 19 sibling CLIs** — `1password`, `application-insights`, `azure-b2c`, `azure-data-factory`, `azure-devops`, `azure-devops-admin`, `azure-management`, `azure-storage`, `fabric`, `figma`, `github-enterprise`, `log-analytics`, `meta`, `powerplatform-customization`, `powerplatform-data`, `rest-api`, `service-bus`, `sharepoint`, `todoist` all report a stale literal (`meta` says `28.0.0-beta.8`; several say `27.0.0`). Deliberately **not** fixed here: it would touch every package in a Teams-only wave. Worth its own sweep.

### Bug fix — `mcp-teams-cli auth login` could not tell you whether sign-in worked

`startAuthentication()` returns as soon as the device code is issued, which is right for the MCP server (long-lived process; a later `auth-status` picks the result up) and wrong for a CLI. The command printed `Authentication status: pending`, exited 0, then lingered until the MSAL promise settled and printed nothing when it did. One live attempt sat for sixteen minutes, exited 0, and had written no token cache — indistinguishable at the terminal from success.

`auth login` now awaits `waitForAuthentication()` for the device code's own lifetime, prints the final status, and exits non-zero if sign-in did not complete. The explicit exit is needed because MSAL's poll timer and the wait timeout both keep the event loop alive past the point the answer is known. The MCP `authenticate` tool is unchanged.

### Cosmetic — stop showing Graph's enum placeholder

System messages render as `[system message]`, which is correct: Graph really does return `messageType: unknownFutureValue`, `from: null` and `body.content: <systemEventMessage/>` for these. The renderer was faithful and is unchanged.

The one nit was the visible flag `_(unknownFutureValue)_`. It is now suppressed when the type is `unknownFutureValue` **and** Graph supplied an `eventDetail` — i.e. when the type name is a placeholder for an event described elsewhere. A real `messageType`, and an `unknownFutureValue` with no `eventDetail` to explain it, both still show.

### Documentation — two "deliberately not implemented" claims were wrong

beta.6 dropped two capabilities on documentation grounds. Live testing disproved both, on the current eight scopes, with no ninth scope. The claims are corrected in `packages/teams/CLAUDE.md`, `docs/technical/TEAMS_TECHNICAL.md`, `docs/documentation/TEAMS.md` and `docs/release-notes/v35.0.0-beta.6.md` (struck through in place, with the correction).

- **`get-channel-messages-delta` works.** `GET /v1.0/teams/{teamId}/channels/{channelId}/messages/delta` returns 200 with delegated permissions from this registration. `/beta/` also returns 200 and additionally exposes `hasReplies` per message. Pages via `@odata.nextLink`. Implementation wrinkle for whoever builds it: **`$deltatoken=latest` is not honoured**, so a client must page to the end of history once before it receives its first `deltaLink`. The v1.0 response is undocumented but real — treat the shape as unstable.
- **`search-messages` works, and spans channels as well as chats.** `POST /v1.0/search/query` with `{"requests":[{"entityTypes":["chatMessage"],"query":{"queryString":"..."},"from":0,"size":N}]}` plus header `Prefer: include-unknown-enum-members` returns 200 with real hits **on `Chat.ReadWrite`, without `Chat.Read`** — Graph does not enforce its documented permission list as literally as the beta.6 note assumed. A phrase existing only in a channel post came back with `channelIdentity.teamId` and `channelIdentity.channelId` populated, so one tool would cover both surfaces. Each hit carries the message id, `chatId`, `webLink`, sender, `createdDateTime` and a highlighted summary. **Renderer caveat:** hits deliver the sender as `from.emailAddress.name`/`.address`, not the `from.user.displayName` shape `toMessageInfo()` expects — they need their own mapping path.

Neither is implemented in this wave. Both are real features deserving their own iteration; reactions was the one addition requested.

## Testing

**Automated.** 30 tests green (`npm run test --workspace=packages/teams`), up from 18:

- `teams-service.test.ts` (new, 3) — `/me/joinedTeams` must not receive `$top`; `/groups` must; response mapping.
- `format-messages.test.ts` (new, 3) — placeholder suppressed with an `eventDetail`, shown without one, real types still shown.
- `message-service.test.ts` (+6, now 24) — reaction paths for parent message, thread reply, removal (`unsetReaction`) and chat, the 403 stale-scope hint on a reaction, and `hasEventDetail` mapping.

**Inversion-checked.** Each new assertion was verified against a deliberately broken source before the suite was trusted: restoring the unconditional `.top()` fails the `$top` test; removing the placeholder guard fails the renderer test; forcing `setReaction` on removal fails the reaction test. All three went red, and the suite is green again with the sources restored.

**Runtime.** Clean build; the built server registers **16 tools** over real MCP stdio and `auth-status` returns cleanly, confirming no stray stdout corrupts the protocol. Verified again on the **published** artifact: `npx --package=@mcp-consultant-tools/teams@beta mcp-teams` registers 16 tools, `mcp-teams-cli --version` reports `35.0.0-beta.3`, and `npm view mcp-consultant-tools@beta dependencies` confirms the bundle pins `teams@35.0.0-beta.3` rather than the previous build. `react-to-channel-message` was called over stdio with a full argument set and reached the service (failing only at the auth gate, as expected without credentials). `mcp-teams-cli --version` now reports the package version, and both reaction commands appear with the expected flags.

**Not verified — needs the work machine.** No Teams credentials on this machine, so none of this wave has been exercised against live Teams. Specifically unproven: that `list-teams` now returns teams in device-code mode (the fix is derived from the isolated live probe, but the fixed code path has not itself been run); that reactions apply and clear on real messages; that `auth login` reports a real sign-in correctly end to end.

## Known Issues

- **`list-teams` is broken on the `latest` tag (`33.0.0`)** for every device-code user, for the same reason fixed here. Fixed only on the beta channel — a production patch may be warranted separately from the v35 promotion.
- 19 sibling CLIs still report hardcoded stale versions (see above). Not fixed in this wave.
