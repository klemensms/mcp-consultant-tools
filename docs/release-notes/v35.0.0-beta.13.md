# Release Notes: v35.0.0-beta.13

**Date:** 2026-08-13
**Branch:** `release/35.0`
**Status:** Published to beta

> Per-iteration agent-level detail. The user-facing single source of truth is [`v35.0.0.md`](v35.0.0.md).

## Overview

**Every MCP server and CLI in the suite now reports its real version.** One defect, 45 entrypoints, 26 packages — no behaviour changes beyond the version string itself, no new tools, no scope or configuration changes.

This started as a sweep of the 19 CLIs known to report stale versions. Checking the servers while there found something worse: **all 26 reported a fabricated version in the MCP initialize handshake**, which is the version an MCP client displays for the server.

## Changes Implemented

### Bug fix — every entrypoint reported a version it made up

Two separate populations, one root cause.

**19 CLIs carried a stale literal.** They ranged from mildly out of date to badly so — `application-insights`, `azure-b2c`, `azure-data-factory`, `azure-devops-admin`, `azure-management`, `github-enterprise`, `log-analytics`, `powerplatform-customization` and `sharepoint` all reported **`27.0.0`**; `azure-devops`, `azure-storage`, `figma`, `meta`, `rest-api` and `service-bus` reported `28.0.0-beta.8`; `1password` `29.0.0-beta.1`; `todoist` `30.0.0-beta.1`; `fabric` `31.0.0-beta.4`; `powerplatform-data` `32.0.0-beta.1`.

**All 26 servers reported a fabricated version.** Twenty-four said **`1.0.0`**, `meta` said `15.0.0`, `todoist` said `30.0.0-beta.1`. That string goes out in the MCP `initialize` response as `serverInfo.version`, so every client in every install has been shown `1.0.0` since these packages were first published.

Both now read from the package's own `package.json`:

```typescript
import { createRequire } from 'node:module';
const require = createRequire(import.meta.url);
const pkg = require('../package.json');
```

**Why `core`'s existing helper did not already prevent this.** `createCliProgram` wraps its `version` argument in `resolvePackageVersion()`, which walks up from `process.argv[1]` to the nearest `package.json`. That works when a build is executed directly — which is why `node packages/azure-devops/build/cli.js --version` printed the correct `35.0.0-beta.4` — and it **fails under `npx`**, where the bin shim lives in a different tree, so the hardcoded fallback is returned instead. npx is how these packages are actually consumed, so the literal was precisely what users saw. `createRequire(import.meta.url)` resolves against the module itself and is correct in both cases.

Seven CLIs already used this pattern and were left alone: `azure-defender`, `azure-sql`, `code-review`, `entra-id`, `message-center`, `powerplatform`, `teams`.

**This is cosmetic in the strict sense** — nothing behaved incorrectly because of it. It is still worth a wave: a version string is what you check first when diagnosing "am I running the fix?", and one that lies costs more than one that is merely absent. The `teams` beta.7 fix to `mcp-teams-cli --version` was made for exactly that reason after it hampered a live test.

## Testing

**Automated.** 815 tests green across 14 test-bearing packages (`meta` 9 → 12), full clean `build:release` with zero TypeScript errors across all 28 packages.

A new guard, `packages/meta/src/__tests__/entrypoint-versions.test.ts`, scans every `src/index.ts` and `src/cli.ts` in the monorepo and fails on any version literal, naming the offending file. It lives in `meta` because that is the package aggregating the whole suite. Three assertions:

1. It finds more than 20 entrypoints — so an empty or broken scan cannot pass vacuously. This matters more than it looks: a guard that silently finds nothing is worse than no guard, because it reports success.
2. No entrypoint passes a string literal as `version`.
3. Every entrypoint reads `require('../package.json')`.

**Inversion-checked.** Reverting `figma/src/cli.ts` to `version: '27.0.0'` turns the guard red and names `figma/src/cli.ts: '27.0.0'` in the failure. Restored, all 12 pass.

**Runtime, verified on both surfaces rather than assumed.** CLI `--version` was run on the built output for `figma`, `azure-devops`, `meta`, `todoist`, `sharepoint` and `rest-api`, each reporting its true version. Separately, four servers (`figma`, `teams`, `azure-devops`, `meta`) were connected over real MCP stdio and their `serverInfo.version` read back from the handshake — the surface that was wrong for every package — each now reporting correctly.

**Not verified:** the `npx` path itself can only be confirmed once published, since that is the whole point of the defect. Checking `mcp-ado-cli --version` over `npx --package=@mcp-consultant-tools/azure-devops@beta` is the single most useful post-publish check.

## Known Issues

Unchanged from beta.12: `sharepoint`'s CLI still ignores `--no-cache`; the Teams package still cannot post an @-mention; `auth login`'s exit code on a completed sign-in and the abandoned-device-code path remain unexercised; no tool can delete a message the agent sent; `list-teams` remains broken on the `latest` tag (`33.0.0`) for device-code users.
