# Release Notes: v35.0.0-beta.22

**Date:** 2026-08-31
**Branch:** `release/35.0`
**Status:** Published to beta

> Per-iteration agent-level detail. The user-facing single source of truth is [`v35.0.0.md`](v35.0.0.md).

## Overview

Single-defect iteration in the Teams inbound renderer, in the same file beta.21 fixed and for the same reason: **a read that silently returns less than it appears to.**

A Teams message longer than 1,500 characters could not be read in full through this server by any call. The cap was per message and fixed, so it took no account of how many messages were asked for, and there was no parameter that raised or bypassed it. The file header stated the opposite in as many words - *"the caller can narrow with `top` or a date range and read the rest"* - and that sentence was false.

It cost a real piece of work before it was found: a supplier's reply on a scoping decision had its closing position dropped, and the record built from it had to carry a warning that the tail was never retrieved. The truncation lands mid-sentence, and the reader has no way to tell whether the missing tail carries a figure, a commitment or a caveat.

`teams` and `meta` only. No config change, no new scope, no tool signature change.

## Changes Implemented

- **The per-message body cap is now one budget shared across the read.** `formatMessages` allocates a single 30,000-character budget over the messages it is rendering, rather than giving each message a fixed 1,500. Narrowing a read therefore does buy a bigger budget for the message you want, which is what the header always claimed.

  30,000 is deliberately what a default 20-message read cost under the old fixed cap, so an ordinary read is no more expensive than before while a one-message read can spend the whole budget on one message.

- **Allocation is max-min fair share, not an equal split.** An equal split alone would have been *worse* than the cap it replaces: a single long message inside a 50-message read would get 600 characters where it used to get 1,500. Shorter messages are served first and release whatever they do not use to the messages still waiting. Real reads are mostly short messages, so in practice one long message in an otherwise ordinary read now comes back whole.

  The consequence worth knowing: a wide read of uniformly long messages is now capped at 30,000 characters of body in total, where it was previously bounded only by 50 x 1,500 = 75,000. That is the hard total cap doing its job.

- **A truncation notice now says what to do next.** `[truncated, N more chars]` read as a dead end. It now carries a hint chosen from the read that produced it: a multi-message read is told to narrow to the one message it wants, and a single-message read - which has nothing left to narrow - is told the message is over the whole-read budget and to open it in Teams, rather than being sent round a loop that changes nothing.

- **Search hits carry the same courtesy.** `MAX_HIT_CHARS` stays at 600, because a hit is a pointer to a message rather than a read of one, but a clipped hit now names the tools that will fetch the whole thing. No behaviour change beyond the notice text.

- **The file header is corrected**, so it documents the escape hatch that now exists instead of one that never did.

## Testing

**167 tests green** in `teams` (up from 161); **1,263 green** across all 15 workspaces with tests, run against the clean release build.

Six new tests in `tools/__tests__/format-messages.test.ts`, written before the implementation and confirmed red first: a single long message returned whole; surplus from 19 short messages spent on one long one; a 50-message read of long messages held under the total cap; the multi-message hint present; the single-message hint present and the multi-message one absent; and an empty body still rendering.

**Verified live against a real tenant, not reasoned about.** A 2,279-character message was posted to a chat, then read back through two MCP clients against the same message:

| Build | Result |
|---|---|
| `35.0.0-beta.11` as shipped | `… [truncated, 779 more chars]`, tail absent |
| This build | full 2,279 characters, end marker present, at `top: 5` |

The rest of the package was exercised live in the same session and is unchanged: chat reads, channel reads, thread replies, search, `list-chats`, `list-teams`, `find-user`, both reaction directions, `update-chat-message`, `mark-chat-read`, and a `delete` / `undo-delete` round trip.

**One thing that was NOT retested:** channel message delete. It returned 403 on the last measurement and no channel message was posted in this session to try it against.

## Known Issues

- **Files can be seen but neither sent nor fetched.** A read names an attachment and hands back its URL, but no tool in the package fetches it and no tool sends one. `packages/sharepoint` already does the file half over `/drives/{driveId}/items/{itemId}/content`, and nothing wires the two together. Recorded in `docs/KNOWN_ISSUES.md` with the Graph route that would close it - resolving a sharing URL through `/shares/` needs no site or drive lookup - and the scope caveat that gates it: `Files.Read.All` is not in `DEVICE_CODE_SCOPES`, and an unconsented scope fails at sign-in and takes all 26 tools down rather than one.

- **The truncation notice's text changed.** Anything parsing the literal string `[truncated, N more chars]` and anchoring on the closing bracket will no longer match, since a hint now sits between the count and the bracket. Not treated as a breaking change - the notice is human-readable rendering inside a message body, not a payload field - but it is the one observable difference for a caller that was scraping the output.

- **Whether a message can be deleted is a tenant messaging-policy setting and it has moved once.** Chat delete returned 403 `AclCheckFailed` on 2026-08-20 and succeeded on 2026-08-31, so the policy was changed in between. `packages/teams/CLAUDE.md` now carries the measured state per surface with its date rather than a blanket claim.
