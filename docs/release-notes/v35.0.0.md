## ⚠️ This release contains breaking changes

**Only if you use the `teams` MCP server** (`@mcp-consultant-tools/teams`, or `meta` with Teams configured), and only in the default `device-code` auth mode.

From **beta.6** the Teams sign-in requests three delegated Microsoft Graph scopes it did not request before, and **beta.15 adds two more** (`User.ReadBasic.All`, `Chat.Create`) for the directory-lookup and direct-message tools. The request is now ten scopes, up from the original five. **An unconsented scope fails at sign-in rather than degrading**, so if your app registration has not been granted these, the Teams server stops working entirely — including the send-only tools that worked before.

Two one-off actions are needed: an admin grants consent for the added scopes, and you re-authenticate once. There are **no `.mcp.json` or environment-variable changes.**

If you already did this for beta.6, you need to do it again for the two scopes added in beta.15. **beta.16 adds no scopes** — if you have consented for beta.15, there is nothing further to grant.

**beta.16 adds a second, much smaller breaking change**, unrelated to consent and affecting both auth modes: `search-messages` takes **`top`** where it took `size`. It is a one-word change in a tool call or a `--size` flag, nothing in your config, and it only matters if you called that tool in the two hours beta.15 was current. See [⚠️ Upgrade Notes](#-upgrade-notes--breaking-changes).

- **Don't want to read further?** Copy the block under [⚡ Quick upgrade](#-quick-upgrade--copy-paste-for-your-claude-agent) into a fresh Claude conversation. Your agent will find the affected configs and tell you exactly which scopes to add — it cannot grant consent for you, that step is yours in the Entra portal.
- **Want the details?** See [⚠️ Upgrade Notes / Breaking Changes](#-upgrade-notes--breaking-changes).

Every other package in v35 is a drop-in upgrade.

## Overview

v35 began as a **security-hardening** release (tool safety annotations, dependency-vulnerability CI, `rest-api` fetch/TLS hardening) and, from **beta.3**, also delivers a **major read-only tooling expansion**: four new read-only servers (`azure-defender`, `entra-id`, `message-center`, `code-review`) and diagnostic/analysis suites added to `azure-sql`, `azure-management`, `azure-devops`, `powerplatform`, and `azure-data-factory`. **beta.6** adds message reading and chat support to `teams`, turning it from an announcement channel into something an agent can read and act on, and **beta.15** completes that arc — the server can now find people in the directory, direct-message them by name, search across channels and chats, and @-mention someone in a reply. Every addition is read-only unless explicitly gated behind a documented `*_ENABLE_*` flag.

No new required configuration and no `.mcp.json` changes anywhere in v35. The one exception to a clean drop-in upgrade is the `teams` server in device-code mode, which needs a one-off Entra admin consent and re-authentication — see the breaking-changes note above.

## Highlights

- **Every tool now carries MCP safety annotations** (`readOnlyHint` / `destructiveHint` / `openWorldHint`) — 589 tools across 21 packages — so clients can confirm before destructive operations and run read-only tools without friction.
- **Automated dependency-vulnerability surfacing** via Dependabot + an `npm audit` CI gate (previously zero automated detection).
- **`rest-api` hardening:** the OpenAPI-spec fetch is now bounded (scheme guard, no redirects, size cap) and the SSL-verification toggle no longer behaves misleadingly.
- **Team iteration capacity tools** (`azure-devops-admin`, beta.2): read and write per-member sprint capacity (capacity-per-day + days-off) and team-wide days-off — so an agent can reflect each resource's bookings into an ADO sprint. Read tools are always on; writes are gated behind a new opt-in flag.
- **Four new read-only servers** (beta.3): `azure-defender` (Defender for Cloud — secure score, assessments, compliance, attack paths), `entra-id` (app-registration credential-expiry + API-permission audit), `message-center` (M365 Service Health + Message Center), and `code-review` (provider-agnostic repo review — .NET EOL, NuGet vulnerability audit, complexity). 31 tools, all read-only.
- **Diagnostic & analysis suites on existing servers** (beta.3): `azure-sql` gains Query Store / session / space / index diagnostics (18 read-only + one gated index-create); `azure-management` gains Resource Graph, log streaming, and detectors (11 read-only); `azure-devops` gains build-issue, branch, and variable-group-diff tools (10 read-only); `powerplatform` gains environment flow-health scan + cloud-flow inventory; `azure-data-factory` gains debug-run history query.
- **Meta bundle no longer silently drops tools on a name collision** (beta.3): a duplicate tool name previously aborted a package's entire registration inside `meta`; it now skips just the colliding name (first package wins) and registers the rest.
- **`query-records` no longer under-reports its own results** (beta.5): the `powerplatform-data` tool capped at 5,000 rows and reported `hasMore: false`, so a caller was told a partial result set was complete. It now pages properly and derives `hasMore` from the Dataverse continuation token. If you have run bulk `query-records` pulls against tables with more than 5,000 matching rows on an earlier v35 beta, re-run them — the totals were wrong with no visible symptom.
- **`list-teams` worked in app-only mode and 400'd in device-code mode** (beta.7): the query always sent `$top`, which `/me/joinedTeams` rejects outright, so every `list-teams` call failed for anyone signed in as themselves. This is **not** a v35 regression — the same code ships in `33.0.0` on the `latest` tag, so it is broken in production today for device-code users. Fixed on the beta channel; a separate production patch may be warranted.
- **Teams gains reactions** (beta.7, **working from beta.8**): `react-to-channel-message` (including reactions on a single thread reply) and `react-to-chat-message`, both add and remove. Within the scopes consented in beta.6 — no new consent step. As shipped in beta.7 they failed on every call, sending the reaction's name where Graph wants the emoji; fixed in beta.8 with no change to how you call them. **If you are on beta.7, upgrade.**
- **`code-review` can authenticate to Azure DevOps as a service principal** (beta.9): `CODE_REVIEW_AZDO_AUTH_METHOD=entra-id` uses the same client ID / secret / tenant ID as every other server, so an unattended or scheduled run no longer depends on a PAT issued against a person and expiring on a fixed schedule. Optional and defaulting to `pat`, so nothing existing changes. It has one prerequisite config cannot satisfy: **the service principal must be added to the Azure DevOps organisation by an org administrator.** Until that is done, `entra-id` fails with a named error telling you exactly that — keep using `pat` in the meantime. **Live testing in beta.11 corrected that error**, which had been quoting the tenant ID where it promised the principal's object ID, and extended it to the clone path. **If you are on beta.9 or beta.10, upgrade** — and note that the same wave fixed an Azure DevOps `pat` clone path that had never worked at all.
- **Teams becomes readable, and stops asking you to sign in every hour** (beta.6): `teams` gains 7 tools — read channel messages and their thread replies, reply into a thread, and list/read/send/mark-read Teams chats. Separately, the device-code token now persists a refresh token and renews silently, replacing an hourly re-authentication prompt. Two prior defects made this necessary: two already-consented scopes were never requested (so any read would have failed with 403), and `offline_access` was consented but entirely unused. **Requires a one-off admin consent + re-authentication — see the breaking-changes note above.**

## 🚀 New Features

- **Team iteration capacity (`azure-devops-admin`).** A new `iteration-capacity` domain adds 5 tools: `get-iteration-capacities` and `get-team-days-off` (read-only, always available), plus `set-team-member-capacity`, `set-team-capacities-batch`, and `set-team-days-off` (gated behind `AZUREDEVOPS_ENABLE_ITERATION_CAPACITY_UPSERT=true`). Writes are full-replace of the targeted member's / team's capacity and days-off. The `member` argument accepts an identity GUID, email, or display name (resolved against the team's membership). Batch is one PATCH per member, so members you don't list are never wiped. A matching `capacity` CLI command group (alias `cap`) ships alongside. PAT needs `vso.work_write` for the write tools.
- **MCP tool safety annotations across all packages.** All tools in the integration packages declare `readOnlyHint`, `destructiveHint`, and (where they reach an external service) `openWorldHint`. Destructive operations (`delete-*`, `drop`, `deactivate-*`, arbitrary SQL/Dataverse executors, queue purges, access revocations, PR-merge-with-branch-delete, etc.) are marked so a client harness can prompt for confirmation; pure reads are marked so they run without friction. Annotations are advisory metadata — they change no tool behaviour or output shape.

### beta.3 — new servers

- **`azure-defender` (new, 12 read-only tools).** Microsoft Defender for Cloud: secure-score read, security assessments, regulatory-compliance state, recommendations, and attack-path enumeration. Subscription-scoped via the shared `AZURE_*` service principal (needs Security Reader).
- **`entra-id` (new, 2 read-only tools).** Audits Entra ID app registrations for expiring/expired client secrets & certificates and for over-broad API permissions. Uses Microsoft Graph `Application.Read.All` (directory), not subscription RBAC.
- **`message-center` (new, 7 read-only tools).** M365 Service Health and Message Center: current service-health overview, incident/advisory issues + incident reports, and Message Center change posts. Uses Graph `ServiceHealth.Read.All` + `ServiceMessage.Read.All`.
- **`code-review` (new, 10 read-only tools).** Provider-agnostic repository review across Azure DevOps / GitHub Enterprise / GitHub App: .NET target-framework EOL detection, NuGet dependency vulnerability audit, code-complexity metrics, and GitHub Packages inspection. NuGet lookups need no credential.

### beta.3 — tools added to existing servers

- **`azure-sql` (+18 read-only, +1 gated).** Query Store performance diagnostics (6), live session + tempdb/space diagnostics (8), and index health diagnostics (4, incl. `sql-create-fk-indexes` gated behind the new `SQL_ENABLE_INDEX_CREATE=true` — a schema-locking maintenance-window op).
- **`azure-management` (+11 read-only).** Azure Resource Graph queries, App Service / Function log streaming, and Defender-style resource detectors.
- **`azure-devops` / `azure-devops-admin` (+10 read-only).** Build-timeline issue extraction, git branch/ref listing, and read-only variable-group diffing (split across the two ADO packages by domain).
- **`powerplatform` (+2 read-only).** `scan-flow-health` (environment-wide cloud-flow run-health scan — per-flow + overall success rate over N days) and `get-flow-inventory` (complete paginated cloud-flow inventory). Both app-only via the Dataverse `workflow` + `flowrun` tables.
- **`azure-data-factory` (+1 read-only).** `adf-query-debug-pipeline-runs` — debug-mode pipeline run history via the (undocumented but real, app-only) `queryDebugPipelineRuns` ARM action; honest truncation reporting and status-casing normalization.

### beta.4 — tools added to existing servers

- **`azure-devops` (+1 read-only).** `pr diff` retrieves a pull request's changes as a unified diff rather than only the changed-file list. `mcp-ado-cli pr diff <project> <repo> <prId>` with `--patch-only`, `--path <p...>`, `--context <n>` and `-i <n>`, plus the matching MCP tool.
- **`powerplatform` (+1 read-only).** `plugin steps` returns an environment-wide plugin step inventory — `mcp-pp-cli plugin steps` with `--no-include-disabled` and `-m <n>`. The implementation (`PluginService.getAllPluginSteps`) lands in `powerplatform-core`; `powerplatform` wires up the CLI command and tool.
- **`log-analytics` (structured output).** `query investigate-app` gains `-f json`. Formatting moved out of the command and the tool into a shared service plus a formatters utility, so the CLI and MCP paths render from one code path instead of two divergent copies.

### beta.6 — Teams message reads & chats

- **`teams` (+7 tools, 4 read-only).** The server could previously only post: nothing read a message, and nothing knew chats existed.
  - **Channel reads (read-only):** `get-channel-messages` (recent messages, newest first) and `get-message-replies` (replies to one message). Reads default to the 20 most recent and cap at Graph's maximum of 50, with `top` plus `since`/`until` range parameters. Channel reads deliberately do **not** expand each thread's replies — a wide skim stays cheap, and you pass a returned message ID to `get-message-replies` for the threads worth opening.
  - **Channel write:** `reply-to-message` posts into an existing thread rather than starting a new one.
  - **Chats:** `list-chats` (read-only, 1:1 / group / meeting, most recently active first, optional member names), `get-chat-messages` (read-only), `send-chat-message`, and `mark-chat-read`.
  - Messages render for a reader rather than as raw Graph JSON: author display name, timestamp, body flattened to plain text with the HTML stripped and `<at>` mentions shown as `@Name`, plus the message ID — the ID is what a reply call needs next. Long bodies are truncated per message so one wide read cannot exhaust a context window.
  - All 7 have matching `mcp-teams-cli` commands.

### beta.7 — Teams reactions

- **`teams` (+2 tools, 16 total).** `react-to-channel-message` and `react-to-chat-message` add or remove an emoji reaction as the signed-in user. `reactionType` accepts the six Graph v1.0 values (`like`, `angry`, `sad`, `laugh`, `heart`, `surprised`, default `like`); `action: "remove"` clears one. The channel tool takes an optional `replyId` to react to a single reply inside a thread rather than the parent message. Both permissions (`ChannelMessage.Send`, `Chat.ReadWrite`) are already in the eight consented in beta.6, so **no additional consent is needed**. Matching `mcp-teams-cli` commands ship alongside.

  ⚠️ **These tools did not work until beta.8** — every call returned HTTP 400. Fixed in beta.8; nothing about how you call them changed.

### beta.9 — Azure DevOps service-principal auth for `code-review`

- **`code-review` gains an authentication choice for the `azure-devops` provider.** A new optional `CODE_REVIEW_AZDO_AUTH_METHOD` selects `pat` (the default when the variable is absent, so **no existing config changes**) or `entra-id`, which authenticates with `CODE_REVIEW_AZDO_CLIENT_ID` / `CODE_REVIEW_AZDO_CLIENT_SECRET` / `CODE_REVIEW_AZDO_TENANT_ID` — the same client-credentials trio every other server in the family uses. This was the only CLI in the set that could not use the shared Entra app registration, which meant an assurance run's access was tied to whoever's PAT was in the config, and would eventually fail on PAT expiry for a reason unrelated to the tenant being assessed.

  Under `entra-id` the credential also reaches `git clone` — eight of the ten tools clone the repository, so REST-only auth would have left `cr-list-repos` working and every analysis tool failing. The clone URL carries no credential at all in this mode; the token travels in `git -c http.extraHeader`, and is redacted from any clone error.

  **Prerequisite:** the service principal must be a member of the target Azure DevOps organisation. Azure DevOps issues *and accepts* the token regardless, then rejects the identity with `401 TF401444` — which reads as "wrong secret" if reported as a bare 401. It is reported instead as a named error carrying the principal's object ID, so an org administrator can add it under **Organization settings > Users**. Until that is done for a given organisation, keep using `pat` there.

### beta.15 — Teams directory lookup, direct messages, search and @-mentions

- **`send-direct-message` — message anyone by name or email, without knowing a chat ID.** Resolves the person in the directory, reuses your existing one-on-one chat with them when there is one, and only opens a new chat when there is not. If the name matches more than one person it reports the candidates and sends nothing, rather than guessing — messaging the wrong colleague is not recoverable. Duplicate threads are guarded twice: by that lookup, and by Graph itself, which returns the existing one-on-one chat rather than creating a second.

- **`find-user` — search the organisation's directory** by name, email or user principal name. Returns display name, email, job title and the AAD user ID that an @-mention needs.

- **`search-messages` — keyword search spanning channels *and* chats in one call.** The cheapest way to answer "where was this discussed" without knowing which team, channel or chat to look in. Each hit carries the IDs needed to read the surrounding thread.

- **`get-channel-messages-delta` — read only what changed** in a channel since a previous call. Note that a first call is expensive: Graph does not honour `$deltatoken=latest`, so a cold start pages the channel's history to establish a delta token. `maxPages` bounds that walk, and a truncated walk deliberately returns **no** delta token, because one taken from a partial walk would silently skip history. For a one-off skim, `get-channel-messages` remains cheaper.

- **@-mentions on every outbound message.** Write `@[Name or email]` inline in any message sent by `send-channel-message`, `reply-to-message`, `send-chat-message` or `send-direct-message`, and it is sent as a real Teams mention that notifies the person. An ambiguous or unresolvable name reports back and sends nothing. A message with no mention markers makes no directory call at all.

- **No `edit-channel-message`, and there cannot be one on this permission set.** Editing a channel message's content requires `ChannelMessage.ReadWrite`; the similarly-named `ChannelMessage.Edit` has no published Graph method behind it. Do not add that permission expecting it to work.

## ⚠️ Upgrade Notes / Breaking Changes

- **`search-messages` takes `top`, not `size`** (beta.16). The parameter is renamed on both the MCP tool and the CLI (`--size` → `--top`), for consistency with the other five reads in the package, all of which already said `top`. It was the odd one out and callers reliably reached for `top` first.

  **Only affects you if you called `search-messages` while beta.15 was current.** Update the parameter name; nothing else changes, and there is no config or consent implication. Note the failure mode differs by surface: the CLI rejects `--size` by name, but the **MCP tool silently ignores an unknown `size` and returns the default 20 hits** rather than erroring — so a call asking for 50 quietly gets 20. Graph's own wire field is still `size`; only the tool parameter changed.

- **A guest is no longer messaged or mentioned from a bare name** (beta.16). `send-direct-message` and `@[...]` mentions now refuse a recipient who is a guest in your directory unless you name them by their exact email address, and tell you the address to re-run with. Previously any unambiguous match was sent to.

  This is a **behaviour change on a path that previously worked**, which is why it is listed here rather than under bug fixes — a script that DMs an external collaborator by first name will now stop. Give it the full email address and it goes through. The reasoning is in the [beta.16 entry under 🐛 Bug Fixes](#-bug-fixes); the short version is that your directory contains suppliers, client contacts and personal addresses alongside colleagues, and a first name matching exactly one of them is *unambiguous*, so nothing stopped it.

- **`teams` device-code sign-in requests two further delegated scopes** (beta.15): `User.ReadBasic.All` and `Chat.Create`, which back `find-user`, `send-direct-message` and @-mentions. The full request is now ten scopes.

  **This breaks for the same reason beta.6 did** — an unconsented scope fails the whole sign-in rather than disabling one tool, so a registration consented only to the beta.6 set of eight will stop authenticating entirely. **If you already performed the beta.6 consent step, you must perform it again for these two.** Same procedure: an admin grants consent on the registration behind `TEAMS_CLIENT_ID`, then `logout` followed by `authenticate`. No `.mcp.json` or environment-variable change.

  **Do not add `ChannelMessage.Edit`** even though it appears adjacent in the portal — nothing consumes it.

- **`teams` device-code sign-in now requests three additional delegated scopes** (beta.6): `ChannelMessage.Read.All`, `Chat.ReadWrite` and `offline_access`, joining the existing `User.Read`, `Team.ReadBasic.All`, `Channel.ReadBasic.All`, `ChannelMessage.Send` and `Group.Read.All`.

  **Why this breaks rather than degrades.** In a tenant where only `User.Read`, `email`, `openid` and `profile` are classified low impact, an unconsented scope cannot be self-consented — the whole sign-in fails, not just the tool that needed the new scope. A registration still holding only the original five scopes will therefore fail to authenticate at all, taking the previously-working send tools down with it.

  **What to do (once):** an admin grants consent for all eight scopes on the registration behind `TEAMS_CLIENT_ID`, then you call `logout` followed by `authenticate` and complete the device-code sign-in. No `.mcp.json` or environment-variable change. The paste-ready agent prompt is at the top of this document.

  **Unaffected:** servers running `TEAMS_AUTH_MODE=client-credentials`. Application permissions are unchanged, and that path does not use the device-code scope list.

- **The cached Teams token is discarded on first run of beta.6** (beta.6). The pre-beta.6 format was a plaintext `~/.mcp-consultant-tools/teams-auth.json` holding a bare access token — five scopes, no refresh token. It is deleted rather than migrated, because silently reusing a narrower token produces a 403 on every read tool with no visible cause. Expect exactly one extra device-code sign-in; from then on renewal is silent.

## 🔧 Technical Improvements / Architecture

- **`rest-api` OpenAPI-spec fetch is now bounded** (`doFetchOpenApiSpec`): rejects non-`http(s)` spec URLs (e.g. `file://`), never follows redirects (`redirect: "error"`), and caps the response at 10 MB (Content-Length pre-check + post-read byte check) to guard against memory exhaustion. This brings the spec-fetch path in line with the main request path's v34 hardening.
- **`teams` token storage is now an encrypted MSAL cache** (beta.6). A new `TokenCache` registers an MSAL `ICachePlugin` on the `PublicClientApplication`, persisting the serialized cache — access token *and* refresh token — as AES-256-GCM ciphertext under a key derived from hostname + username, at file mode 0600. This replaces a plaintext JSON file containing a bare bearer token. A cache copied to another machine cannot be decrypted, and a decrypt failure degrades to a normal device-code sign-in.
- **`teams` service split** (beta.6). Message reads, replies and chat operations live in a new `MessageService` that shares `TeamsService`'s authenticated Graph client rather than owning authentication, so there is one token cache and one sign-in for the package. `markdownToHtml` — previously duplicated as a private function in both the MCP tool and the CLI command — is extracted to a single `message-content.ts` alongside a new `htmlToText`, and every outbound message routes through the shared sanitizer.

## 🐛 Bug Fixes

- **Teams could message someone outside your organisation from a first name, with no warning** (beta.16, found by the first live test of beta.15). The directory search that backs `find-user`, `send-direct-message` and @-mentions returns guests as readily as colleagues — on the test tenant, a single common first name returned six people, **four of them at other companies**, including one personal Gmail address. The ambiguity guard did not cover this and could not have: a name matching exactly one supplier and *no* colleague **is** unambiguous, so it resolved cleanly and would have sent to a stranger at another company with nothing said about it. The same exposure applied to `@[...]` in a channel post, which notifies the person and hands them the thread.

  A guest is now resolved **only from their exact email address** (or their `#EXT#` UPN). A name — even their full display name — is refused, with the address named so the retry is obvious. Guests are also marked as such in `find-user` output and in the candidate list of an ambiguous match. Messaging an external collaborator on purpose still works; you just have to say who. Detection reads the guest marker in the user principal name rather than `userType`, which needs a permission this registration does not have and returns `null` without it.

- **Every `search-messages` hit came back without its link** (beta.16). A search hit names its deep link `webLink`; every other message endpoint in Graph calls the same field `webUrl`, and the mapper read that. Reading an absent property is silent, so the field was simply never populated and nothing indicated why — and the renderer did not print the link even when present, so both halves were broken independently. Each hit now shows a `View:` link.

- **The team ID on a `search-messages` hit could not be used to read the message** (beta.16). A hit from a **private channel** carries that channel's own backing group rather than the parent team, so feeding it straight into `get-channel-messages` fails with `Group ID '…' is not found` — an error that reads like a permissions or deletion problem rather than a wrong argument, which is the expensive part. The value came from Graph unaltered, so this was a trap rather than a mapping mistake. Each channel hit's team is now confirmed against the teams you are in (one call, which settles the ordinary case) and only falls back to a channel walk for a hit that fails it. A hit whose team cannot be identified **loses the field and says so**, rather than handing back an ID that will fail — the point of returning IDs at all is that a follow-up read can use them.

- **21 CLI write commands still wrote a cache file into the caller's directory** (beta.14, gap left by beta.12). Beta.12 took the write-cache convention repo-wide but classified commands with a verb-prefix regex, which guesses intent from a name. It missed `batch-create`, `push`, `push-tasks`, `str-replace`, `vote`, `copy` (twice), `receive`, `insert`, `upsert`, `batch`, `unassign`, `unassign-workspaces`, `archive`, `batch-delete`, `disassociate`, `queue` and three `drop`/`insert` commands in `azure-sql`. The rule is now the one the repo already documents to itself: **a command whose own `.description()` tells you to set an `ENABLE_*_WRITE=true` or `ENABLE_*_DELETE=true` flag is a write.** It needs no judgement and it gets right the case verb-matching must get wrong — `azure-storage queue receive` reads like a read, but receiving hides the message and changes its visibility, which is why it sits behind the write flag. A guard test now enforces it across the monorepo. `rest-api batch` deliberately keeps its cache: its payload is the actual response bodies, which is the thing worth grepping.
- **`code-review`'s clone hint never appeared, and its clone error said less than the previous release's** (beta.14, reported against beta.3). Under `entra-id`, a clone-path command returned a bare `Git clone failed: … Cloning into '<dir>'…` with no membership paragraph — and unlike beta.2, without git's own `fatal: Authentication failed` line. Both symptoms are one bug, and the hint logic was never at fault: the Entra clone path is byte-identical between the two releases. Left to itself git answers a rejected credential with an **interactive credential prompt**, and on a machine with a controlling terminal it blocks until the 120-second timeout kills it — and a killed git has printed only `Cloning into '<dir>'...`, so the authentication text the hint matches on never reaches the caller. Which message you got depended on whether a credential happened to be cached on that machine, which is why two builds sharing the same code behaved differently. The clone now runs unattended (`GIT_TERMINAL_PROMPT=0`, both askpass escapes emptied, and `-c credential.helper=` so a machine keychain cannot answer with a stale or someone else's credential), failing immediately with `could not read Username … terminal prompts disabled` — which the existing matcher recognises, so the hint attaches. A clone killed by the timeout now says so rather than presenting a truncated message as the whole story.

- **Every MCP server and CLI reported a version it made up** (beta.13). 19 CLIs carried stale string literals — nine said `27.0.0`, others `28.0.0-beta.8`, `29.0.0-beta.1`, `30.0.0-beta.1`, `31.0.0-beta.4` and `32.0.0-beta.1`. Separately and more visibly, **all 26 servers reported a fabricated version in the MCP `initialize` handshake**: 24 said `1.0.0`, `meta` said `15.0.0`. - **Teams message reads mangled mentions and swallowed emoji** (beta.10). Graph emits **one `<at>` element per word** of a mention — each with its own `mentions[]` entry, all resolving to the same entity — so a two-word name rendered as `@Jane @Doe`. Runs of `<at>` elements are now coalesced, keyed on the resolved entity id rather than on adjacency, so two different people mentioned back to back are still rendered as two mentions. Separately, Teams encodes emoji as an element carrying the character in an `alt` attribute with no text content, so every emoji was silently dropped from every message body; the character is now rendered.
- **Teams `list-chats` showed a "Last activity" date it was not sorting by** (beta.10). The list is ordered by the last message's timestamp, but the column displayed `lastUpdatedDateTime` — which tracks changes to the chat itself, such as topic or membership, not messages in it. Measured live, the most recently active chat in the list displayed a date **six weeks stale**, which reads as a colleague who has gone quiet rather than one who messaged that morning. The cause is that `/me/chats` will order by `lastMessagePreview/createdDateTime` **without returning it** — it needs `$expand` — so the sort key was never in the response. It is now expanded and displayed. Ordering was never affected.
- **Teams CLI write commands left a cache file in whatever directory they were run from** (beta.10). A reaction or send command created `.context/.mcp-teams-cache/<command>.json` in the caller's working directory — on one machine, inside a cloud-synced folder, which then synced it. Write commands now persist nothing; their payload was only an echo of the arguments. **Read commands still cache**, since that JSON is the point. Fixed in `teams` only — see Known Issues.

- **`rest-api` SSL-verification toggle was a silent no-op.** `REST_ENABLE_SSL_VERIFY=false` created an `https.Agent` that native `fetch` ignores, so TLS was always verified regardless of the setting. The misleading dead agent is removed. The server now **never disables TLS on the operator's behalf**; if `REST_ENABLE_SSL_VERIFY=false` is set it emits a loud security warning and directs the operator to set `NODE_TLS_REJECT_UNAUTHORIZED` in the environment themselves if they genuinely must (keeping the insecure scope explicit at deploy time). - **`query-records` silently truncated at 5,000 rows and claimed completeness** (beta.5). `DataService.queryRecords` asked for `$top = maxRecords + 1` and inferred `hasMore` from `value.length > maxRecords`. Dataverse caps every response at 5,000 rows whatever `$top` requests, so at `maxRecords: 5000` the sentinel row could never return — the server gave exactly 5,000, the comparison evaluated false, and the tool reported `hasMore: false` while dropping every row past the cap. A window holding 8,323 rows returned 5,000 and reported nothing missing. `$top` cannot detect this either: it is client-driven paging, so no `@odata.nextLink` accompanies it, and Dataverse ignores `$top` entirely when a page-size preference is present. Now uses server-driven paging (`Prefer: odata.maxpagesize` + following `@odata.nextLink`), with `hasMore` derived from the continuation token rather than a row count. `maxRecords` above 5,000 is now genuinely served — one extra API call per 5,000 rows — instead of silently capped, so the `max: 5000` wording in the tool description and technical doc is updated.

- **`powerplatform`, `powerplatform-data` and `sharepoint` HTTP servers returned 401 on OAuth discovery paths** (beta.5). A 401 there tells an MCP client "OAuth is supported, you are unauthorized" — the client then starts an authorization flow that can never complete and reports "authentication failed", while the API key works fine and `initialize` / `tools/list` keep returning 200. A guard now runs before the auth middleware.
- **`teams` requested only five of its eight consented scopes** (beta.6). The device-code flow asked for `User.Read`, `Team.ReadBasic.All`, `Channel.ReadBasic.All`, `ChannelMessage.Send` and `Group.Read.All`. `ChannelMessage.Read.All` and `Chat.ReadWrite` were consented tenant-wide but never requested, so the cached token never carried them — any message-read or chat call would have failed with 403 for a reason invisible from the error text. Now all eight are requested. - **`teams` had no token refresh at all, so sign-in expired hourly** (beta.6). The package persisted a bare access token and had no MSAL token cache and no silent-refresh path. When the access token expired after ~1 hour, the next call threw "Not authenticated" and a human had to redo the device-code flow — while `offline_access` sat consented and unused. The MSAL cache now persists the refresh token, and token acquisition tries the in-memory token, then `getAllAccounts()` + `acquireTokenSilent()`, before reporting not-authenticated. `InteractionRequiredAuthError` (refresh token expired or revoked) falls back to device code; other errors propagate rather than being flattened into a misleading "not authenticated". `auth-status` also attempts a silent refresh, so an expired access token backed by a live refresh token reports `authenticated` instead of sending you to sign in.
- **`teams` `logout` left the account recoverable in-process** (beta.6). - **`teams` `list-teams` failed with HTTP 400 in device-code mode** (beta.7, pre-existing). `listTeams()` built one query for both auth modes and always applied `$top=100`. Device-code mode reads `/me/joinedTeams`, which rejects that outright — `The query specified in the URI is not valid. Query option 'Top' is not allowed` — so every call failed, MCP tool and CLI alike. `$top` is now applied only on the client-credentials `/groups` path, which accepts it. ## Known Issues

Confirmed defects recorded in [`docs/KNOWN_ISSUES.md`](../KNOWN_ISSUES.md) and deliberately not fixed in v35. None is introduced by this release.

- `createPiiPipelineFromEnv` discards its options argument — the parameter is declared `_options` and the body only calls `loadPiiConfig()`, so the `environmentIdentifier` passed by four call sites has no effect.
- The "environment looks unprotected" warning is dead code: `checkEnvironmentLooksUnprotected` has zero call sites, and `MCP_ENVIRONMENT_TYPE` is read by no production code path. Setting it does nothing.
- **`list-teams` is broken on the `latest` tag (`33.0.0`)** for every device-code user (surfaced in beta.7). Fixed on the beta channel only; a production patch is a separate decision from promoting v35.
- ~~**Teams mentions render as one `@` per word**~~ · ~~**`list-chats` shows a "Last activity" column that disagrees with its own sort order**~~ · ~~**message reads drop `<emoji>` elements**~~ (surfaced in beta.8) — **all three fixed in beta.10.**
- ~~**The CLIs write their response cache into the current working directory**~~ (surfaced in beta.8) — **fixed in `teams` in beta.10, across the repo in beta.12, and completed in beta.14.** The beta.12 sweep classified commands by verb prefix and missed 21; those are marked as of beta.14, and a guard test now enforces the rule. **Read commands still cache into the working directory by design** — that JSON is the point. It does mean the working directory is part of the invocation: a read started in the wrong folder leaves repository or record data there, which on a client engagement is client data in an untracked place. Start runs from the intended folder, treat any `.context/` as confidential, and use `--no-cache` to suppress the file.
- **`sharepoint`'s CLI ignores the global `--no-cache` flag.** Its `outputResult` is a bespoke implementation that never reads the global flags, so a read command always writes its cache file with no way to opt out. Pre-existing and unrelated to the beta.12 sweep, which did give it the write-command fix. Honouring the flag means threading `flags` through every call site in that package.
- **Four packages that debuted mid-beta carry a prerelease on their `latest` tag** — `code-review`, `azure-defender`, `entra-id`, `message-center`. npm assigns `latest` on a package's first-ever publish regardless of `--tag beta`. Harmless for anyone pinned to `@beta`, but a bare `npm install` resolves to a prerelease. Corrected at v35 promotion, not mid-beta.
- ~~**The Teams package cannot post an @-mention**~~ (surfaced in beta.12 testing) — **fixed in beta.15 and confirmed live on 2026-08-13.** All four outbound paths accept `@[Name or email]` inline and send a real mention that notifies the person.
- **`send-direct-message` reports `chatExisted: false` for an existing chat past your 250th** (surfaced in beta.16 review). The existing-chat lookup walks 5 pages of 50. Past that it reports a new chat where there was an old one; it does **not** create a duplicate, because Graph returns the existing one-on-one chat rather than opening a second. A label, not a lost message. Similarly, `search-messages` walks at most 20 teams when repairing a channel hit's team id, and a hit in the 21st team keeps no team id rather than a wrong one.
- **No tool can delete a message the agent itself sent** (surfaced in beta.8). Nothing in the package can clean up after a verification run. Raised as a feature idea; not scoped.
- **The `$top = maxRecords + 1` completeness check survives in three other `powerplatform-core` services** (beta.5) — `MetadataService.getGlobalOptionSets`, `WorkflowService.getWorkflows` and `FlowService.getFlows`. This is the same false-completeness defect fixed in `query-records`: each will report `hasMore: false` on a truncated result wherever its result set can reach the 5,000-row page cap. `FlowService.getFlowInventory` is unaffected — it already pages via `@odata.nextLink`.
