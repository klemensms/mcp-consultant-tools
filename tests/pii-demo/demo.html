The pipeline at a glance

Four layers, each catching what the previous one missed. Configurable per-deployment; the v1 default has all four active.

Layer 1 · request side
Query-time exclusion
Strips configured PII fields from $select before the request leaves. Data never reaches us.
Layer 2 · response shape
Configured-field redaction
Replaces values in known PII fields with synthetic tokens. Cheap, deterministic, auditable.
Layer 3 · free text
Regex on every string
Catches structured PII (email, phone, ISO date) in any field regardless of name.
Layer 4 · free text
NER on configured fields
Catches person names that don't match any pattern. Compromise.js multilingual NER.
Audit · pre-flight
Observe mode
Pipeline runs but values pass through unchanged. Footer reports what would have been redacted.

Query 2 · Cross-call correlation

query-records contacts $filter=firstname eq 'Maria' $select=firstname,lastname,emailaddress1

Same Maria, different filter. Within one MCP server process the tokens must match across calls — otherwise the agent loses track of "is this the same person we just looked at?"

Scenario firstname lastname Match Q1?

l1-exclusion (absent — stripped from $select) (absent — stripped from $select) —

Tokens differ across scenarios because each MCP server process has its own random salt. They are deterministic within a single process lifetime — that's what makes the agent's reasoning still work across multiple tool calls. Restart the server and the salt rotates, breaking long-term correlation by design (privacy boundary).

Both findings closed in beta.4

  1. yomifullname redacts (F4). Added the Yomi family (yomifirstname, yomimiddlename, yomilastname, yomifullname) plus middlename to default L2 contact rules in packages/core/src/pii/config.ts. Same yomi family also added to default lead and systemuser rules per F7.
  2. [PII protection: …] audit footer emits on writes (F5). Refactored DataService.{getRecord,createRecord,updateRecord,executeAction} to embed piiReport as a sibling key on the result object; the powerplatform-data tool layer extracts it and appends formatSummaryFooter(piiReport) to the response text. Same pattern applied to azure-devops work-item-tools (6 tools).

The same audit-footer extension is needed on azure-sql (sql-execute-query, sql-execute-sproc, sql-execute-unrestricted) and rest-api (rest-request) tool layers — services already wrap piiReport since beta.3, only the tool layer discards. Carries to v1.6 because those surfaces aren't exercised by this demo. executeAction on Dataverse is closed in beta.4 as part of the powerplatform-data fix.

Override-replacement gotcha (visible in scenario 2 / l1-exclusion)

In the l1-exclusion scenario specifically, yomifullname still returns raw "Maria Schmidt" — because that scenario's PII_CONFIG_PATH JSON explicitly overrides fieldRules.contact.redactInResponse with a list authored before beta.4 (no Yomi family). PII_CONFIG_PATH overrides are not additive: when you set a contact field list in your config, defaults are replaced, not merged. Documented in docs/documentation/pii-protection.md. Workaround: either remove the contact entry from your override to inherit defaults, or carry the new yomi-family lines forward in your override.

Cross-cutting findings

  1. L1 is the strongest GDPR posture but has scope. Field-exclusion only works for fields that are well-typed PII and not needed for the agent's investigation. For description / notetext-style free text, L1 isn't an option — the field is needed for context, you just want the values inside it tokenised.
  2. L2 + L3 + L4 combine multiplicatively. L2 catches 100 % of configured fields cheaply. L3 picks up most free-text PII (anything email-shaped, phone-shaped, ISO-date-shaped). L4 catches the remaining cases (person names that don't fit any pattern). Each layer's job gets smaller as you add the next.
  3. Cross-call correlation works on read AND write. Same person → same token within one process, across query→update boundaries. Different processes → different tokens. The agent can reason about identity across multiple tool calls without the platform retaining any mapping.
  4. The annotation entity proves defense in depth. With L2 only, the annotation note leaks every PII shape it contains. With L2 + L3 + L4, every PII shape except locale-specific date formats is caught. No single layer is sufficient.
  5. Observe-mode footer counts upper-bound the real work. Useful for "what would happen if we turned protection on" planning. Don't compare them directly to redaction-on counts — when redaction is active, L2 replaces a value first and L3/L4 see the synthetic token, so they don't double-count.
  6. Closed in beta.3: annotations are in scope (Finding 1 → Q4); custom regex extension is documented (Finding 2); write paths are redacted (Finding 3 → Q5). The pipeline now applies to query-records, get-record, create-record, update-record, and execute-action.
  7. Closed in beta.4: Yomi family (yomifullname et al.) redacts by default on contact / lead / systemuser (F4 + F7); write-path responses now emit the [PII protection: …] audit footer (F5) on powerplatform-data and azure-devops write tools; locale date formats kept as customPatterns-only with copy-paste recipes added to the user doc (F6).

Known v1 limits surfaced by this run

  • Locale-specific date formats ("12 March 1985", "12.03.1985") not caught by built-in L3 → use customPatterns in PII config to extend without forking. Beta.4 added a "Locale date formats — copy-paste recipes" subsection to docs/documentation/pii-protection.md covering English long/short month, German DD.MM.YYYY, UK DD/MM/YYYY, US MM/DD/YYYY. Built-in defaults for these formats remain rejected by design (false-positive risk on build numbers / version strings / timestamps).
  • PII_CONFIG_PATH overrides are not additive — observable in scenario 2 / l1-exclusion of Q5: yomifullname returns raw because the custom config carries a pre-beta.4 contact field list (no Yomi family). The other protected scenarios (l2-only, l2-l3, full-l1-l4) inherit beta.4 defaults and redact correctly. Documented in pii-protection.md; either omit contact from your override or carry yomi entries forward.
  • Audit footer not yet emitted on azure-sql or rest-api tool layers. Services already wrap piiReport, only the tool layer discards. Same mechanical fix as the beta.4 powerplatform-data / azure-devops extension — tracked for v1.6 once those surfaces are exercised by the demo.

Out of scope

Layer 5 (local-LLM final sweep) — deferred to v2 once L1–L4 has at least one engagement of usage.

Phase 6 (audit & compliance logging) — separate session. The footer text in every response is the redaction correlation signal; Phase 6 will persist these as tamper-evident audit records (metadata + counts only, never values).

Other surfaces with write-path body redaction wired in beta.3 but tool-layer footer not yet emitted (carries to v1.6): azure-sql (sql-execute-sproc, sql-execute-unrestricted, CRUD tools) and rest-api (rest-request). Same pipeline, same defaults — will be added to this demo when test fixtures are seeded.

Reproducing this report

  1. Re-seed fixtures into a Dataverse test tenant (tests/pii-demo/README.md "Fixtures").
  2. Configure 6 MCP servers in .mcp.json (one per scenario). For Q5 (write-path), the demo MCPs need POWERPLATFORM_ENABLE_UPDATE=true.
  3. Restart Claude Code.
  4. Fire the 30-call matrix (5 queries × 6 servers) from a single prompt against …__query-records and …__update-record.
  5. Persist responses to tests/pii-demo/output/responses/.
  6. Run node tests/pii-demo/output/_build-manifest.mjs to regenerate manifest.json.
